# SwapPulse API Audit

**Audit date:** 11 September 2026  
**Scope:** SwapPulse/Base44 backend functions, public and authenticated HTTP/API surfaces, AT Protocol/PDS APIs, Web3 RPC/relay boundaries, Discord, Stripe, Turnstile, SMTP/push, TCGDex and market-data providers, webhooks/callbacks, health/status APIs, API contracts and documentation.  
**Status:** **NOT RELEASE READY** until unresolved P0 findings are remediated and the exact production deployment is re-tested.

| Priority | Area | Finding | Required action |
|---|---|---|---|
| 🔴 P0 | Public health API SSRF | `health-check` is public and derives the podcast probe origin from the caller-controlled `X-Base44-App-Url` header. `checkPodcastRss(origin)` then performs a server-side fetch without validating that origin against the application allowlist or the shared SSRF guard. Unless the hosting layer strips/replaces that header before function execution, an unauthenticated request can steer a backend fetch to another origin. | Do not consume `X-Base44-App-Url` directly. Reuse `resolveAppUrl()` or a fixed canonical origin, require HTTPS production hosts, and regression-test loopback/private/link-local/cloud-metadata/redirect targets. Keep the health endpoint unable to fetch arbitrary origins even if proxy headers are spoofed. |
| 🔴 P0 | AT Protocol consent boundary | `atproto-bridge` and `atproto-publish-post` authenticate ownership but do not enforce the user's `Do Not Sell or Share` / federation opt-out at the canonical publication boundary. Higher-level callers such as reconciliation may check consent, but a direct publication call can bypass that preference. | Enforce federation consent inside the canonical record publication/delete/update layer for every non-required outward publication. Fail closed before PDS writes, centralise the policy, and integration-test create/update/delete/manual publish/retry/reconcile paths with consent enabled and withdrawn. |
| 🔴 P0 | Production AT Protocol API availability | Live `AtprotoAccountHealth` records checked on 11 September 2026 show all three monitored identities with `credential_valid:false`, `profile_resolves:false`, `handle_resolves:false`, `repo_reachable:false` and `AT_PDS_UNREACHABLE`. Recent `AtprotoDeliveryEvent` records repeatedly show `AT_AUTHENTICATION_FAILED` and `AT_PUBLICATION_FAILED`. The federation API is therefore materially unavailable in the current live state. | Repair PDS reachability/session credentials without weakening SSRF/origin binding. Run real create/update/delete/profile/handle/repo tests against production, reconcile failed delivery events, add alerting on repeated authentication/publication failures, and do not mark federation healthy until end-to-end publication succeeds. |
| 🔴 P0 | Custom-handle verification authority | `verifyHandleClaim` accepts a caller-supplied `did` rather than binding verification to the authenticated user's authoritative DID. The function returns a trusted-looking verification result for that supplied DID and the current workflow relies on the caller to persist HandleClaim/user state. | Move the entire claim transaction server-side. Derive the DID from the authenticated user, verify the domain against that DID only, create/update HandleClaim through the backend, and prohibit browser writes to verification/approval state. Add tests proving one account cannot verify a domain for another DID. |
| 🔴 P0 | Profile search API contract | The live `search-profiles` function accepts `{ field, value, limit }`, while the current Search UI was previously verified calling it with `{ query }` and swallowing the failure. The supported API and its primary consumer therefore disagree, making cross-profile search non-functional. | Define one versioned contract, update all callers and OpenAPI together, return visible typed errors instead of silent UI fallback, and test local + federated profile search end to end before release. |
| 🔴 P0 | PDS session SSRF / identity binding | Earlier PDS session handling exposed a high-risk arbitrary-origin/identity boundary. | **Completed:** the shared PDS session path now requires HTTPS, resolves and rejects private/reserved/loopback/link-local hosts, validates DID/service origin binding, checks the authenticated PDS session DID, blocks unsafe redirects and uses request deadlines. Keep all PDS clients on this shared path and regression-test DNS rebinding/redirect cases. |
| 🔴 P0 | Starknet relay arbitrary-write boundary | A generic JSON-RPC relay would let a compromised browser or backend submit arbitrary deploy/invoke/devnet calls. | **Completed:** the current transaction relay uses a server-side bearer secret, strict method/contract/selector/class-hash policy, reconstructs expected calldata, validates signed drafts, blocks arbitrary invoke/deploy/devnet methods and has policy smoke tests proving missing-token and disallowed-call rejection. Preserve this architecture. |
| 🔴 P0 | Age-verifier webhook authenticity and replay | A verifier callback that accepted arbitrary evidence/status or replayed events could incorrectly grant or revoke value-bearing adult eligibility. | **Completed:** `age-verifier-webhook` is POST-only, body-size limited, metadata-only, HMAC-SHA256 authenticated with a minimum 32-character secret, constant-time compared, rejects unexpected evidence fields, binds opaque subjects to server records, handles superseded/out-of-order events, detects event-id conflicts and treats completed events idempotently. Keep regression coverage for replay, stale events and chain-sync retry. |
| 🟠 P1 | Handle-verification SSRF | `verifyHandleClaim` blocks obvious IP/hostname strings but its `https://${domain}/.well-known/atproto-did` request does not use `assertSafeHost()`. A hostname can resolve to private/link-local infrastructure or change resolution after validation. The two verification fetches also have no timeout. | Use the shared DNS/IP SSRF guard before every request and after any resolution step, use `redirect:'manual'`/no redirects, enforce a short deadline and response-size cap, and remove the home-grown hostname denylist as the primary SSRF control. |
| 🟠 P1 | Status API truthfulness | Live `StatusService` data contains many critical/high services marked `operational` with `last_checked_at:null`, including the PDS, API Gateway, transaction relay and RPC, while live AT account health shows the PDS path failing. The status surface can therefore communicate operational health without a current probe. | Represent unprobed/stale services as `unknown` or `stale`, attach freshness thresholds, wire real probes for every public status item, and make aggregate status depend on fresh evidence rather than a stored default. |
| 🟠 P1 | Health-check semantics | `checkBase44()` always returns up, while SMTP, VAPID, Stripe and NowPayments checks mostly test whether a secret/config value exists rather than whether the upstream service works. A configured but broken credential is reported as healthy. | Distinguish configuration checks from live dependency checks. Add safe provider probes where appropriate, expose `unknown` when a meaningful check is impossible, record latency/freshness, and never call a service operational solely because a secret exists. |
| 🟠 P1 | Public health diagnostics disclosure | The public `health-check` response includes per-service failure detail originating from internal health helpers, including configuration errors such as missing credential names and upstream HTTP/network details. | Return only coarse public states and a correlation/incident ID. Keep detailed provider/configuration errors in admin-only diagnostics/logging. Review every public health response for environment/topology disclosure. |
| 🟠 P1 | TCGDex request deadlines | The canonical `fetchTcgdex()` helper performs a bare `fetch()` with no `AbortSignal` timeout. Multiple public endpoints and health checks call it directly or indirectly, so a stalled upstream connection can occupy backend workers indefinitely relative to application expectations. | Add a hard deadline to the shared TCGDex fetch, classify timeout separately, cap response bytes and make retries respect one overall request budget. Ensure every TCGDex caller uses the hardened helper. |
| 🟠 P1 | Public card-search amplification | `search-cards` is unauthenticated and can fall back across set forms and many TCGDex language catalogues. One crafted cache miss can generate many upstream calls. The limiter is process-local and the underlying calls have no timeout. | Add per-client/IP/account throttling, persistent/global upstream budgets, cache negative lookups, limit language fan-out per request, add an overall deadline and prefer indexed/local catalogue search before multi-language upstream probing. |
| 🟠 P1 | Third-party provider quota exhaustion | PokéWallet, TCGplayer and other enrichment endpoints use server-held provider credentials and global soft budgets, but public callers are not given meaningful per-client quotas. An abusive client can intentionally exhaust the shared daily/hourly budget and deny enrichment to everyone while staying within the global ceiling. | Add per-client/account/IP quotas in front of provider-backed endpoints, retain global provider headroom as a second limit, cache/negative-cache aggressively and return `429` with retry metadata for abusive clients. |
| 🟠 P1 | Provider quota reservation races | PokéWallet, PokemonPriceTracker, TCGplayer and Impact usage accounting follows read-then-update/create patterns rather than an atomic increment/reservation. Concurrent workers can observe the same count and both reserve capacity, overshooting soft/provider limits. | Replace read-modify-write counters with atomic increments/conditional updates or a transactional quota service. Enforce uniqueness on bucket keys and test concurrent reservations across separate function instances. |
| 🟠 P1 | Provider cache concurrency | Several provider clients implement cache upserts as query-then-create/update and use an in-memory `inflight` map. The map only deduplicates inside one runtime, so concurrent cold workers can duplicate upstream calls and cache rows. | Add unique cache keys plus atomic upsert/lease semantics. Use a short distributed refresh lease so one worker refreshes while others serve stale content. |
| 🟠 P1 | Turnstile response binding | Shared `verifyTurnstile()` and `create-fiat-donation` validate only `success:true`. They do not validate the returned `hostname` or purpose `action`, so a token generated for another allowed widget/surface can potentially be replayed across SwapPulse endpoints until Cloudflare's single-use rule stops it. Cloudflare recommends validating hostname/action when configured. | Configure distinct actions for sensitive surfaces, validate expected `hostname` and `action`, enforce the 2048-character token limit and keep production hostnames explicit. Continue mandatory server-side Siteverify validation. |
| 🟠 P1 | Turnstile availability / timeout | Shared Turnstile verification and the donation-specific Siteverify request have no network timeout. Public form/donation requests can hang on a slow Cloudflare response. | Add a short `AbortSignal` deadline, fail closed for the protected action, optionally use Siteverify idempotency keys for safe retries, and monitor verification latency/failure rate. |
| 🟠 P1 | Stripe checkout idempotency | `create-fiat-donation` creates a Stripe Checkout Session without a Stripe `Idempotency-Key`. A browser/network retry after an ambiguous response can create more than one checkout session for the same user intent. | Generate a server-side donation intent/idempotency key before the Stripe call, send it as Stripe's `Idempotency-Key`, persist it, and make local record creation/retry reconcile to the same session. |
| 🟠 P1 | Stripe request deadlines | Both checkout creation and checkout-session verification call Stripe without a hard timeout. | Add bounded request deadlines and explicit timeout errors to all Stripe calls. Retry only idempotent operations and never retry session creation without the same idempotency key. |
| 🟠 P1 | Donation settlement reliability | Fiat donations are reconciled when the browser returns and calls `verify-fiat-donation-session`; no Stripe webhook handler/signature verification path was found in the current function tree. A successful payment whose browser never returns can remain locally pending. | Add a signed Stripe webhook for authoritative asynchronous settlement, store/process event IDs idempotently, keep return-page verification as a user-facing fallback, and periodically reconcile pending sessions. |
| 🟠 P1 | AT Protocol auth timeouts | Public `atproto-auth` performs handle resolution, PLC/did:web fetches, PDS session creation, profile lookup and follow pagination with multiple raw `fetch()` calls that have no hard deadline. Public callers can therefore tie up work through slow external dependencies even though SSRF validation is strong. | Put all AT HTTP through one timeout/size/redirect-aware client, enforce an overall authentication deadline, cap pagination work and return typed retryable errors. |
| 🟠 P1 | AT bridge remote-blob limits | `atproto-bridge` `uploadBlob` restricts image hosts and redirects, but fetches the remote object with no timeout or byte cap, reads the entire response into memory and trusts the caller-supplied MIME type before uploading it to the PDS. | Enforce upstream timeout, `Content-Length` plus streaming hard byte limit, verify actual image magic/MIME and dimensions, set an AT-compatible maximum and derive the upload MIME from inspected bytes. |
| 🟠 P1 | PDS blob validation | `pds-blob-upload` caps caller-supplied base64 length but accepts any non-SVG `image/*` MIME string, does not verify file magic/dimensions and sends the full decoded object to the PDS without a request timeout. | Validate decoded magic bytes/MIME/dimensions, use a stricter allowlist, add per-user byte quotas and a PDS upload deadline. Keep blobs within the relevant AT lexicon/use-case limits. |
| 🟠 P1 | Link-preview response size | `fetch-link-preview` has good DNS/redirect SSRF protection and a 5-second request timeout, but after headers it calls `res.text()` without enforcing a maximum response size. An authenticated user can point it at a huge public HTML response and force substantial memory allocation. | Reject oversized `Content-Length`, stream with a hard maximum (for example a few hundred KB), stop reading after the limit and cap redirect/header processing. |
| 🟠 P1 | Discord API deadlines | `discordRequest` retries rate limits and transient 5xx responses but does not set an HTTP deadline. Discord OAuth token/profile requests in `discord-link-callback` also have no timeout. A slow Discord connection can stall account linking or role synchronisation. | Add timeouts to every Discord fetch, keep 429-aware retry within one total deadline, and return/reconcile partial OAuth/role-sync state safely. |
| 🟠 P1 | Invite redemption atomicity | `redeem-invite` reads an active code, performs follow/friendship side effects and only then marks the code used. Two concurrent requests can both observe `active`, and a failure after partial social writes can leave the code reusable. | Atomically claim the invite first with compare-and-set/unique redemption state, then perform idempotent side effects. Persist a redemption transaction/state machine so retries resume rather than duplicate work. |
| 🟠 P1 | Invite identity field drift | `redeem-invite` reads `user.data?.did`, `user.data?.bsky_handle` and `user.data?.avatar_url`, while current backend code and the User schema use top-level `user.did`, `bsky_handle`, `avatar`. This can silently create accepted friendships/follows with an empty DID or wrong metadata. | Use the canonical User shape everywhere, fail when a real DID is required, add contract tests against the current Base44 SDK user object and remove legacy `user.data` access. |
| 🟠 P1 | Login-code expiry contract | Normal `send-login-code` stores a 5-minute expiry but its email says 15 minutes. `atproto-auth` independently issues login codes with a 15-minute expiry. The same authentication factor therefore has two security/UX contracts. | Define one expiry constant/shared issuance helper, use it in every login path and email/UI copy, and test exact boundary/clock-skew behaviour. |
| 🟠 P1 | Authentication rate-limit concurrency | Login-code and AT-auth rate controls use query-then-update/create counters. Concurrent requests can race the same bucket and exceed the intended request threshold. | Move authentication throttles to atomic counters/conditional writes with unique subject buckets and test parallel requests from separate workers. |
| 🟠 P1 | Bot-guard failure mode | `send-login-code` catches bot-guard failures and continues. The separate email throttle still provides protection, but failure of the bot-protection subsystem removes one intended control without surfacing degraded state. | Decide and document a fail-closed or degraded-safe policy for authentication abuse controls. At minimum tighten the fallback throttle, alert on bot-guard failure and prevent prolonged silent bypass. |
| 🟠 P1 | IP pseudonymisation strength | `botGuard` describes stored IP data as hashed, but `hashIp()` is a deterministic unsalted 32-bit non-cryptographic hash. IPv4 values are small enough to brute-force, so this is weak pseudonymisation and collision-prone for enforcement. | Replace it with server-secret HMAC-SHA256 over a normalised IP/prefix, rotate/retain keys according to policy and document retention. Do not present a 32-bit checksum as privacy-preserving hashing. |
| 🟠 P1 | RPC gateway client identity | The public RPC gateway rate limiter trusts `CF-Connecting-IP` / `X-Forwarded-For` style headers. If the service is reachable outside the trusted Cloudflare/reverse-proxy path, callers can spoof source identity and bypass per-IP throttling. | Bind the raw gateway to loopback/private ingress, configure the proxy to overwrite forwarding headers, trust forwarded IP only from known proxy addresses and add an ingress test proving direct public access is impossible. |
| 🟠 P1 | RPC computational abuse | The read-only RPC gateway correctly blocks write/devnet/batch methods, but permitted methods such as `starknet_call`/fee estimation can still consume node CPU. In-memory per-IP rate limits are process-local and restart/replica scoped. | Add method-weighted limits, request complexity/calldata caps, concurrency ceilings and edge/global throttling. Keep raw node access private and monitor expensive-method latency. |
| 🟠 P1 | Chain explorer deployment provenance | Current checked-in `chain-explorer` pins `https://rpc.swappulse.org/rpc` and uses 10-second deadlines, but an earlier live audit observed a production `Invalid URL: 'undefined'` failure. This audit could not independently prove the deployed production function matches the checked-in source. | Redeploy/verify the exact commit, run live explorer summary/transaction/block/address tests, record the deployed source revision and fail release if runtime code differs from the canonical tree. |
| 🟠 P1 | OpenAPI release drift | `openapi.yaml` still identifies SwapPulse API `0.9.0` / release `v0.9.0`, while the project has progressed beyond that baseline. The document is labelled authoritative, so stale schemas become a client contract defect. | Regenerate/update OpenAPI from the current supported endpoints, bump the API/release metadata, validate examples against live handlers and gate releases on OpenAPI contract tests. |
| 🟠 P1 | Direct HTTP routing contract | API docs show `https://swappulse.org/functions/{function-name}` with `https://swappulse.org` as the OpenAPI server, while also noting some Base44 deployments use platform-managed function URLs. This audit could not verify those custom-domain function paths externally. | Publish one canonical externally tested transport, include the exact production base URL in OpenAPI, add smoke tests from outside Base44 for every supported route and remove examples for routes not actually served. |
| 🟠 P1 | Status-monitor coverage | `status-monitor` maps and refreshes only a small subset of the 29 published `StatusService` entries. Most displayed API/services never receive an automated `last_checked_at`, yet remain `operational`. | Define monitoring ownership for every published service or remove unsupported entries. The status worker should update all visible services, record probe type/freshness and mark stale/unmonitored entries explicitly. |
| 🟠 P1 | API error-detail leakage | A large number of functions still return `error.message` directly on 4xx/5xx paths. Some messages can include provider status, configuration names, internal function assumptions or upstream details. | Standardise public typed error codes/messages, log detailed errors server-side with correlation IDs and review every endpoint that returns raw exception text. Never include secrets or internal URLs in client errors. |
| 🟠 P1 | API security regression coverage | Security-sensitive API boundaries have bespoke protections but there is no demonstrated single release suite covering health SSRF, consent bypass, handle claims, webhook replay, provider quota races, payment idempotency, AT auth timeouts and RPC abuse together. | Add unit/integration/adversarial API tests for each trust boundary and make them release gates. Include concurrent/race tests, malformed bodies, oversized responses, timeouts, replay and cross-user authority tests. |
| 🟡 P2 | Status-subscription enumeration | After a valid Turnstile challenge, `subscribe-status` returns `alreadySubscribed:true` for a confirmed address, revealing subscription membership to someone who knows the email. | Return the same generic response for new, pending and existing subscribers. Send any state-specific message only to the mailbox owner. |
| 🟡 P2 | Request-method consistency | Some functions explicitly require POST while many others parse JSON regardless of method or do not reject unsupported methods. This makes browser/proxy/cache semantics and CSRF assumptions inconsistent. | Define allowed methods in OpenAPI and enforce them in every handler. Use GET only for side-effect-free public reads and POST/PUT/PATCH/DELETE deliberately for state changes. |
| 🟡 P2 | Malformed JSON handling | Shared `getParams()` and many handlers catch JSON parse failures and silently treat the body as `{}`. A syntactically invalid request can therefore become a defaults-based request rather than an explicit `400 INVALID_JSON`. | Reject malformed JSON with a consistent 400 error on endpoints expecting JSON. Only treat an absent body as empty when the contract explicitly permits it. |
| 🟡 P2 | Public request body limits | Only selected high-risk functions such as the age-verifier webhook implement explicit body-size limits. Many public JSON endpoints rely on platform/runtime limits rather than declaring application bounds. | Add per-endpoint request-size limits for public/authentication/payment/search APIs or document and test the Base44 platform limit if it is the authoritative control. |
| 🟡 P2 | Response envelope consistency | Catalogue APIs, federation APIs, market enrichment, auth, status and chain functions use different success/error shapes (`data`, `ok`, `success`, bare objects, `error_code`, `reason`). | Adopt a stable versioned envelope for supported external APIs or document endpoint-specific schemas precisely. Include machine-readable error codes consistently. |
| 🟡 P2 | Provider limiter scope | TCGDex's sliding-window limiter and several `inflight` maps are in-memory. They do not coordinate separate isolates/instances and reset on cold start. | Treat in-memory limits only as local smoothing. Put provider-wide quotas in persistent/edge coordination where provider terms require a true global rate. |
| 🟡 P2 | Provider version/user-agent drift | Third-party clients identify themselves with mixed historical strings such as `SwapPulse/0.7` and `SwapPulse/0.8`, reducing operational traceability. | Centralise an application/API version identifier and update provider User-Agent/telemetry automatically from release metadata. |
| 🟡 P2 | Legacy NowPayments status surface | Current function search found NowPayments referenced by health/status monitoring, but no current crypto-donation/create-checkout function was present. The status page can therefore report a configured NowPayments secret as an operational API even when no supported product endpoint consumes it. | Either restore and audit the supported crypto-donation API or remove/retire the NowPayments service, docs and health status until it is an active dependency. |
| 🟡 P2 | API correlation / observability | API logging is largely function-specific and there is no consistent request/correlation ID returned across provider calls, webhooks, retries and user-facing errors. | Generate/propagate a request ID at the API boundary, include it in structured logs and safe error responses, and link downstream provider/relay attempts without storing unnecessary personal data. |
| 🟡 P2 | Health-check cache/load control | The public health function can trigger multiple upstream checks on every call, including TCGDex/PokéWallet/PDS/podcast probes, and no endpoint-level cache or public caller throttle is evident. | Cache the public health snapshot for a short interval and run expensive probes from the scheduled monitor rather than per visitor. Serve the last fresh snapshot with its timestamp. |
| 🟡 P2 | External profile-search scalability | `search-profiles` scans up to 500 private ProfileConfig records with the service role and joins matching users in parallel. Visibility is carefully enforced, but growth will make this expensive and relationship caps can make visibility incomplete. | Build indexed/search-safe public projections, paginate deterministically and resolve relationship visibility with purpose-built queries rather than service-role scanning. |
| 🟡 P2 | OpenAPI coverage | The OpenAPI document intentionally covers only selected product endpoints while a much larger Base44 function surface exists. Internal vs supported-public status is not mechanically enforced, so accidental dependency on undocumented functions is easy. | Maintain an explicit API exposure registry (`public`, `authenticated product`, `admin/internal`, `webhook`) and generate/validate OpenAPI from only supported surfaces. Block accidental public exposure in CI. |
| 🟡 P2 | Exact-release execution unavailable | The Base44 command sandbox for this audit mounted an empty `/workspace`, so build/lint/typecheck and executable API/security suites could not be rerun against the exact audited state. File/API inspection and live entity checks were possible, but this is not equivalent to an executable release gate. | Run the complete API test matrix from a correctly mounted exact-commit CI checkout, including production smoke tests, before changing the audit to release-ready. |
| 🟡 P2 | Public status freshness metadata | Public-facing status records do not consistently expose/prove how a service was checked or whether “operational” means configured, probed or manually set. | Store probe type, last success, last failure, latency and freshness/SLO state. Render stale/unknown differently from verified operational state. |
| 🟢 P3 | API documentation version strings | Comments/docs across provider clients retain old application version markers and some legacy provider terminology. | Keep version strings and provider inventory generated from canonical release/config metadata rather than hand-maintained comments. |
| 🟢 P3 | API naming consistency | Function names mix kebab-case and camelCase (`sendPush`, `getFeedSkeleton`, `processAgentFeedback`, `verifyHandleClaim`, etc.), making discoverability and documentation generation harder. | Standardise names for new APIs and provide deprecation aliases/migration notes rather than renaming live callers abruptly. |
| 🟢 P3 | README retrieval during audit | The requested Base44 web-agent README endpoint returned HTTP 403 from the Base44 sandbox and could not be fetched by the web tool. The audit therefore relied on the current app source, root README and API documentation already present in the project. | Keep the MCP/web-agent README accessible to authorised audit tooling or mirror the required operating instructions into the repository so future audits can prove they used the exact current guidance. |

## Verified controls worth preserving

The audit found several strong API boundaries that should not be weakened while fixing the findings above: the shared PDS session resolver uses DNS/IP SSRF protection and identity/origin binding; the Starknet transaction relay rejects arbitrary write methods and reconstructs expected calls; the public RPC gateway is write-blocked and response/body bounded; Discord interactions verify Ed25519 signatures and reject timestamps older than five minutes; the age-verifier webhook is signed, metadata-only and idempotent; market-provider credentials stay server-side and TCGplayer/PokemonPriceTracker usage is policy-gated; `fetch-link-preview` revalidates every redirect target against the shared SSRF guard; and payment verification re-fetches Stripe server-side rather than trusting the browser redirect.

## Release decision

The API surface should remain **NOT RELEASE READY** while the unresolved P0 items remain: health-check SSRF, federation-consent bypass, live AT Protocol/PDS failure, custom-handle DID authority and the broken profile-search contract. After those are fixed, the P1 reliability/security items, especially provider timeouts, Turnstile binding, Stripe idempotency, quota races, blob limits and status truthfulness, should be closed before a production launch sign-off.
