## Executive summary

The current architecture mixes self-asserted platform milestones, trust/authorisation credentials and cryptographically verifiable credentials, although those categories do not have the same assurance. Achievement mutation is admin-only, but many proof sources are user-controlled; service-role issuance does not make weak upstream evidence trustworthy.

The proof/export layer is not ready for cryptographic trust. The browser-generated “ES256K” JWS is reproducible without a private issuer key, snapshots contain only sampled evidence and remain admin-editable/deletable, and the verifier cannot soundly resolve/re-evaluate the captured evidence.

Privacy is release-blocking because public Achievement metadata can expose identifiers originating from private CollectionEntry and ScannerCorrection records, while any authenticated user can ask the service-role verifier to inspect another holder’s snapshot/evidence.

Audit-visible data in this session contains **0 Achievement rows, 0 AchievementProofSnapshot rows, 0 TradingFeedback rows, 0 Vouch rows, 0 CardReview rows and 0 ScannerCorrection rows**. This is audit-session evidence only, not a claim about all production history. No visible exploitation was found.

The required Base44 web-agent README returned HTTP 403. The command sandbox exposed only an empty `/workspace` without `package.json`, so exact-release build, lint, typecheck and executable Achievement tests could not be run here.

No functional code or production data was changed during this audit.

## Verified strengths to preserve

- Achievement create/update/delete is administrator-only.
- Rules are centralised in versioned `achievementConfig.ts`.
- The evaluator is a pure function, a useful testability boundary.
- Scanner corrections start quarantined with `accepted:false`, and only approved + accepted rows count for Scanner Sage.
- A 24-hour revocation grace concept exists.
- Account deletion/force deletion include Achievement and AchievementProofSnapshot.
- Proof snapshots already have a policy-hash/integrity-hash concept that can evolve into a real evidence commitment.
- No audit-visible Achievement/snapshot rows currently exist, reducing migration risk if fixed before use.

## Release decision

**Do not release Achievements as cryptographically verifiable credentials, Trusted Trader authority, or external-role proof while AC-001 through AC-012 remain unresolved.**

Recommended order: **separate self-asserted milestones from verified credentials → secure all upstream evidence → bind holder identity server-side → remove private proof-reference leakage → make evaluation/snapshots append-only and complete → disable simulated signed-VC export → fix revocation freshness/role gating → implement a real issuer/status/verifier or relabel accurately → fix portability/data rights/profile status → harden the Goal Tracker → run the full adversarial release suite.**
