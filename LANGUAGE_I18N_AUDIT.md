# SwapPulse Language / Internationalisation Audit

**Audit date:** 11 September 2026  
**Scope:** Supported interface locales, static and dynamic translation coverage, language selection and persistence, TCGDex catalogue localisation, legal/policy localisation, SEO language metadata, dates/numbers/currency, emails/push/system messages, Help translations, AI translation pipeline, geo-locale detection, accessibility and localisation release controls.  
**Supported interface locales:** English (UK), Spanish, French, German, Italian, Brazilian Portuguese, Japanese, Simplified Chinese and Korean.  
**Status:** **NOT LANGUAGE-RELEASE READY**. Critical privacy and translated-content integrity issues remain, and selecting a non-English locale does not currently produce a consistently localised end-to-end experience.

| Priority | Area | Finding | Required action |
| --- | --- | --- | --- |
| 🔴 P0 | Geo-language privacy | On a first visit without a saved language, the browser calls `ipapi.co` and then `ipwho.is` to infer locale from the visitor's IP. The Privacy Policy says the user's language preference is not shared with third parties and does not disclose either geolocation provider. The requests occur before an explicit language/analytics consent choice. | Remove third-party IP geolocation from locale selection, or obtain/disclose the appropriate consent and providers before the request. Prefer browser language as the privacy-preserving default. Update the Privacy Policy and data inventory before re-enabling any geo inference. |
| 🔴 P0 | Translated Help integrity | Live AI-generated `TranslationOverride` records translate obsolete or inaccurate Help source material into all eight non-English languages. Verified examples include `help.wallet` describing the retired custodial multi-chain/fiat/escrow wallet, `help.online-now` promising a presence-disable control that does not exist, `help.search` describing a real firehose/network-wide search that the AT audit disproves, and `help.labelers` describing protocol-native labelers that the current architecture does not implement. | Freeze publication of translated Help until the English source is reconciled with the current product. Add source revision/hash tracking, invalidate translations whenever source text changes, require review for security/privacy/financial/protocol content, and regenerate only after the authoritative source is correct. |
| 🟠 P1 | Interface translation completeness | SwapPulse advertises nine interface locales, but the non-English static translation files are materially smaller than `en.js` and the runtime silently falls back to English for missing keys. Choosing a supported locale therefore does not guarantee a fully translated UI. | Build an exact key-coverage report from the real runtime dictionary, require 100% coverage for release-critical/public UI, and expose fallback counts per locale. Do not call a locale fully supported while material screens still rely on English fallback. |
| 🟠 P1 | Language settings localisation | `LanguageSection.jsx`, the page users visit to configure languages, is itself hardcoded in English, including Interface language, Auto-translate posts, Target language, Translation provider, Languages I speak, Hide posts in these languages and privacy ratings. | Move all language-setting labels, descriptions, provider/privacy text and accessibility labels into the translation system for all nine locales. |
| 🟠 P1 | Terms localisation | The Terms page uses `t()` only for the page title. The table of contents, all 22 sections, last-updated text, navigation and SEO metadata are hardcoded English. Non-English users are therefore shown an English legal agreement. | Treat Terms as a separately versioned legal document. Provide reviewed translations where offered, clearly identify English as authoritative, include locale/version/date metadata and do not advertise a translated legal page until its body is actually translated. |
| 🟠 P1 | Privacy Policy localisation | The Privacy page similarly translates only its page title. Its table of contents, all policy text, last-updated text, navigation and SEO metadata remain English. | Provide reviewed policy translations or explicitly mark the policy as English-only. Keep legal translation versions tied to the exact authoritative English policy revision. |
| 🟠 P1 | Legal source accuracy before translation | The authoritative English Terms/Privacy source itself contains statements that conflict with the hardened product, including old claims that collection entries and DMs are federated and that automated AI moderation applies labels. Translating the current source would multiply incorrect legal/privacy representations. | Reconcile the authoritative English legal copy against the backend, AT Protocol, LLM and privacy audits first. Only then translate and version it. Add policy-to-implementation review to every release containing material data-flow changes. |
| 🟠 P1 | hreflang accuracy | `useSEO()` publishes hreflang alternates for all nine locales on every page, even pages whose bodies are English-only or partially translated. Search engines are therefore told that equivalent translated pages exist when they do not. | Emit hreflang only for language variants that are substantially translated and semantically equivalent. Maintain per-route locale availability instead of assuming every route exists in every language. |
| 🟠 P1 | Localised SEO content | Many pages pass hardcoded English titles/descriptions/JSON-LD to `useSEO()`, including Login, Explore, Terms and Privacy. Changing the UI language therefore changes `og:locale` but can leave the actual search/social metadata English. | Put public-page SEO title, description and structured-data strings into reviewed locale dictionaries and test each supported locale's rendered metadata. |
| 🟠 P1 | Translation precedence | Runtime lookup order is `TranslationOverride` first, then the static locale dictionary, then English. An AI/manual override can therefore replace a reviewed static human translation. | Make reviewed static/manual translations authoritative, or introduce explicit approval/priority fields. AI-generated content should never silently supersede a reviewed human translation. |
| 🟠 P1 | Translation schema/runtime mismatch | The `TranslationOverride` schema description states that static human translations always win, but `I18nProvider` implements the opposite precedence. | Make the schema documentation and runtime behaviour agree, with automated precedence tests. |
| 🟠 P1 | Translation coverage audit correctness | `audit-translations` checks `TranslationOverride` records against `UI_STRINGS_EN` and does not count valid translations already present in the static locale files. It can therefore report a translation missing even when the runtime already has it. | Audit the same merged dictionary the runtime actually uses: reviewed static strings plus approved overrides plus fallback state. |
| 🟠 P1 | Hardcoded-string detection | The translation audit cannot discover English strings written directly in JSX/TS or backend messages. Significant hardcoded English exists across settings, login, profile themes, moderation, messages, onboarding and card-search flows. | Add static lint/AST checks for user-facing literals outside approved exceptions and include them in the localisation release gate. |
| 🟠 P1 | False translation-green state | The admin Translation Management UI can say “All translations present — no pages falling back to English” even though the audit does not inspect static fallback behaviour or hardcoded strings. | Change the completion claim to reflect only what is actually measured, then expand the audit until a green result really means no unintended English fallback/hardcoded UI for the tested locale. |
| 🟠 P1 | AI translation approval | `sync-translations` makes an LLM translation active immediately after generation. There is no required human review before it is displayed to users. | Add `pending → reviewed → published` states, reviewer identity/timestamp and a preview/diff workflow. Require human review for legal, security, privacy, financial, moderation and Web3 terminology. |
| 🟠 P1 | Translation freshness | Translation overrides retain `source_value` but no authoritative source hash/revision relationship is enforced. If English text changes, an old translation can remain active indefinitely. | Store a cryptographic/source revision for every translated key and automatically mark translations stale whenever the source changes. |
| 🟠 P1 | Placeholder/tag integrity | AI translation output is not validated to ensure placeholders such as `{handle}` and permitted inline tags are preserved exactly. A translation can silently drop/rename a placeholder or damage structured markup. | Parse and compare placeholder/tag sets before publishing. Reject translations with missing/extra placeholders, invalid tags or malformed structured content. |
| 🟠 P1 | Terminology control | The AI translation prompt contains only a short brand-name keep-list. There is no maintained glossary/style guide for Pokémon TCG terms, AT Protocol concepts, Web3 security language, moderation terminology or product names. | Maintain per-language terminology/glossary rules and run automated term checks plus human linguistic review. |
| 🟠 P1 | Structured Help translation robustness | Help translations are stored as AI-generated JSON strings. `useHelpContent` contains compatibility normalisation for prior structural damage and silently falls back to English when parsing fails. | Translate structured fields individually or enforce a strict JSON schema, validate before publish and expose malformed/stale translation errors to administrators rather than silently hiding them. |
| 🟠 P1 | Auto-translate posts control | Settings offers “Auto-translate posts”, target language and Local/DeepL/Google provider choices, but source-wide inspection found no post-rendering translation engine consuming these settings. | Implement the feature end to end with consent/privacy and provider handling, or remove/label the controls unavailable. Do not present provider/privacy choices for a function that is not operating. |
| 🟠 P1 | Fluent/hidden language controls | “Languages I speak” and “Hide posts in these languages” are stored in settings, but no feed/search consumer was found applying `fluent` or `hidden`. | Wire these preferences into language detection/feed filtering with an override/reveal mechanism, or remove the controls. |
| 🟠 P1 | Catalogue locale split | Explore, SetQuickFilter and FilterPanel often derive TCGDex language from `settings.language.preferredContent[0]`, whose default is `en-GB`, instead of the active interface locale/current card-language setting. A user can switch the UI to French/Japanese/etc. while set/type catalogue metadata remains English. | Establish one documented precedence: explicit card-language override → active interface locale → English fallback. Make all catalogue entry points use the same reactive source. |
| 🟠 P1 | Simplified Chinese catalogue mapping | `zh-CN` maps to internal `zh`, while the backend intentionally maps internal `zh` to the TCGDex API's `zh-tw` (Traditional Chinese). Thus the Simplified Chinese interface defaults its catalogue to Traditional Chinese instead of `zh-cn`. | Map `zh-CN` to internal/API `zh-cn`. Reserve internal `zh`/API `zh-tw` for a future Traditional Chinese locale and add mapping tests. |
| 🟠 P1 | Brazilian Portuguese catalogue mapping | The `pt-BR` interface maps to generic internal `pt` even though the catalogue layer supports the distinct `pt-br` code. | Map Brazilian Portuguese to `pt-br` and keep Portuguese variants explicit. Test card/set names across `pt-br` and `pt-pt`. |
| 🟠 P1 | Geo locale accuracy | Country-to-locale inference collapses multilingual/regional countries into one locale, e.g. Belgium→French, Switzerland→German, Hong Kong/Taiwan/Singapore→Simplified Chinese and Portugal→Brazilian Portuguese. Geo detection can also override a user's browser language and then writes the guess to localStorage as a sticky preference. | Prefer browser/account language over country inference. If geo suggestions remain, offer them as a non-sticky suggestion rather than silently changing the interface. Use regionally correct variants. |
| 🟠 P1 | Date/time localisation | Many components call `toLocaleDateString()`/`toLocaleString()` with the browser default locale rather than the selected SwapPulse locale. Switching SwapPulse language therefore does not reliably switch dates/times. | Centralise date/time formatters around the active locale and the user's configured timezone/date/time preferences. |
| 🟠 P1 | Shared formatting | `src/lib/format.js` hardcodes `en-GB`, GBP and English condition/variant/trade-status labels. These helpers are reused in non-English UI. | Make formatters accept/use active locale and currency, and translate enumerated product/status labels through stable keys. |
| 🟠 P1 | Relative time localisation | `timeAgo()` uses Moment `fromNow()` without synchronising Moment's locale to the selected interface language. Relative-time text can therefore remain English. | Prefer `Intl.RelativeTimeFormat` with the active locale, or synchronise Moment locale and ship/test the required locale data. |
| 🟠 P1 | Email localisation | Many user-facing backend emails are hardcoded English, including login/security codes, onboarding/activation, weekly digests, wishlist alerts, suspension/enforcement and status communications, even though `User.locale` is stored. | Create server-side locale dictionaries/templates and render transactional emails using the recipient's saved locale, with reviewed English fallback. |
| 🟠 P1 | Push/system notification localisation | Push and in-app system messages are commonly constructed in English on the backend, including new messages, starter-pack events, AT migration events, status incidents and chain recovery. | Localise server-generated notifications using the recipient locale and stable message keys/parameters rather than final English strings. |
| 🟠 P1 | Backend error localisation | Frontend catch blocks frequently surface raw backend/provider `error` messages. Those messages are predominantly English, so non-English users receive mixed-language error states. | Return stable machine error codes plus safe parameters. Translate user-facing errors in the client/server presentation layer instead of displaying provider text. |
| 🟠 P1 | Competing locale state | Interface language can exist simultaneously in localStorage, `User.locale`, `SettingsConfig.locale.interface`, URL `?lang`, browser language and geo detection. Global LanguageSwitcher updates some of these while LanguageSection updates an additional SettingsConfig field. They can diverge. | Define one authoritative account preference plus a clearly ordered session override. Remove redundant persisted locale fields or reconcile them transactionally. |
| 🟠 P1 | Card-language account restore | `setCardLanguage()` writes `User.card_language` and localStorage, but the frontend source contains no reader that restores `User.card_language` into a new browser/device. The claim that the card-language choice “survives sessions/devices” is therefore not demonstrated. | Load the saved account card-language preference after authentication when no local explicit override exists, and test cross-device persistence. |
| 🟠 P1 | Translation override loading | Every app mount loads up to 5,000 recent TranslationOverride rows plus up to 5,000 Help rows for all languages, then filters in the browser. This is unnecessary payload, exposes every language's translation corpus publicly and can silently omit older non-Help overrides after the cap. | Fetch only the active language/relevant revision, cache/version the bundle and page or prebuild translation assets. Do not rely on a global 5,000-row cap for correctness. |
| 🟠 P1 | Card-language filter coverage | `CardLanguageSwitcher` supports 17 catalogue languages, but the reusable `LanguageFilter` only offers All plus nine legacy language codes. Users cannot consistently search/filter all languages that the catalogue selector claims to support. | Generate all catalogue language controls from one canonical language registry and test all supported codes. |
| 🟠 P1 | Interface/catalogue promise | Language Settings says switching interface language “switches the UI and card catalogue instantly”, but an explicit card-language override can intentionally keep catalogue language different, and Explore can remain bound to `preferredContent`. | Rewrite the copy to explain the independent card-language option and fix the inconsistent catalogue source. |
| 🟠 P1 | Static translated product claims | Non-English static dictionaries also contain translated product statements about federation, identity/data portability, AI moderation and on-chain achievements that have drifted as the architecture changed. These translations can remain stale even after English product behaviour changes. | Include translation-source freshness in product documentation/UI changes and audit high-risk claims across every locale after architecture changes. |
| 🟠 P1 | Localisation regression testing | There is no demonstrated automated release suite that renders critical pages under all nine locales and checks for raw keys, unintended English fallback, overflow, broken placeholders, malformed Help JSON and locale-specific formatting. | Add locale-matrix component/E2E tests for authentication, settings, feed, messages, legal pages, wallet/Web3 and error states. | 🟡 P2 | `?lang` persistence | A `?lang=LOCALE` link is treated as an explicit language choice and immediately written to localStorage. Following a shared/promotional localised link can permanently change the visitor's future default language until they manually switch it back. | Treat URL language as a page/session override unless the user explicitly chooses to save it. |
| 🟡 P2 | First-load language flash | `getInitialLocale()` renders synchronously from URL/storage/browser, then the mount effect can replace it with account/geo locale. This can produce a visible language switch after initial render. | Resolve account/session preference before the primary shell where possible, or use a short locale-loading state without external geo lookup. |
| 🟡 P2 | Pluralisation/grammar | The translation function provides simple key lookup and `{placeholder}` replacement only. It has no ICU/message-format plural, select or grammatical rules. | Adopt `Intl.PluralRules`/ICU MessageFormat for count- and gender/grammar-sensitive strings rather than concatenating English-shaped phrases. |
| 🟡 P2 | Locale-save failures | `setLocale()` swallows account persistence failures. The browser appears to save the language even if the account preference fails, causing cross-device divergence without feedback. | Keep local switching responsive but expose sync status/retry and reconcile authoritative account state. |
| 🟡 P2 | Language-control accessibility copy | `CardLanguageSwitcher` and `LanguageFilter` still contain hardcoded English labels/ARIA text such as “Card language”, “Select card data language”, “Filter card language” and “All Languages”. Screen-reader users therefore receive English controls in non-English sessions. | Localise visible labels and accessible names using the same dictionaries as the surrounding page. |
| 🟡 P2 | User date/time preferences | Settings defines timezone, `dateFormat` and `timeFormat`, but most UI formatting does not consume those preferences consistently. | Introduce one locale/timezone formatting service and migrate user-facing timestamps to it. |
| 🟡 P2 | Client-only language SEO | `<html lang>`, hreflang and route SEO are changed after React mounts. Non-JavaScript crawlers/social unfurlers can see the default English document regardless of the selected locale. | Pre-render or generate locale-aware metadata at the server/edge for public pages that are genuinely localised. |
| 🟡 P2 | Regional language variants | One locale is used broadly across different regional variants: `es-ES` for Latin America, `fr-FR` for all Francophone regions, `de-DE` for Austria/Switzerland and `pt-BR` for Portugal. Vocabulary/date expectations can therefore be regionally wrong. | Either present these as generic language choices or add regional variants where product usage justifies them. Do not infer a specific regional locale solely from country shortcuts. |
| 🟡 P2 | CJK/layout QA | Japanese, Simplified Chinese and Korean are supported, but no dedicated automated layout/typography regression evidence was available for CJK line breaking, narrow controls, truncation and translated modal/page expansion. | Add screenshot/visual regression checks at mobile/tablet/desktop widths for every locale, with emphasis on CJK and longest German/French strings. |
| 🟡 P2 | Exact-release verification | The Base44 command sandbox remains detached from the authoritative app tree, so a complete executable dictionary/key scan and locale-matrix test suite could not be rerun from that shell against this exact state. | Run i18n lint, dictionary coverage, build/typecheck and locale E2E tests from an exact-commit CI checkout before changing the release status. |
| 🟢 P3 | LanguageSwitcher event cleanup | `LanguageSwitcher` adds an anonymous `keydown` listener whenever opened but removes only the mousedown listener. Repeated opens accumulate Escape handlers. | Register the key handler in a named variable and remove it in the effect cleanup. |
| 🟢 P3 | Legacy locale comments | Translation code still contains comments/mappings for retired `en-US`, Arabic, Hindi and Russian interface locales, which are no longer offered. | Separate explicit migration aliases from currently supported locales and update comments/documentation to avoid implying unsupported UI languages. |
| 🟢 P3 | Internal catalogue aliases | The catalogue layer deliberately uses internal aliases `jp` and `zh` while the current TCGDex API uses `ja` and `zh-tw`. The backend compatibility mapping works, but multiple registries make future mapping mistakes easier, as demonstrated by the `zh-CN` bug. | Centralise interface locale, internal catalogue code and upstream API code in one typed registry with unit tests and avoid duplicating language maps across frontend/backend files. |

## Verified strengths

SwapPulse already has several useful localisation foundations worth preserving. It has nine explicit interface locales with native language names, a separate 17-language card-catalogue selector, English fallback that prevents blank interfaces, runtime `<html lang>` updates, parameter interpolation, locale-aware wallet/chain date formatting in newer components, and language-specific catalogue cache keys. The backend TCGDex client also deliberately normalises its historical internal aliases (`jp`→current API `ja`, `zh`→current API `zh-tw`), so Japanese catalogue calls are not broken merely because the internal alias is `jp`. Translation writes/generation are admin-only, and the language switcher exposes proper listbox semantics.

## Language release decision

SwapPulse should **not** describe all nine interface languages as complete end-to-end translations yet. The highest-priority remediation order is: **remove/disclose IP geolocation and fix the Privacy Policy → correct stale English Help/legal/product source material → invalidate/regenerate stale translations → fix Simplified Chinese/Brazilian Portuguese catalogue mappings and catalogue-language precedence → make the translation audit measure the real runtime and hardcoded strings → localise legal/security/system communications → replace decorative language controls with working functionality → unify date/number/locale state → add nine-locale release tests.**

Only after those changes should the product claim that a supported non-English locale provides a complete, consistent interface rather than a translated core with English fallback.
