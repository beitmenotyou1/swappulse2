| 🔴 P0 | WTF-001 - Cross-user RecommendationCache poisoning | `RecommendationCache.did` and its free-form recommendations payload are caller-controlled, while `getFeedSkeleton` later service-role reads the newest cache by DID. An authenticated attacker can create a cache row labelled with another collector's DID and inject recommendation state for the victim. | Make RecommendationCache backend-only, key it to authenticated user identity plus server-derived canonical DID, type/limit the payload, enforce uniqueness/versioning and test victim-DID poisoning. |

## Executive summary

Who to Follow is **not currently a functioning or trustworthy personalised recommendation feature**. The dedicated page and home sidebar request the wrong backend feed and then expect a response shape that the actual Who to Follow branch does not provide.

Behind that integration failure are two release-blocking state-isolation issues: RecommendationPreference and RecommendationCache accept caller-controlled DIDs while backend reads use service-role lookup by DID. Follow and Vouch provenance is also not authoritative, making the trust graph, existing-follow exclusions and mutual-vouch explanations forgeable.

The deployed personalisation is much narrower than the product copy claims. Raw private collections are deliberately excluded, which is a privacy strength, but no trade, Circle or interest signals replace them. Persona and region are null, several preference fields do nothing, and the persona cap can restrict output to three candidates.

Federated discovery is also incomplete. Bluesky mutuals are capped/partially silent, the advertised Who to Follow AT feed uses actor profile records where an AT feed skeleton expects post URIs, and all three monitored AT identities are currently unhealthy.

Audit-visible data returned **0 RecommendationPreference rows** and **1 RecommendationCache row**; that cache contained an empty recommendation list generated 13 August 2026. This describes only what the audit session could see, not a guarantee about all production records.

The required Base44 web-agent README returned HTTP 403. Connected source/schema/data APIs remained available. The command sandbox did not expose the canonical app checkout, so exact-commit build/lint/typecheck and executable security tests remain residual verification actions.

No user, follow, vouch or recommendation data was changed. Only this audit report was added.

## Recommended remediation order

1. Bind RecommendationPreference/Cache to immutable authenticated user identity and make cache server-only.
2. Replace browser-direct Follow/Vouch trust inputs with backend-authoritative graph mutations/projections.
3. Split the app people-recommendation API from AT post feed-skeleton endpoints.
4. Fix WhoToFollow and RightSidebar against one typed app DTO.
5. Add block/mute and enforcement exclusions before scoring and again before cache serve.
6. Repair score semantics, persona cap and preference toggles.
7. Add only explicit privacy-safe/opt-in collection, Circle, trade or interest projections.
8. Repair federated follow/mutual reliability and disclose partial graph state.
9. Update Privacy, help copy and localisation to match reality.
10. Run full unit, integration, adversarial and exact-release build gates.

## Release decision

**Do not release Who to Follow as a trustworthy personalised recommendation feature while WTF-001 through WTF-006 remain unresolved.**

## External standards check

Current AT Protocol feed guidance describes a custom feed generator as returning a list of **post URIs** for AppView hydration. The current SwapPulse Who to Follow branch instead places actor profile record URIs in the skeleton `post` field, so the people-recommendation feature should not be represented through that post-feed contract.
