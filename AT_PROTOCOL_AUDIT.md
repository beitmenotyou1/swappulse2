# SwapPulse AT Protocol Audit

**Audit date:** 11 September 2026  
**Scope:** SwapPulse AT Protocol identity, PDS hosting and sessions, DID/handle resolution, repository reads/writes, sync/relay ingestion, AppView compatibility, custom Lexicons, federation privacy, moderation labels, social graph reconciliation, account migration/export, blobs/media, OAuth/app-password authentication and live production state.  
**Status:** **NOT RELEASE READY** until unresolved P0 findings are remediated and end-to-end production federation is proven.

| Priority | Area | Finding | Required action |
|---|---|---|---|
| 🔴 P0 | Production federation availability | Live `AtprotoAccountHealth` records checked on 11 September 2026 show all three monitored identities with `credential_valid:false`, `profile_resolves:false`, `handle_resolves:false`, `repo_reachable:false` and `AT_PDS_UNREACHABLE`. Recent delivery events repeatedly show `AT_AUTHENTICATION_FAILED` and `AT_PUBLICATION_FAILED`, and a public post remains unbridged after eight failed federation attempts. | Restore PDS/session connectivity without weakening origin/DID validation. Prove handle resolution, profile resolution, repository reads, create/update/delete and AppView visibility for real accounts. Reconcile failed delivery events and keep federation release-blocked until live publication succeeds. |
| 🔴 P0 | Relay / firehose architecture | `firehose-ingest` does not consume `com.atproto.sync.subscribeRepos`. It is a five-minute poller over selected PDS repositories plus limited Bluesky AppView searches. It has no network relay sequence cursor, repository revision tracking, commit-chain verification, `#identity`/`#account` event handling or formal desynchronisation recovery. This is not network-wide AT Protocol synchronisation. | Replace or supplement polling with a protocol-native relay/Jetstream/subscription consumer. Track sequence and repo revision, process identity/account events, verify continuity, persist durable cursors and trigger `getRepo`/resync when continuity is lost. Keep polling only as reconciliation/backfill. |
| 🔴 P0 | Live inbound sync state | The newest live `IngestCursor.last_run_at` observed is 21 August 2026, with duplicate rows for the same repo/collection, while `StatusService` marks `AT Protocol Relay (Firehose)` operational on 11 September 2026. The PDS status row is also `operational` with no `last_checked_at`. The inbound pipeline therefore appears stale while the status surface reports health. | Make relay health depend on advancing durable sequence/revision state and maximum ingestion lag, not only PDS `_health`. Enforce one cursor per stream/repo state, alert on stalled progress and mark stale/unknown services non-operational. |
| 🔴 P0 | Federation consent boundary | `outbound-reconcile` and `initial-push-custom-records` honour `do_not_sell`, but canonical publication paths such as `atproto-bridge`, `atproto-publish-post` and the retry worker do not enforce the preference themselves. Direct/manual/retry publication can therefore bypass the user's federation opt-out. | Move consent enforcement into the canonical outward-publication boundary used by every create/update/retry/reconcile path. Fail closed before PDS writes and test opt-out before publication, after withdrawal and during retries. |
| 🔴 P0 | Cross-PDS bearer destination | `initial-push-custom-records` authenticates each user with `getPdsSessionForUser(identity.pdsUrl, ...)` but then sends `session.accessJwt` to the global `PDS_URL` rather than the validated `s.pdsUrl`. For users hosted elsewhere this can disclose a bearer token to the wrong PDS origin and makes the bulk push fail or publish to the wrong service. | Use the validated per-user PDS origin returned with the session for every request. Add an invariant that bearer credentials can only be sent to the origin they were minted for, plus a multi-PDS regression test. |
| 🔴 P0 | Custom handle authority | `verifyHandleClaim` accepts a caller-supplied DID rather than deriving the authoritative DID from the authenticated user. `HandleClaim` owner RLS also permits client create/update of trusted verification fields such as DID/status/timestamps. A user can therefore manufacture trusted-looking claim state for another DID even if the PDS later rejects the handle. | Make handle claiming a single backend transaction. Derive DID from the authenticated account, verify DNS/HTTPS against that DID, persist status server-side and make DID/status/method/timestamps backend-only. Test cross-account DID substitution. |
| 🔴 P0 | Custom-record authorship provenance | Multiple `org.swappulse.*` ingest mappers prefer self-asserted payload fields such as `authorDid`, `raterDid`, `voucherDid`, `participantDid`, `hostDid`, `reviewerDid` or `curatorDid` over the repository DID. An attacker can publish a record in their own repo while claiming another person's DID, and SwapPulse can store that claim as provenance. | Treat the repository DID from the AT URI/commit as the authoritative author for every user-authored custom record. Ignore or validate redundant author-DID fields against it. Add adversarial tests for forged rater/voucher/host/author DIDs. |
| 🔴 P0 | Portable trust and reputation | Local Vouch/Reputation-style records allow owners to supply trusted DID/trade/provenance fields, while federated mappers also trust body-provided author DIDs. `get-portable-reputation` additionally reads the shared repo and expects snake_case fields even though current custom records are written per-user with camelCase Lexicon fields. Portable trust is therefore forgeable locally and functionally inconsistent on the network. | Redesign trust records so issuer/rater identity is bound to authenticated user/repo DID and referenced trades are verified server-side. Rebuild portable reputation from validated AT records indexed by repo DID/URI, not self-asserted fields. Do not consume current reputation for privileged roles until provenance is fixed. |
| 🔴 P0 | Community labeler approval | `CommunityLabeler` owners can update `approval_status`, reviewer metadata and counters through entity RLS. `apply-community-label` trusts approved status, so a labeler owner can self-approve and then issue labels. No live labelers were present during this audit, but the privilege boundary is structurally open. | Make approval/revocation/reviewer fields admin/backend-only and derive counters server-side. Require an approved immutable labeler identity before accepting label operations. Add self-approval and cross-labeler tests. |
| 🔴 P0 | Post federation provenance | Post owners can update whole Post rows, including DID/AT URI/CID/bridged/federation/moderation fields. These fields are later used for federation state, ownership and reconciliation, so a client can forge local protocol provenance or status. | Split user-editable content from backend-only federation/moderation metadata. Lock DID, AT URI, CID, bridged flags, federation state/attempts/errors and trusted counters to backend/admin updates. Derive owner identity from authentication. |
| 🔴 P0 | Account deletion and PDS lifecycle | `delete-account` does not delete or deactivate a SwapPulse-provisioned PDS account/repository. Its PDS step attempts a moderation-label `tombstone` rather than account/repo deletion, then removes the Base44 user. The fallback anonymisation also does not clear PDS URL/app-password and migration identity fields, and retired `PdsCredential` rows are omitted. | Define explicit self-sovereign choices: disconnect/export while leaving an externally owned repo intact, or strongly authenticated deletion/deactivation of a SwapPulse-provisioned PDS account. Revoke stored credentials, clear all AT identity secrets, remove legacy PdsCredential rows and verify public repo/account state after erasure. |
| 🔴 P0 | Custom-record network discovery | `register-lexicons` states that publishing `com.atproto.lexicon.schema` records makes custom collections discoverable/indexed on `bsky.app`. Publishing a Lexicon makes its schema resolvable; it does not make Bluesky's AppView index arbitrary custom collections. SwapPulse currently has no proven network-wide indexer for `org.swappulse.*` records. | Build protocol-native discovery/indexing for SwapPulse collections, for example relay/Jetstream/Tap or `listReposByCollection` plus repository sync and a SwapPulse AppView/search index. Treat Bluesky AppView as an `app.bsky.*` compatibility service, not the index for custom records. |
| 🔴 P0 | PDS session SSRF / bearer binding | Earlier per-user PDS session handling exposed an arbitrary-origin and identity-binding risk. | **Completed:** the shared `getPdsSessionForUser` path now enforces HTTPS, DNS/IP SSRF checks, redirect blocking, PDS origin validation, session-DID matching and request deadlines. Keep all bearer-bearing PDS operations on this shared origin-bound path and regression-test DNS rebinding/redirect cases. |
| 🔴 P0 | Private data in public AT repositories | Earlier designs described DMs, collection state, wishlists, disputes, challenge entries and similar records as federated even though AT repositories are public. | **Completed for new publication:** `federationPolicy.ts` now centralises `NEVER_FEDERATE` for sensitive/local-only collections and DirectMessage/Conversation are local E2EE records. Keep the boundary fail-closed. Historical PDS copies must still be independently checked/remediated before declaring old data clean. |
| 🟠 P1 | Lexicon namespace authority | SwapPulse code publishes `org.swappulse.*` schemas but does not verify at release/runtime that the required `_lexicon.swappulse.org` authority record resolves to the DID/repository hosting those schema records. A schema record alone is not authoritative. | Add a deployment verification that resolves `_lexicon.swappulse.org`, checks the `did=` value, resolves that DID/PDS and fetches each expected schema record by NSID. Fail federation activation if authority cannot be proven. |
| 🟠 P1 | `site.standard.*` authority | The local registry republishes six `site.standard.*` schemas into the SwapPulse schema repository. SwapPulse does not control the `standard.site` authority namespace, so those records are not authoritative definitions of those NSIDs and can drift from the real Standard.site schemas. | Do not register third-party Lexicons as if SwapPulse owned them. Resolve and consume the canonical `site.standard.*` schemas from their authority, pin/validate compatible versions and publish only records that conform to the authoritative definitions. |
| 🟠 P1 | Lexicon/privacy source drift | The Lexicon registry and entity descriptions still describe several `NEVER_FEDERATE` record types as "mirrored", "portable" or "cross-instance", including collection entries, wishlists, DMs, disputes, challenge entries and subscriptions. These descriptions contradict the current privacy policy and can lead future code to re-open unsafe publication paths. | Remove or clearly mark private/local-only Lexicons as non-publishable, align entity docs, builders and UI copy with `federationPolicy.ts`, and add a CI assertion that `NEVER_FEDERATE` collections cannot appear in outward publication registries. |
| 🟠 P1 | AT moderation labels | `atproto-bridge`/`moderatePost` use `com.atproto.label.emitLabels` through the PDS as a best-effort network label path. Current AT label architecture uses a labeler service identity with signed labels and public `queryLabels`/`subscribeLabels`; no standards-based distribution path equivalent to this PDS call was found. | Separate SwapPulse custom community labels from protocol-native AT labels. If network moderation labels are required, operate/integrate a real labeler service such as Ozone, publish its DID/service endpoint, sign labels and expose the standard label query/subscription interfaces. |
| 🟠 P1 | End-user AT authentication | `atproto-auth` asks end users for app passwords and stores an encrypted app password for linked accounts. Current AT Protocol guidance makes OAuth the primary client authentication method and recommends OAuth for end-user login flows; password/app-password sessions are legacy-compatible and better suited to bots/CLI tools. | Migrate account linking/login/write authorisation to AT OAuth using the supported OAuth client libraries, PKCE/DPoP/PAR/session refresh and minimum required scopes. Retire stored reusable app passwords after migration and provide a re-authorisation flow. |
| 🟠 P1 | PDS domain isolation | The production PDS is configured under `pds.swappulse.org` while the web app is `swappulse.org`. Current AT Protocol production guidance recommends a separate domain for the PDS rather than a subdomain of the app's registered domain because blobs, OAuth/session surfaces and future clients can create origin/security conflicts, and later PDS hostname changes require account migration. | Plan a dedicated PDS registered domain before wider adoption. Model the migration impact on existing PLC DIDs/accounts and do not casually rename an active PDS host. Keep app/OAuth client domains isolated from blob/PDS hosting. |
| 🟠 P1 | Provisioned-account self-sovereignty | SwapPulse provisioning creates a random PDS account password, uses it to mint an app password, then discards the main password while retaining the app credential server-side. No complete user-facing recovery/export/handoff flow proving independent control of a SwapPulse-provisioned PDS account was demonstrated. | Give users a standards-compatible recovery and migration path that does not depend on Base44 remaining available. Document who controls recovery keys/email, support secure password/account recovery and prove PDS-to-PDS account migration before calling the identity self-sovereign. |
| 🟠 P1 | Credential repair and DID continuity | `repairCredentialForUser` provisions a fresh PDS account when credentials for an existing account are unavailable, explicitly abandoning the old account/DID. That breaks the stable-DID property, followers, record URIs and trust continuity. | Recover/control the existing account or perform a real AT account migration using PLC rotation/recovery. Never silently replace a DID as a credential repair. Require explicit user consent for any identity replacement and migrate/reconcile content and graph. |
| 🟠 P1 | Legacy PDS credential residue | Three retired `PdsCredential` rows still exist in live data. At least one row's DID differs from the current identity observed for the same account, demonstrating stale identity material. The legacy schema also contains an app-password field even though User-level encrypted credentials are now canonical. | Revoke legacy credentials at the PDS, migrate only verified current identities, delete retired rows and remove the legacy schema after backup/rollback requirements expire. Add a uniqueness/current-DID reconciliation check. |
| 🟠 P1 | Repository export authenticity | `export-repo` calls its output an AT-compatible "CAR-like" archive but generates bespoke JSON containing Base44 entity rows and user metadata. It is not an AT repository CAR/MST export and does not carry the signed commit/MST structure required for true repo portability. | Use `com.atproto.sync.getRepo` for real CAR export and separately export private Base44-only data in a clearly labelled archive. Do not describe the JSON export as an AT repository export. |
| 🟠 P1 | Repository import / migration | `import-repo` replays JSON entries through `createRecord`, generating new record keys/URIs and not importing the original MST/commit or media blobs. Strong references can therefore break, and the operation is not a real PDS migration. | Use the standard migration flow: `getRepo` CAR, transfer blobs/private preferences as appropriate, provision the target account and import through `com.atproto.repo.importRepo`, preserving the DID and repository history. |
| 🟠 P1 | Import abuse controls | `import-repo` accepts arbitrary collection names/record bodies from a caller-provided archive, has no explicit archive/record count or byte limits and performs raw PDS writes without a request deadline. Although writes target the caller's repo, Base44 becomes an unbounded generic writer using stored credentials. | Strictly version/validate archive input, allowlist supported operations or move to standard CAR import, enforce total/record/blob size limits, time budgets and per-user rate limits, and use origin-bound PDS helpers. |
| 🟠 P1 | Federated search semantics | `federated-search`, actor resolution and author feeds depend on Bluesky's `public.api.bsky.app`. This provides Bluesky `app.bsky.*` visibility, not a generic index of the full ATmosphere or SwapPulse custom Lexicons. Calling it "across the AT Protocol network" overstates coverage. | Separate Bluesky compatibility search from SwapPulse custom-protocol search. Index custom collections independently, label the source/coverage in the UI and merge results deliberately rather than treating one AppView as the whole protocol. |
| 🟠 P1 | AT network request deadlines | Many AT-facing functions still use raw `fetch()` without hard deadlines, including handle/DID resolution, PLC/did:web requests, AppView search/profile/feed calls, provisioning, graph imports/backfills and some PDS repo operations. Slow upstreams can exhaust backend execution time. | Route AT HTTP through bounded shared clients with overall deadlines, redirect policy, response-size caps, typed retryability and backoff. Avoid unbounded parallel fan-out to AppView/PDS endpoints. |
| 🟠 P1 | Social graph deletion reconciliation | `import-atproto-graph` claims to catch follow/unfollow events, but reconciliation only creates missing follows/followers. It never deletes local Follow rows that no longer exist remotely, so unfollows can remain indefinitely. | Reconcile a complete remote snapshot or process relay delete operations. Tombstone local follows absent from a proven-complete remote listing, preserving safeguards when pagination is incomplete. |
| 🟠 P1 | Social graph truncation | Graph import/reconciliation caps each direction at 10 pages of 100 records and then stamps `graph_reconciled_at`. Accounts with more than 1,000 follows/followers can be silently incomplete, and existing-set lookups are also capped at 500 in places. | Persist graph cursors until exhaustion, never mark reconciliation complete after a capped partial scan, and use scalable indexed uniqueness rather than 500-record in-memory dedup sets. |
| 🟠 P1 | Legacy follow backfill provenance | `backfill-follows` loads Follow rows globally and invokes `atproto-bridge` as the admin without resolving each original owner's PDS session. Admin publication can therefore place historical follow records in the admin/shared repo instead of the user's repo. | Group backfill rows by immutable owner, resolve each owner's origin-bound PDS session and write the follow into that repo only. Validate repo DID equals the follow actor DID before publication. |
| 🟠 P1 | Federation verification false positive | `verify-federation` returns `ok` when either handle resolution succeeds **or** any PDS post exists. It checks only one migrated user and does not verify relay ingestion, AppView visibility of a fresh write, custom-record indexing, deletes or session health. | Define an end-to-end federation acceptance test that requires handle/DID/PDS agreement, fresh create/read/update/delete, relay/index visibility and cursor advancement. Test multiple PDS origins and fail if any required stage fails. |
| 🟠 P1 | Migration terminology / semantics | `migrate-to-swappulse` primarily imports data into Base44, changes a handle and synchronises content while retaining the same external PDS identity. It is not equivalent to moving an AT account/PDS, yet product/workflow wording can imply an AT migration. | Distinguish "connect/import into SwapPulse" from "move AT account/PDS". If true migration is offered, follow the standard account-migration procedure while preserving DID, repository and blobs. |
| 🟠 P1 | Handle-verification SSRF | `verifyHandleClaim` blocks obvious IP/hostname strings but does not use the shared DNS/IP `assertSafeHost()` before requesting `https://<domain>/.well-known/atproto-did`, and its verification requests have no timeout. A hostname resolving to private/link-local infrastructure remains a server-side request risk. | Use the shared SSRF resolver, revalidate DNS before connection, block redirects, enforce short deadlines and response-size limits, and return only the verification result rather than raw DNS records unless diagnostics are admin-only. |
| 🟠 P1 | Profile image SSRF through redirects | `profileSync.uploadImageBlob` validates the initial image hostname but then intentionally uses `redirect:'follow'` without validating the final redirect destination. A trusted CDN that redirects to another origin can defeat the original host allowlist. | Follow redirects manually and re-run SSRF/origin validation at every hop. Restrict final hosts or download through a trusted image transformation service with a fixed origin. |
| 🟠 P1 | Profile/blob resource limits | Profile image downloads, JPEG transform downloads and several PDS blob uploads read entire responses into memory without a hard byte cap and often without timeouts. The code also relies on the PDS to reject profile images above Lexicon constraints. | Stream with explicit byte/dimension/MIME limits before allocation/upload, enforce profile blob limits locally, add upload deadlines and reject content whose magic bytes do not match the accepted image type. |
| 🟠 P1 | Generic PDS blob validation | `atproto-bridge` remote `uploadBlob` and `pds-blob-upload` accept caller MIME information with limited validation. Remote blob fetches can lack hard size/deadline checks and base64 uploads do not verify image magic/dimensions. | Derive MIME from inspected bytes, use a strict image allowlist, cap decoded/downloaded bytes and dimensions, enforce timeouts and per-user upload quotas, and keep remote fetches on validated public origins only. |
| 🟠 P1 | Credential decrypt failure handling | `getUserIdentity` falls back to treating `pds_app_password` as plaintext whenever AES-GCM decryption fails, including when the encryption key changes or ciphertext is corrupt. That hides key-rotation/configuration faults and can repeatedly send ciphertext as a password. | Version encrypted credential formats. Fail closed on ciphertext authentication/decryption errors, distinguish explicitly migrated plaintext records and provide a controlled rotation/re-encryption path. |
| 🟠 P1 | Custom Lexicon validation | Inbound custom records are mapped directly from values without proving they validate against the authoritative Lexicon revision. The protocol guidance treats non-validating data as invalid rather than something consumers should repair/accept. | Resolve/pin authoritative schemas, validate every inbound custom record before trust or persistence, reject invalid required/type/format data and version schema evolution deliberately. |
| 🟠 P1 | Ingest cursor integrity | Live data contains duplicate `IngestCursor` rows for the same repo/collection. Cursor lookup uses the newest record, so concurrent runs/cold workers can diverge and duplicate or miss polling windows. | Enforce a unique stream/repo cursor key and atomic compare-and-set advancement. With a true relay consumer, store durable sequence plus per-repo revision rather than record-key-only high-water marks. |
| 🟠 P1 | Linked handle mutability | `User.did` and PDS secrets are backend-protected, but `bsky_handle` is not field-level protected in the current User schema. A client can potentially change the locally displayed linked handle independently of DID/PDS verification. | Make linked AT handle backend-managed. Derive it from the PDS session/resolver, keep user-chosen SwapPulse username separate and periodically revalidate handle-to-DID binding. |
| 🟠 P1 | Custom app-password validator | `validate-app-password` implements a SwapPulse-specific external app-password validation/scoping model even though legacy app-password creation is being retired and AT OAuth is now the primary client authorisation mechanism. This creates a parallel, non-standard auth surface that can drift from AT method names/scopes. | Deprecate the custom validator in favour of standards-based OAuth/resource-server authorisation. If retained temporarily, explicitly version it, restrict callers and audit operation-to-scope mappings against current Lexicons. |
| 🟡 P2 | Follow-feed completeness | `get-follow-feed` fetches AppView author feeds for at most 20 external followed DIDs and searches at most 10 followed hashtags per request. Users following more can receive an incomplete "strictly followed" feed without an explicit partial-result marker. | Page/fan out through a feed-generation/indexing service rather than N AppView calls, or return cursor/partial metadata and deterministic coverage. |
| 🟡 P2 | Sync dashboard accuracy | `get-sync-status` computes follow status with `deriveStatus(true, ...)`, which reports `complete` unless the step is explicitly failed even when `complete` is separately false. This can tell users their graph sync is complete when it is not. | Derive follow status from an actual completion/cursor/reconciliation state and display stale/partial status explicitly. |
| 🟡 P2 | AppView crawl assumption | `request-appview-crawl` and profile sync comments treat `app.bsky.actor.getProfile` as a way to "nudge" or prompt AppView indexing. No current protocol guarantee for that behaviour was found. | Remove the crawl-nudge claim. Rely on correct relay ingestion/discovery and measure actual index visibility; keep profile reads as reads only. |
| 🟡 P2 | Lexicon inventory drift | The federation workflow description still says it publishes "all 23 org.swappulse.* lexicons", while the in-code registry currently contains 35 Lexicons including six `site.standard.*`, and the JSON directory contains a different inventory. | Generate inventory/counts from one canonical source and fail CI when JSON files, registry, privacy policy or workflow documentation diverge. |
| 🟡 P2 | Silent AppView failures | Several AppView helpers catch network/non-2xx failures and return empty arrays/null, making upstream outage indistinguishable from "no actors/posts/profile". This masks federation faults in search and feeds. | Return typed source status (`ok`, `unavailable`, `rate_limited`, `partial`) separately from result arrays and surface degraded federation to the UI/monitoring. |
| 🟡 P2 | AT health error taxonomy | Account health currently collapses multiple failure modes into broad states such as `pds_unreachable`, even when the underlying cause may be credential/session, DID-service mismatch, DNS or actual network reachability. | Record separate safe machine codes for DID resolution, PDS discovery, network reachability, session auth, repo access, handle resolution and AppView indexing so remediation is actionable without leaking secrets. |
| 🟡 P2 | Exact-release execution | The Base44 command sandbox is detached from the app project, so the full AT test suite could not be executed against the exact audited source from this environment. Static Base44 inspection, live entity checks and external protocol research were available, but they are not a substitute for executable release gates. | Run protocol integration tests from an exact-commit CI checkout against a test PDS/relay/AppView setup and production smoke tests before changing the release status. |
| 🟡 P2 | Firehose terminology | Workflows, status entries and comments call the five-minute poller a "Firehose"/"Relay" even though it is not a `subscribeRepos` consumer. This makes operations and incident response overestimate federation coverage. | Rename the current component to PDS/AppView polling reconciliation until a real subscription consumer exists, then expose actual relay sequence/lag metrics. |
| 🟢 P3 | Retired credential comments | Several comments/functions still refer to `PdsCredential` as the active identity source even though credentials were consolidated onto User, while live legacy rows still remain. | Update terminology after the legacy records are safely revoked/deleted so maintainers do not accidentally reintroduce the retired path. |
| 🟢 P3 | Unused session helper shape | `resolveSessionForRequest` wraps the result of `getPdsSessionForUser` inside another `session` property, producing a different shape from its declared return contract. No active callers were found in this audit. | Fix or remove the helper before reuse and add a small type/runtime test for session-return shape. |
| 🟢 P3 | Naming and protocol copy | Code and user-facing diagnostics mix "BlueSky", "Bluesky", "firehose", "migration" and "federated network" terminology for materially different components. | Standardise terminology: AT Protocol/ATmosphere for protocol-wide behaviour, Bluesky AppView for Bluesky services, PDS for repository hosting, relay/Jetstream only for real event-stream ingestion. |

## Verified controls worth preserving

The audit also found strong AT-specific safeguards that should be kept while the architecture is corrected: per-user PDS sessions are origin/DID bound and SSRF hardened; PDS session tokens are held server-side; the current publication policy recognises that AT repositories are public and blocks sensitive record classes from new federation; new direct messages are local-only and end-to-end encrypted; `atproto-bridge` verifies ownership before delete/update for non-admin callers; post publication has bounded retries with exponential delay; outbound reconciliation uses per-user PDS sessions and safe pagination caps; custom handles are ultimately rechecked by the PDS updateHandle flow; and raw AT credentials are not intentionally exposed back to the browser after linking.

## Release decision

SwapPulse's AT Protocol layer is **NOT RELEASE READY**. The immediate blockers are live PDS/federation failure, the absence of a real relay/subscription ingestion architecture, stale inbound state hidden by a green status, consent bypass at canonical publication, the cross-PDS bearer-origin bug, forgeable handle/custom-record/trust provenance, client-controlled labeler/federation state, incomplete PDS account erasure and the incorrect assumption that publishing custom Lexicons makes them discoverable through Bluesky's AppView.

Recommended remediation order: **restore PDS/session health -> fix cross-PDS token destination -> lock trusted federation/handle/trust fields -> bind custom-record authorship to repo DID -> enforce consent at the canonical publisher -> replace polling with relay/Jetstream sync -> build custom-record indexing/search -> fix PDS account deletion/recovery -> migrate user auth to OAuth -> correct Lexicon/labeler/migration/portability architecture -> rerun full protocol integration and production smoke tests.**
