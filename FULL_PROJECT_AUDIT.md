# SwapPulse Full Project Audit

**Audit date:** 11 September 2026  
**Scope:** Entire current SwapPulse project: Base44 frontend and backend, entity/RLS model, authentication and account lifecycle, privacy/consent, AT Protocol/PDS federation, social/community features, trading/trust/reputation, payments, AI/agents, card scanning/verification, Cairo/Starknet identity and account contracts, staking, bridge/card lifecycle, transaction relay, RPC/node infrastructure, public APIs/status, release engineering, accessibility and documentation consistency.  
**Status:** **NOT RELEASE READY**. Multiple unresolved P0 findings remain.  

This is an application, protocol and architecture audit based on the current Base44 app state, live Base44 entity state where available, and the connected GitHub repository. It is not a substitute for an independent penetration test, independent Cairo/Starknet audit, provider-side infrastructure audit or legal review.

| Priority | Area | Finding | Required action |
| --- | --- | --- | --- |
| 🔴 P0 | Account deletion / erasure | `delete-account` does not delete `PdsCredential`, `DirectMessage`, `Conversation`, `DmPublicKey`, `CardVerificationSession`, `AgeVerificationSession` and other account-linked private records. Three retired `PdsCredential` rows still exist. If hard User deletion fails, the anonymisation fallback also leaves PDS credential fields behind. | Make deletion inventory-driven and exhaustive. Revoke/delete PDS app-password credentials, delete or lawfully anonymise all private/account-linked records, clear encrypted PDS fields on fallback, test deletion against every entity and verify no live credential remains. |
| 🔴 P0 | CCPA / federation opt-out | The **Do Not Sell or Share** preference is stored, and reconciliation/backfill checks it, but the live `atproto-bridge` and dedicated post-publishing paths do not. A user who enables the opt-out can still trigger new real-time PDS federation. | Put the consent check inside the canonical publication boundary (`atproto-bridge` / shared publisher), fail closed for create/update publication while opted out, and add integration tests proving posts, likes, follows and custom records cannot federate when the flag is enabled. |
| 🔴 P0 | Community labelers | A `CommunityLabeler` owner can update their own row, including `approval_status` and related trust metadata, so a labeler can potentially self-approve before issuing trusted labels. | Separate applicant-editable fields from approval state. Make approval, reviewer, review time, accuracy/issue counters and trust state backend/admin-only. |
| 🔴 P0 | Trust / Vouches | `Vouch` creation is client-authorised and accepts caller-supplied voucher/target DIDs. `getTrustProfile` counts local vouches, so forged identity fields can inflate trust even though duplicates are deduplicated. | Create/revoke vouches through an authenticated backend endpoint that derives the caller DID, validates the target, enforces one active vouch per pair and treats authoritative PDS records as provenance where applicable. |
| 🔴 P0 | Trade reputation | Reputation records accept caller-controlled rater/target identity and trade references. Those records feed portable reputation and can also influence Discord Verified/Trusted Trader role calculation. | Bind feedback to an authenticated participant in a completed trade, derive both parties and trade ID server-side, enforce one rating per participant/trade and make reputation records immutable except through trusted backend flows. |
| 🔴 P0 | Posts / moderation / engagement integrity | Post owners retain broad whole-row update authority over backend-managed moderation/federation fields and `likes`, `reposts` and `replies`. Interaction helpers create Like/Repost records and then attempt browser-side counter updates that can be rejected for other users' posts while owners can forge their own counters. | Split user-editable post content from system fields. Move moderation/federation state and engagement counters behind backend/atomic operations or compute counters from authoritative interaction records. |
| 🔴 P0 | Challenges | `ChallengeEntry` owners can modify score/status/verification/moderation fields. `submitChallengeEntry` service-role fetches supplied `CollectionEntry` IDs without requiring `created_by_id` ownership; the current DID check is optional because CollectionEntry DID may be absent. | Query contributed cards by authenticated owner ID, not caller-provided identity metadata. Compute counts/status/hashes server-side and make scoring, verification and moderation fields backend-only. |
| 🔴 P0 | Circle challenges | `submitChallengeEntry` does not enforce `challenge.scope === circle` membership or `circle_ref` at the backend boundary. A non-member can submit to a circle challenge if they know the challenge ID. | Require active circle membership server-side for submission, leaderboard/read access and reward calculation. Add negative tests for non-members and former members. |
| 🔴 P0 | Voice Spaces roles | `SpaceParticipant` lets a participant create/update their own row including privileged `host`, `co_host`, `mod` and `speaker` roles. A modified client can self-promote. | Create joins as listener only through a backend endpoint. Require host/mod authority for stage-role transitions and bind every participant DID/user ID server-side. |
| 🔴 P0 | WebRTC signalling | `SpaceSignal` is publicly readable and clients can supply signalling identity fields. SDP/ICE metadata is therefore too broadly exposed and sender identity can be spoofed. | Replace direct entity writes with an authenticated signalling endpoint. Derive sender identity, allow reads only to active space participants/intended recipients, expire signals aggressively and test malicious callers. |
| 🔴 P0 | Bridge event reconciliation | `chain-action-submit` can put a bridge transfer into `PENDING_RELAY` without recording the authoritative BridgeAdapter outbound nonce. Reconciliation skips transfers that lack that nonce. | Confirm the transaction receipt, parse the exact `BridgeOutInitiated` event, persist nonce/asset/recipient/amount idempotently and use event data as the source of truth before relay progression. |
| 🔴 P0 | Bridge destination safety | External bridge destinations are still validated mainly by coarse string length before being committed on-chain. A malformed destination can be committed after value is locked/burned. | Implement chain-specific canonical validators for EVM addresses, Solana addresses and every supported destination L2 before a draft is signed. Include wrong-chain/malformed/fuzz cases. |
| 🔴 P0 | Card bridge recovery | Card bridge-out burns the NFT. `BridgeAdapter.refund()` restores fungible tokens only, `CardNft` has no safe bridge-remint path, and the original mint attestation remains consumed. A failed card bridge therefore has no demonstrated lossless recovery path. | Redesign card bridging around lock/mint or an audited privileged recovery/remint mechanism that preserves identity/provenance. Add failed-relay/refund/remint/replay/unauthorised integration and fuzz tests before enabling card bridge value. |
| 🔴 P0 | Staking asset recovery | Cairo supports recovery actions, but Base44 verification gating applies to all staking actions, including `request_undelegate`, `withdraw` and `exit_validator`. Expired/revoked verification can therefore prevent a user recovering already-owned stake. | Gate only new/increasing-risk actions on current verification. Always permit safe undelegation, withdrawal and validator exit for the position owner, subject to contract timing rules. |
| 🔴 P0 | Chain identity reconciliation | The live ChainIdentity mirror still reports verification `ACTIVE` although its recorded V2 expiry was **3 September 2026 00:14:34 UTC**; `last_reconciled_at` is **2 September 2026** and no identity-reconciliation workflow is present. | Schedule `chain-identity-reconcile`, derive effective status from expiry at read time, alert on stale reconciliation and prove the mirror converges after expiry/revocation/network recovery. |
| 🔴 P0 | AT Protocol outbound federation | Live AT account-health records are fresh but currently report `pds_unreachable` / invalid credentials, and recent outbound delivery events are failing. Local posting may succeed while federation does not. | Restore PDS reachability/session credentials without weakening SSRF/session-origin controls, prove create/update/delete end to end for each linked identity and alert on consecutive publication/account-health failures. |
| 🔴 P0 | Profile search | Main Search calls `search-profiles` with `{ query }`, while the backend still accepts a different field/value contract; the UI swallows the failure. Local usernames therefore do not reliably search from the main search experience. | Replace both sides with one documented query/prefix search contract, return visible errors, test local and federated merge/dedupe and add contract tests. |
| 🔴 P0 | Custom handles | Handle proof verification still accepts a caller-supplied DID and the browser creates/updates trusted handle state after verification. Trusted handle ownership is therefore partly client-controlled. | Make DNS/HTTPS proof validation, DID binding, HandleClaim creation, user state and PDS handle update one authenticated backend transaction bound to `auth.me().did`. |
| 🔴 P0 | Production chain deployment provenance | A previous live audit observed `chain-explorer` returning `503 Invalid URL: 'undefined'` while the checked-in implementation now pins the canonical public RPC. The current environment could not independently re-prove the deployed live function. | Redeploy/verify the canonical function, smoke-test the production endpoint against the public RPC and record the deployed source/commit/version so repository and Base44 runtime provenance are demonstrably identical. |
| 🟠 P1 | Retired PDS credential store | `PdsCredential` is documented as retired, but three live rows remain and the schema stores `app_password` as plaintext admin-readable data, while the replacement User field is AES-GCM encrypted. | Verify every user is consolidated, delete the legacy rows, revoke superseded PDS app passwords where appropriate and remove/retire the schema after migration evidence is retained. |
| 🟠 P1 | Data portability export | `export-my-data` filters most entities only by `created_by_id`, so it misses received DMs/conversations and omits several account-linked entities such as DM keys, verification sessions, consent/age metadata and other records relevant to the user. | Build the export from an explicit data inventory with owner/participant/recipient relationships, include all user-linked personal data while excluding secrets that should never be exported, and test against seeded multi-party accounts. |
| 🟠 P1 | Direct-message storage boundary | The normal UI encrypts DMs, but `DirectMessage.create` remains client-authorised and the schema does not enforce an `e2ee:` ciphertext pattern. A modified client can persist plaintext. | Use a backend message-create endpoint or enforce a strict ciphertext envelope/schema at the data boundary; derive sender and conversation membership server-side. |
| 🟠 P1 | Follow identity / reply-policy integrity | `Follow` creation is client-authorised and accepts a caller-supplied follower DID. The followers-only reply check trusts Follow fields, so a forged graph record can distort social graph state and potentially bypass reply policy. | Create/delete follows through a backend endpoint that derives the authenticated follower DID, validates target DID and uniqueness, and use authoritative graph/PDS state for permission checks. |
| 🟠 P1 | Prediction voting | Sentiment votes are created client-side and the browser then tries to update the poll total. A voter generally cannot update another user's poll, leaving vote rows and tallies inconsistent. | Use one atomic backend vote endpoint with one-vote-per-user/poll enforcement and server-computed totals. |
| 🟠 P1 | Pull of the Week voting | Pull votes and nomination counters are separate client mutations and “one vote per week” is primarily UI-enforced. | Move vote creation and tallying to a backend transaction/endpoint with uniqueness and idempotency. |
| 🟠 P1 | Pack Parties | The prominent **Join Now** action still has no click handler. | Implement join/leave/membership state and permissions, or remove/disable the action until the lifecycle exists. |
| 🟠 P1 | TCGDex request timeout | The shared TCGDex client retries with backoff but has no hard fetch timeout/AbortController. A hung upstream request can leave interactive previews waiting indefinitely. | Add a bounded upstream timeout, cancellation/error classification and frontend retry state; do not retry indefinitely after the overall deadline. |
| 🟠 P1 | AI trending card IDs | `get-web-trends` sanitises model output but does not verify AI-generated `card_id` values against TCGDex before caching/displaying them. | Resolve/validate every generated ID against TCGDex, drop invalid IDs or resolve by card name, and cache only verified catalogue references. |
| 🟠 P1 | Public challenge UX/API | Challenge detail is publicly reachable, but `getLeaderboard` requires authentication. ## Verified controls and strengths

The audit also re-verified several important controls that should be preserved during remediation: strong-authentication credential changes are backend/step-up protected; sensitive User identity/security fields are server controlled; PDS session handling has HTTPS/SSRF/origin binding protections; new DM UI flows fail closed rather than falling back to plaintext; Stripe donation completion is server verified; card verification now uses private files and server-issued verification state; LLM agents are read-only/advisory at the privilege boundary; the Starknet relay reconstructs/allowlists signed calls instead of trusting arbitrary browser calldata; private chain authority keys stay server/host-side; raw Devnet RPC remains loopback-only behind a read-only public RPC allowlist; V2 identity verification has replay/expiry/revocation logic at the Cairo layer; and legacy custodial wallet/seed-phrase entities are quarantined rather than used by the active wallet architecture.

## Release decision

SwapPulse should **not** be treated as production-ready for public-value use while any P0 row above is unresolved. The immediate remediation order should be: account erasure and consent enforcement; trust/reputation/labeler and Post/Challenge/Voice-Space server authority; staking/bridge recovery and chain reconciliation; AT Protocol PDS recovery; profile/handle trust; then P1 privacy/API/release hardening. After remediation, rerun the same audit against the exact GitHub/Base44 deployment commit and require all build, type, Cairo, relay and production smoke gates to pass.

Future whole-project and feature audits must continue to use [AUDIT_STANDARD.md](AUDIT_STANDARD.md).
