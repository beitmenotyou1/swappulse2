## Executive summary

This full-system audit confirms that the earlier Circle Discovery score was not only a directory/discovery problem. The central architectural flaw is that the `Circle` document currently combines community metadata, curator identity, member profile cache, membership authority, public federation state and access-control data.

That design affects every Circle-dependent feature. A caller-creatable duplicate Circle can shadow a legitimate `at_uri`; public Circle visibility is treated as membership for circle-scoped trades; Starter Packs can bypass the private-Circle join rule; Circle-scoped challenges do not enforce membership; and private/member-visible Circles cannot reliably use scoped-trade/challenge features because those features require a public AT URI.

The full pass also found three Circle-specific federation release blockers beyond the earlier discovery audit. `import-repo` can write a valid non-public Circle archive record directly into a public PDS without applying `federationPolicy`; Circle publication inherits the project-wide outward-consent bypass; and account deletion removes local Circle rows without proving that public Circle records or the PDS account were removed.

Live audit-visible data currently contains **0 Circle rows, 0 CircleExit rows, 0 StarterPack rows, 0 circle-scoped TradeListings and 0 circle-scoped Challenges**. This is good remediation timing: the architecture can be corrected before a large private-community dataset needs migration.

The project-mandated Base44 web-agent README endpoint returned HTTP 403. The connected Base44 source API remained available and was used for the audit. The Base44 command sandbox mounted `/workspace` without the project's package manifest, so executable build/lint/typecheck and Circle security tests could not be run there. This is why the audit is marked complete with residual verification actions rather than fully release-verified.

No functional code, Circle records or user data were modified. Only this audit report was added.

## Verified strengths to preserve

- `federationPolicy.ts` only permits public Circles through normal PDS publication.
- `atproto-bridge` independently enforces that policy on normal create/update.
- Firehose ingest rejects remote non-public Circle records.
- The sitemap only emits public Circle detail URLs.
- Normal `circle-membership` derives the actor DID and blocks direct private joins.
- Ordinary members do not inherit curator update/delete rights.
- `get-visible-trades` fails closed when a scoped listing has no Circle reference.
- Outbound reconciliation can remove a previously bridged Circle that becomes non-public.
- `privacy-remediate-pds` provides a confirmed admin cleanup path for historical ineligible PDS copies.
- No live Circle/Exit/StarterPack/scoped-trade/scoped-challenge records were visible in this audit.

## Recommended remediation order

1. Introduce an immutable local Circle identity plus server-authoritative `CircleMembership` records with invited/requested/active/left/kicked/banned states and roles.
2. Use local immutable Circle IDs for private application authorisation; reserve AT URIs for public interoperability only.
3. Route direct join, invitations, Starter Pack joins, leave, kick, ban, account deletion and enforcement through one membership service.
4. Fix `canViewCircleContent` so public discoverability never substitutes for scoped-content membership.
5. Fix Circle Challenge membership enforcement and scoped listing creation authorisation.
6. Harden repository import and canonical federation consent before any PDS Circle write.
7. Make Circle creation/update/delete backend-authoritative, including federation metadata and dependent-resource cleanup.
8. Add private onboarding, member moderation, reporting, curator transfer and notifications.
9. Decide whether public membership is local-only or genuinely portable. If portable, use participant-authored/signed assertions instead of curator claims.
10. Add server-side full-corpus search, cursor pagination, accessibility/localisation fixes and exact-commit regression gates.

## AT Protocol reference

AT Protocol's Repository specification describes account repositories as public account-content storage whose contents are public and verifiable. A SwapPulse `private` or `members_visible` flag therefore cannot provide confidentiality after a Circle record is written to a PDS. A real AT repository export is a CAR/MST export rather than the current bespoke JSON replay format.

Reference: https://atproto.com/specs/repository

## Release decision

**Do not release the Circle subsystem as production-complete while CR-001 through CR-009 remain unresolved.**

The correct remediation is not another client-side visibility check. SwapPulse needs one immutable Circle identity, one backend-authoritative membership service and a strict split between local private community state and optional public AT Protocol projections. Once Trades, Challenges, Starter Packs, AI recommendations, account deletion and data export consume that common membership authority, the existing Circle UI and public-only federation policy can be retained and hardened rather than rebuilt from scratch.
