# SwapPulse Settings Full Feature Audit

**Audit date:** 12 September 2026  
**Scope:** Settings shell/navigation; account and identity settings; real and decorative security controls; TOTP/WebAuthn; privacy; consent and data rights; push/in-app notification policy; quiet hours; language/translation; accessibility/appearance; challenge settings; AT Protocol/PDS linking, export/import and sync; app passwords; invite links/email; Discord linking and role sync; age eligibility; chain identity entry points; account deletion; help/documentation consistency; mobile/accessibility; live audit-visible policy/delivery data; exact-release verification.  
**Overall score:** **11/100**  
**Risk:** **Critical / High Risk**  
**Release status:** **NOT RELEASE READY**  
**Status:** Source, schema, cross-audit and audit-visible data review complete. Exact-release build/lint/typecheck could not be executed because the Base44 command sandbox exposes an empty `/workspace` rather than the application checkout. The required Base44 web-agent README also returned HTTP 403, so this report does not claim that prerequisite was successfully read.

| Priority | Area | Finding | Required action |
| --- | --- | --- | --- |
| 🔴 P0 | Account security | **ST-001 - The Account tab contains a false Two-factor authentication control.** The switch only writes `SettingsConfig.security.mfaEnabled`; the authentication boundary does not consume that value. The real TOTP/WebAuthn state is held separately on protected User/WebAuthn records and managed by the Security tab. A user can therefore see “2FA enabled” without their account actually being protected by a second factor. | Remove the decorative Account toggle immediately, or make it a read-only reflection of the authoritative factor state. All enable/disable actions must use the real security-factor backend and recent step-up verification. |
| 🔴 P0 | Account security | **ST-002 - The Session timeout selector is false security.** `security.sessionTimeout` is stored in SettingsConfig but no server-side session/inactivity enforcement consumes it. Choosing 1 hour, 6 hours, 24 hours or 7 days changes UI data only. | Remove the control until a server-authoritative session policy exists, or implement true absolute/inactivity expiry and expose only effective values enforced by the authentication layer. |
| 🔴 P0 | Settings policy isolation | **ST-003 - SettingsConfig can be created for another collector's DID.** RLS binds the row only to `created_by_id`, while `did` is client-controlled. Backend services later use service-role reads by DID for notification and leaderboard policy, so an attacker can create a newer victim-DID config that changes effective settings. | Make SettingsConfig backend-only for mutation. Key it primarily to immutable Base44 user ID, derive the current DID server-side, enforce one authoritative row, reject mismatches, and migrate duplicates/stale-DID rows. |
| 🔴 P0 | Push recipient isolation | **ST-004 - PushToken can be created with another user's DID.** Direct entity creation is owner-RLS protected but the stored recipient DID is client-controlled. Central push delivery selects active tokens by recipient DID through the service role, allowing an attacker-owned browser subscription to be labelled with a victim DID and receive that victim's push payloads. | Make PushToken create/update/delete backend-only, derive both owner and DID from the authenticated session, make endpoints globally exclusive to one account, and regression-test victim-DID registration. |
| 🔴 P0 | Notification preference isolation | **ST-005 - NotificationPreference can be created for another user's DID.** The visible “Who can reach you” settings write directly to an entity whose creator is protected but whose `did` is caller-supplied. Backend delivery later looks up the newest preference by DID, allowing cross-user pause/filter poisoning. | Replace direct entity writes with a session-bound backend upsert, enforce one preference row per immutable user, derive DID server-side, and reject mismatched legacy rows. |
| 🔴 P0 | Consent integrity | **ST-006 - ConsentRecord ownership is not bound to its declared user_id/DID.** Direct entity creation allows an authenticated creator to choose arbitrary identity fields, while backend communication/federation decisions use service-role consent lookups. A forged record can therefore influence another account's consent state. | Make ConsentRecord backend-only through `update-consent-preferences`, derive user ID and DID from auth, enforce one canonical record per account, and migrate/reject duplicates and stale identities. |
| 🔴 P0 | Push delivery | **ST-007 - Web Push is still failing in the latest audit-visible delivery logs.** The current NotificationLog dataset contains 296 rows; the newest visible attempts through 10 September 2026 are failures. The preceding Notifications audit verified the deployed regression as `VAPID setup failed`. Settings currently exposes Enable/Test Push despite the central channel not being healthy. | Repair deployed VAPID configuration, add a startup/health check and admin real-device diagnostic, alert on sustained failure rate, and make successful real-device delivery a release gate. Settings should surface server registration/delivery health rather than only browser permission state. |
| 🔴 P0 | Notification authenticity | **ST-008 - Notification settings govern an inbox whose trusted social events can still be forged.** The existing notification producer accepts caller-supplied recipient/target fields for some interaction events without proving the underlying authoritative interaction exists. Settings can therefore filter or enable events that are not themselves trustworthy. | Derive notification recipient, actor and target from authoritative interaction/content records after the mutation succeeds. Remove free-form trusted-event creation from clients and add abuse/idempotency tests. |
| 🔴 P0 | Federation consent | **ST-009 - “Opt out of sale/sharing” does not reliably stop outbound federation.** Some reconciliation/backfill paths honour `do_not_sell`, but canonical publication/retry paths do not enforce the preference at the final outbound boundary. The Settings copy promises that posts, trades and profile will stop appearing on wider AT Protocol apps. | Put federation consent in the one canonical PDS publication boundary used by every create/update/retry/reconcile path. Fail closed before any outbound write and test opt-out, withdrawal, retry and historical queued work. |
| 🔴 P0 | Account deletion / PDS | **ST-010 - Delete account does not actually delete or deactivate a SwapPulse-provisioned PDS account/repository.** The current backend emits a tombstone-style label and deletes local User data instead of performing a standards-correct PDS account/repository lifecycle. Settings says federated data is being erased. | Define explicit self-sovereign choices for disconnect/export versus deletion of a SwapPulse-provisioned PDS. Revoke stored credentials, delete/deactivate controlled remote state where the user requested erasure, and independently verify the resulting public repository/account state. |
| 🔴 P0 | Account deletion / local privacy | **ST-011 - The canonical deletion path is not complete even locally.** `ProfileConfig` is omitted, so enhanced profile data such as location/contact/social fields can survive. Friendship cleanup also references the wrong participant field for one side of the relationship. The Danger Zone nevertheless says all associated data is permanently erased. | Maintain one authoritative erasure inventory generated from all user-linked entities, include ProfileConfig and both relationship directions, verify no orphans remain, return per-phase results, and do not report complete success on partial cleanup. |
| 🔴 P0 | Repository import trust boundary | **ST-012 - Settings repository import can inject trust-bearing local records through service-role mappers.** `import-repo` accepts caller-provided collection names/bodies, writes them to the caller PDS, then maps supported collections into Base44 as service role. Mappers accept caller-selected voucher/rater/participant/lifecycle fields for records such as vouches, trading feedback, challenges and trade chains. This bypasses the normal provenance rules those trust signals require. | Do not import trust-bearing operational state through generic record mappers. Strictly allowlist safe portable record classes, bind authorship to the authenticated repo DID, re-run authoritative validation/state machines, and quarantine legacy/unverified trust records instead of making them active. |
| 🔴 P0 | Repository import privacy | **ST-013 - Generic import can publish data classes that should not be blindly public and does not enforce normal privacy publication policy.** The importer accepts arbitrary collections, while mappers include private/sensitive-shaped records such as collection entries and communication records. It also does not consult the user's federation opt-out at this boundary. | Replace generic JSON replay with a standards-correct, policy-aware migration process. Apply a strict collection allowlist, schema/size validation, privacy classification, consent checks and server-derived authorship before any PDS or local write. Never restore private Base44-only data by publishing it publicly. |
| 🔴 P0 | Invite identity / friendship | **ST-014 - InviteCode can be directly created with an arbitrary inviter DID, and redemption trusts it to auto-follow/auto-friend that identity.** InviteCode create RLS allows a user-owned row while `inviter_did` is client-controlled. `redeem-invite`/`connect-invite` service-role read the code and create accepted relationship state using the cached inviter identity. | Make personal invite creation backend-only and session-derived, make codes unforgeably bound to the inviter user/DID, and route follow/friendship creation through the authoritative relationship state machine. Migrate or invalidate untrusted legacy personal codes. |
| 🔴 P0 | Language privacy | **ST-015 - First-visit language detection sends the visitor's IP-derived request to third-party geo services before an explicit consent choice.** This is inherited from the current language/i18n implementation and conflicts with the privacy-preserving role Settings is meant to provide. | Remove external IP geolocation from locale selection. Prefer URL/session choice, saved account preference and browser language. If geo inference is retained, disclose the providers/data flow and obtain the required consent before the request. |
| 🟠 P1 | Settings data model | **ST-016 - “One SettingsConfig per user” is already false in live audit-visible data.** Six SettingsConfig rows currently represent only four stored DIDs, with two identities having duplicate rows. Effective behaviour depends on newest-row selection. | Migrate to one immutable user-keyed row, define deterministic merge/migration rules, delete/quarantine duplicates and add uniqueness/idempotency tests. |
| 🟠 P1 | Settings save integrity | **ST-017 - Settings updates are optimistic with no rollback or visible sync failure.** `useSettings` mutates local state first and only logs persistence errors. The UI can therefore show a privacy/security preference as saved when the backend write failed. | Return explicit save state, rollback or mark unsynced on failure, retry safely, and show the user whether the effective server setting matches the screen. Privacy/security toggles should fail visibly. |
| 🟠 P1 | Settings loading | **ST-018 - Initial SettingsConfig loading uses a shallow top-level merge.** If an older config contains only part of a nested object, nested defaults can disappear rather than being recursively merged, producing undefined or legacy behaviour. | Use one versioned server normaliser/deep merge for every settings read, migrate old schema versions and test partial legacy documents. |
| 🟠 P1 | Identity migration | **ST-019 - Many settings/policy records are keyed to mutable DID values rather than immutable account identity.** Historical DID/link/migration changes can strand policy or cause a new DID to inherit defaults while stale rows remain active. | Key policy by immutable Base44 user ID and treat DID as a reconciled denormalised identity. Transactionally migrate SettingsConfig, PushToken, NotificationPreference and consent when DID state changes. |
| 🟠 P1 | Settings architecture | **ST-020 - There is no single authoritative settings service.** Browser components write SettingsConfig, NotificationPreference, User fields, ConsentRecord via backend, localStorage cookie state and other feature-specific records independently. | Introduce typed backend settings endpoints/projections with explicit namespaces and effective-state responses. Keep sensitive/privacy policy out of generic client entity CRUD. |
| 🟠 P1 | Privacy controls | **ST-021 - Collection visibility is decorative.** Full-source inspection finds `collectionVisibility` in Settings/defaults but not in the collection/publication rendering paths it claims to control. | Wire the preference into an explicit public-showcase model with server enforcement, or remove the control. | 🟠 P1 | Privacy controls | **ST-024 - “Hide monetary values” is decorative.** `valueHidden` is stored but collection/trade/profile value surfaces do not consume it consistently. | Apply one formatter/redaction policy across every value surface and API response where necessary, or remove the setting. |

## Executive assessment

Settings is one of SwapPulse's most security-sensitive surfaces because it tells users what protections, privacy choices and portability guarantees are effective. The current implementation has a dangerous mismatch between **what Settings says** and **what the backend actually enforces**. The two clearest examples are the decorative Account 2FA/session-timeout controls and the five Privacy controls that save successfully without changing the related data flows.

The deeper problem is identity binding. `SettingsConfig`, `PushToken`, `NotificationPreference`, `ConsentRecord` and `InviteCode` all contain identity/policy fields that can be supplied by a browser while backend services later trust them through service-role lookup. This converts apparently private “my settings” rows into cross-account policy or delivery primitives.

The AT Protocol section also needs to be treated as a security boundary rather than a convenience import/export page. The current JSON import can replay arbitrary collection data and then service-role map it into local entities. For trust-bearing collections, that can bypass the normal authoritative source-of-truth rules. For private data classes, generic publication can also violate the privacy boundary the rest of SwapPulse is trying to establish.

## Audit-visible production/state evidence

- Six SettingsConfig rows were visible, representing four stored DIDs; two identities already have duplicate SettingsConfig rows.
- Zero NotificationPreference rows were visible. This means ST-005 is a latent code-proven vulnerability rather than evidence of active exploitation.
- One ConsentRecord was visible.
- One active PushToken was visible.
- 296 NotificationLog rows were visible. The newest visible delivery attempts through 10 September 2026 are failures; the preceding notification audit identified the active deployment error as VAPID setup failure.
- The sparse settings/consent dataset is not evidence that the underlying trust boundaries are safe. It does make migration to a canonical one-row-per-user model easier.

## Verified strengths worth preserving

- `User.did` is backend-managed rather than ordinary client-writable identity state.
- The real Security tab uses dedicated backend functions instead of trusting the decorative SettingsConfig MFA flag.
- Security factor management requires a short-lived security-management step-up token for enabling/disabling TOTP and managing WebAuthn credentials.
- WebAuthn registration uses server challenges, user verification and backend-managed credentials; the browser does not receive stored private keys.
- TOTP/WebAuthn entity fields are protected from ordinary client read/write through stronger RLS/service-role patterns than generic SettingsConfig.
- App-password creation is visibly retired and surviving credentials can be revoked.
- Push registration's intended backend path derives the correct DID from the authenticated User; the vulnerability is the parallel direct entity write path, not the normal registration function.
- Age eligibility deliberately stores age bands/verification status rather than names, DOB or identity documents, and value-bearing eligibility requires stronger private verification than self-declaration.
- Settings does not place names, emails, DOB, identity documents or privileged blockchain keys on-chain.
- The Discord OAuth link flow uses signed expiring state plus a server-stored one-time challenge, exchanges the authorisation code server-side and does not persist Discord OAuth tokens.
- Discord link collision checks prevent the same verified Discord account from being linked to two different SwapPulse users.
- The Settings Danger Zone uses a multi-step accessible Dialog plus type-to-confirm rather than a single accidental-click action.
- Accessibility settings for reduced motion, theme and font size do produce real UI effects.
- Reduced-motion CSS is broad and strong rather than merely cosmetic.
- Repository migration is explicitly labelled temporarily unavailable rather than pretending the retired transfer flow is safe.
- `update-consent-preferences` and `register-push-token` demonstrate the correct pattern: session-derived identity and service-role writes. The remaining direct entity paths should converge on this model.

## Target Settings architecture

1. **One immutable owner key.** Every settings/policy record is keyed primarily by Base44 user ID; DID is resolved/derived server-side and reconciled when identity changes.
2. **One typed settings service.** Browser code never directly creates security/privacy policy entities. `get-settings` returns effective values plus source/revision/health; `update-settings` validates a typed namespace and performs an idempotent upsert.
3. **Authoritative security status.** TOTP/WebAuthn/session policy is computed by the authentication backend. There are no writable shadow flags such as `mfaEnabled`.
4. **Server-enforced privacy.** Collection/trade/location/value/presence controls are checked at the query/publication boundary, not merely at rendering time.
5. **Central notification policy.** Consent, pause, event type, channel, relationship filters, quiet hours, token health, rate limits and logging are applied exactly once before inbox/push delivery.
6. **Consent as fail-closed policy.** One canonical ConsentRecord per immutable user, with explicit unknown/yes/no state, versioned policy text and a deterministic federation/communications boundary.
7. **Separate portability products.** A real AT repository export/migration is distinct from a Base44 personal-data export. Private local data is never made public merely to make it “portable”.
8. **Safe import.** No generic service-role materialisation of trust records from user JSON. Supported portable records are allowlisted, authored by the authenticated repo DID and pass normal authoritative validation.
9. **One security step-up service.** MFA changes, app-password revocation/reveal, account deletion and other high-impact identity changes use the same action-bound recent-auth token model.
10. **Capability-aware UI.** Every control declares whether it is active, unavailable, legacy/revoke-only or planned. A saved toggle is never presented as protection unless its enforcement path is live and tested.
11. **Settings versioning/migration.** Every config has schema version, immutable owner, revision, last effective update and deterministic migration from old rows.
12. **Privacy-safe diagnostics.** Users can see save/sync health, notification registration health, PDS sync state and high-impact security activity without seeing secret material.

- A PushSubscription endpoint cannot remain active for two accounts after account switching.

## Recommended remediation order

1. Remove/disable the false Account 2FA and session-timeout controls.
2. Lock SettingsConfig, PushToken, NotificationPreference, ConsentRecord and InviteCode behind session-derived backend endpoints; migrate duplicates.
3. Repair Web Push/VAPID and centralise every notification path behind one consent/policy dispatcher.
4. Make every exposed Privacy setting server-authoritative; add the missing presence control.
5. Put federation consent at the final PDS publication boundary.
6. Fix account deletion/export truthfulness, including ProfileConfig, relationships, credentials and PDS lifecycle.
7. Disable generic repository import until trust/privacy allowlisting and standards-correct migration are designed.
8. Fix invite identity handling, false email-send UX, logging/quotas and owner revocation.
9. Encrypt TOTP secrets, hash all temporary codes and unify high-impact actions behind recent security step-up.
10. Reconcile language controls/geo privacy/localisation with the Language audit and remove decorative translation filters.
11. Rebuild Settings around one typed versioned effective-settings service and capability-state UI.
12. Finish Settings accessibility/localisation/help accuracy, then run exact-release build/lint/typecheck and full integration/E2E security regression.

## Release decision

**SwapPulse Settings is not release ready.** Settings currently tells users they have controls that are either not enforced, not authoritative, or can be influenced through identity-unbound records. Because Settings is where users make security, privacy, consent and data-rights decisions, those mismatches are release-blocking even when the surrounding feature works elsewhere.

The immediate goal should not be adding more switches. It should be making every existing switch correspond to one backend-enforced, identity-bound source of truth. Once that foundation is in place, the real strengths already present in the Security, age-eligibility and Discord-linking flows can become the model for the rest of Settings rather than isolated hardened islands.
