# SwapPulse Site-Wide Security & Usability Audit

**Audit completed:** 29 August 2026  
**Scope:** SwapPulse Base44 application, frontend, backend functions, entity/RLS configuration, authentication and account-security flows, payments, direct messages, AT Protocol/PDS integration, public-link handling, uploads, admin/moderation surfaces, blockchain configuration handoff, accessibility and production dependency/static checks.  
**Status:** Complete with residual maintenance actions.

This is an application-level engineering audit, not a substitute for an independent penetration test, infrastructure audit or formal smart-contract audit before real-value production use.

| Priority | Area | Finding | Required action |
| --- | --- | --- | --- |
| 🔴 P0 | WebAuthn credential control | Browser-controlled WebAuthn credential lifecycle would allow a compromised authenticated session to alter strong authentication state. | **Completed:** WebAuthn create/update/delete is backend-only, ownership is user-bound and security-factor changes require fresh step-up verification. |
| 🔴 P0 | TOTP / step-up security | TOTP enable/disable and step-up verification needed stronger server authority and secret handling. | **Completed:** TOTP state is backend-controlled, secrets are backend/admin-readable only, email codes are salted SHA-256 digests and step-up capabilities are signed, user-bound and short-lived. |
| 🔴 P0 | Passwordless recovery | Recovery/setup paths risked becoming a compatibility bypass around configured second factors or account binding. | **Completed:** recovery/setup is bound to the verified account, configured second factors are respected and `store-login-key` no longer trusts caller-selected email before verification. |
| 🔴 P0 | User identity integrity | Client-editable DID/signing/security fields could allow identity impersonation or reuse of sensitive compatibility keys. | **Completed:** `User.did`, legacy signing key, push subscription material, encrypted PDS credentials, PDS URLs and moderation account-state fields are backend-managed. |
| 🔴 P0 | PDS SSRF/session binding | Per-user PDS URLs are untrusted input and authenticated bearer tokens could be sent to the wrong origin without strict validation. | **Completed:** PDS origins require public HTTPS, SSRF/private/reserved targets are rejected, redirects are blocked and sessions are bound to both DID and validated PDS origin. |
| 🔴 P0 | Direct-message confidentiality | New DMs could not safely tolerate plaintext fallback or public federation of message content. | **Completed:** new DMs are local-only, E2EE is required, sender identity is auth-bound and plaintext fallback/public PDS bridging is disabled. |
| 🔴 P0 | Donation/payment confirmation | Browser navigation to a success route could be mistaken for confirmed payment. | **Completed:** Stripe Checkout Session is retrieved server-side and amount, currency, session ID and payment state are verified before marking donation success. |
| 🔴 P0 | Notification integrity | Browser users could not be allowed to forge/mutate system notifications or moderation outcomes. | **Completed:** notification creation/mutation and content-report moderation fields are backend/staff controlled; read-state mutation uses authenticated backend operations. |
| 🔴 P0 | Redirect/XSS boundary | Untrusted URLs and deep links could otherwise permit dangerous schemes, cross-origin redirects or unsafe rendered content. | **Completed:** external navigation is restricted to HTTP(S), unsafe schemes/protocol-relative/cross-origin routes are rejected, raw user HTML is not rendered and `_blank` links use `noopener noreferrer`. |
| 🔴 P0 | Upload abuse | Multiple upload surfaces lacked a single consistent type/size/row-count enforcement model. | **Completed:** profile/post/story/report/podcast/import uploads now enforce appropriate MIME, size, quantity and row limits before expensive processing. |
| 🔴 P0 | Web3 secret boundary | Privileged Starknet/admin/verifier trust must never live in browser code or unverified network configuration. | **Completed:** Base44 stores public chain coordinates only, network activation independently verifies chain/registry/account-class pins, and private/write RPC is separated from public/read-only RPC. |
| 🟠 P1 | Direct-message report privacy | Moderation tooling must not recreate a hidden general-purpose plaintext decryption path for private conversations. | **Completed:** routine plaintext escrow/decryption is disabled; reports use explicit evidence and historical privacy-remediation tooling handles legacy bridged copies. |
| 🟠 P1 | Live-stream/public URL safety | Stored media URLs and user-generated external links can become script/navigation vectors if not validated at both write and render boundaries. | **Completed:** supported URL schemes are validated both when stored and when rendered. |
| 🟠 P1 | Accessibility | Many icon-only buttons, visual labels and placeholder-only controls did not expose strong accessible names/relationships. | **Completed:** 59 icon-only buttons, 57 label/control relationships, 74 literal-placeholder controls and 32 translated-placeholder controls were corrected, with additional specialised controls named explicitly. |
| 🟠 P1 | Content Security Policy | HTML meta CSP is useful but cannot provide the complete protection of production HTTP response headers such as `frame-ancestors` and HSTS. | Configure production/edge response headers for `Strict-Transport-Security`, full `Content-Security-Policy`, `frame-ancestors`, `Permissions-Policy`, `X-Content-Type-Options: nosniff` and appropriate sensitive-response cache controls. |
| 🟠 P1 | React Router dependency | Production dependency audit reports moderate advisories in React Router 6.x, while the published remediation requires a major React Router 7 migration. | Plan and test a React Router 7 migration as scheduled maintenance; keep attacker-controlled routes/deep links sanitised in the meantime. |
| 🟠 P1 | Legacy simulated AT signing | Legacy simulated client-facing AT signing remains architectural debt even though the key is backend-protected. | Replace it with proper PDS-native/session signing semantics; never reuse the compatibility mechanism for Starknet keys. |
| 🟠 P1 | Passwordless compatibility bridge | Current passwordless login still interoperates with Base44's email/password bridge. | Migrate to a native passwordless/session mechanism when the platform supports it without weakening current step-up protections. |
| 🟠 P1 | Platform/infrastructure assurance | Repository review cannot independently prove Base44 storage encryption/IAM, CDN TLS/HSTS/WAF/rate limits, mail-provider security or Stripe dashboard configuration. | Verify those controls operationally before high-risk/public-value launch and retain evidence outside the code audit. |
| 🟠 P1 | Smart-contract assurance | Application review and Devnet tests do not constitute a formal Cairo/Starknet smart-contract audit. | Obtain an independent Cairo/Starknet review before real economic value, production recovery governance, native passkey cryptography or sovereign/L3 deployment. |
| 🟡 P2 | Build gate | Production Vite build completed successfully at the end of the audit. | **Completed:** build gate passed. |
| 🟡 P2 | ESLint gate | Static linting needed to be clean before audit closure. | **Completed:** ESLint passed. |
| 🟡 P2 | Backend parse/bundle gate | All backend entrypoints needed parse/bundle validation. | **Completed:** 212 / 212 backend entrypoints passed. |
| 🟡 P2 | Entity RLS coverage | Ordinary application entities without explicit RLS would create accidental data exposure. | **Completed:** zero ordinary entities were missing explicit RLS and zero entities had open `create: {}` rules. The Base44-managed `User` model remains the platform exception with sensitive custom fields restricted. |
| 🟡 P2 | Secret scanning | Tracked source needed checks for literal Stripe/AWS/private-key signatures and committed environment files. | **Completed:** no tracked literal secret signatures and no tracked `.env` files were found. |
| 🟡 P2 | Dependency audit | Production packages required vulnerability review before audit closure. | **Completed with residual action:** zero critical/high vulnerabilities remained; two moderate React Router advisories are tracked for the planned major migration. |
| 🟡 P2 | Accessibility regression scan | Final JSX icon/link/image and form scans needed to confirm remediation did not leave obvious accessibility regressions. | **Completed:** icon/link/image scan reported zero findings; only shared shadcn `Input`/`Textarea` primitives remain for callers to label. |
| 🟢 P3 | Audit report consistency | The original audit mixed findings, remediations and residual risks across long narrative sections. | **Completed:** reformatted into the project-wide Priority / Area / Finding / Required action standard. |

## Release decision

Within the application/code/schema scope available to this audit, the identified high-impact application findings were remediated and no unresolved critical/high dependency finding remained at audit close. This does **not** mean the application is perfectly secure or independently penetration-tested.

Future security and feature audits must use [AUDIT_STANDARD.md](AUDIT_STANDARD.md).
