# SwapPulse LLM / Agent Audit

**Audit date:** 11 September 2026  
**Scope:** Base44 agent definitions, agent tool permissions, prompt-injection boundaries, model-output rendering, direct `InvokeLLM` and image-generation calls, multimodal card scanning/attestation, moderation assistance, AgentFeedback and learning loops, RAG/knowledge refresh, AI translations, market/sentiment AI, scheduled AI workflows, memory/privacy, data rights, model provenance, cost controls, UI claims and release verification.  
**Status:** **NOT LLM/AGENT-RELEASE READY**. Unresolved P0 findings remain.

| Priority | Area | Finding | Required action |
| --- | --- | --- | --- |
| 🔴 P0 | Card verification authority | Collectors previously could create/update their own `CardVerificationSession` trust state while downstream flows consumed it as authority. | **Completed:** session creation/update is backend/admin controlled, card identity is derived from the caller-owned CollectionEntry, private file references are used and browser-supplied trust state is no longer authoritative. |
| 🔴 P0 | AI moderation authority | Earlier AI moderation paths could lead from model output into user-impacting moderation state. | **Completed:** `ai-moderation` is advisory-only, the moderation agent has read-only tools, `autonomous-moderation` is a disabled tombstone and no current LLM response directly hides content, adds strikes or restricts accounts. |
| 🔴 P0 | Toxic-label autonomous enforcement | The toxic-label workflow previously represented an AI-triggered path toward account enforcement. | **Completed:** `Toxic Label Handling` is hard-disabled with `${ false }`; `handle-toxic-label` is staff-only and records advisory review without strikes, restrictions, deletion or other punitive action. |
| 🔴 P0 | Agent excessive agency | Specialist agents previously presented a risk of model-directed application mutation. | **Completed:** all eight current agent definitions are non-anonymous and expose read-only entity tools only. No agent config grants create, update or delete operations. |
| 🔴 P0 | Learning-loop poisoning / automatic activation | User feedback previously risked becoming behavioural guidance without a strong quarantine boundary. | **Completed:** feedback is sanitised, suspicious content is safety-flagged, generated insights are inactive and pending review, flagged insights cannot be approved, and no insight becomes active automatically. |
| 🔴 P0 | Indirect prompt injection + Markdown exfiltration | Several specialist agents (`collection_advisor`, `sentiment_conversationalist`, `achievement_goal_tracker`, `networking_concierge`, and `market_watch`) do not contain the explicit untrusted-record prompt boundary used by Collector Copilot/Trade Assistant. Some combine attacker-controlled/public records with the current user's private records. Their UIs render assistant output through unrestricted `ReactMarkdown`, which can render remote images and ordinary external links. This creates a credible indirect-prompt-injection chain where hostile record text influences the model to emit an attacker URL and the browser automatically requests it, potentially carrying model-visible private data in the URL. | Add the same explicit indirect-prompt-injection policy to every agent; field-minimise mixed-trust tool results; configure Markdown to disallow remote images and raw external media; route all generated links through the safe external-link confirmation layer; add adversarial tests proving public record text cannot cause private-data disclosure or remote fetches. |
| 🔴 P0 | AI possession trust oracle | `create-card-attestation` still lets a single vision-model result directly upgrade a session to Level 2 and feed the possession-verified trust signal. Thresholds, physical-card checks and screen/manipulation flags reduce risk, but there is no independent liveness/challenge proof or second verifier. A model false-positive therefore becomes a trust false-positive rather than merely a bad suggestion. | Treat Level 2 as a probabilistic visual signal unless stronger evidence exists. Add a challenge-response/liveness step, independent second verification for high-trust use, and human review or stronger proof before any high-value reputation/asset consequence. Record exactly what the model did and did not prove. |
| 🔴 P0 | AI data lifecycle / erasure | Agent conversations can contain private collection, wishlist, trade and moderation context, but the project contains no explicit conversation export/delete flow and account deletion does not demonstrate a cascade over Base44-managed agent conversations. `AgentFeedback` is service-created with `submitted_by_user_id`, while account cleanup does not explicitly delete by that provenance field. | Before release, prove and document the platform retention/cascade behaviour for every agent conversation/message. Add user-visible conversation deletion, include AI conversation/feedback data in export where appropriate, and make account erasure explicitly delete/anonymise AgentFeedback by `submitted_by_user_id` plus all project-controlled AI artefacts. |
| 🟠 P1 | Moderation-agent server-side role boundary | The moderation agent is described and presented as staff-only, but its agent definition only sets `allow_anonymous_access: false`. The React page checks for admin/moderator, but a normal authenticated user can potentially call the Base44 agent API directly. Entity RLS limits the records tools can return, but staff-only AI access and model-credit use are not enforced at the agent boundary itself. | Add a platform/server-side admin-or-moderator allowlist for `moderation_agent`, or proxy conversation creation/messages through a role-checked backend function. Keep entity RLS as a second boundary. |
| 🟠 P1 | Specialist indirect-prompt-injection consistency | Only Collector Copilot, Trade Assistant and Moderation Agent have strong explicit instructions that tool/entity content is untrusted data. Other specialist agents read user-generated records without an equivalent boundary. | Standardise a shared untrusted-data instruction block across every agent and regression-test malicious Post, TradeListing, Circle, Meetup, vote and insight content. |
| 🟠 P1 | Sentiment vote privacy | `sentiment_conversationalist` is explicitly instructed to inspect “who voted what”. `SentimentVote` is broadly readable, but individual voter identity is not needed to compute market/community sentiment. | Give the agent aggregate vote counts only. Remove voter identity from the tool scope/prompt and expose a server-generated aggregate read model for sentiment analysis. |
| 🟠 P1 | Networking presence/social-graph scope | `networking_concierge` can read broad Presence, Follow and SpaceParticipant data across the community and is told to use participation/presence for recommendations. The prompt says to filter “where possible” rather than enforcing subject scope. | Replace broad entity reads with purpose-built recommendation endpoints that return only the minimum authorised candidate fields and respect presence/privacy choices. |
| 🟠 P1 | Achievement-agent social-data scope | `achievement_goal_tracker` reads the user's private collection/achievement data alongside community Vouch, TradingFeedback, VoiceSpace and Meetup records. Filtering is instruction-based rather than tool-enforced. | Use purpose-built, user-scoped progress endpoints and aggregate community evidence instead of granting the model broad raw entity access. |
| 🟠 P1 | Private-data field minimisation | Agent entity tools return whole records. For example, CollectionEntry includes purchase price and free-text notes even when a question may need only card IDs/counts, and Wishlist includes the collector's maximum willingness to pay. Those fields can be sent to the model provider whenever the agent chooses to read the entity. | Introduce field-projected/purpose-built agent tools and send only fields required for the current task. Keep private notes, budgets and acquisition details out of model context unless the user explicitly asks for them. |
| 🟠 P1 | Agent memory policy not pinned | Only `moderation_agent` explicitly defines `memory_config` and disables cross-conversation memory. The other seven agents do not pin memory behaviour in source, so retention/context behaviour depends on platform defaults rather than an audited project decision. | Explicitly configure memory for every agent. Default to conversation-only/no cross-conversation context unless a documented feature requires memory and the user has a clear control over it. |
| 🟠 P1 | AgentFeedback erasure provenance | `submit-agent-feedback` correctly records the authenticated user in `submitted_by_user_id`, but `delete-account` does not explicitly include that field in AgentFeedback cleanup. Service-created records therefore are not guaranteed to match ordinary `created_by_id` cleanup. | Add `submitted_by_user_id` to erasure matching and test deletion using real service-created feedback rows. |
| 🟠 P1 | AgentFeedback data portability | `export-my-data` does not include AgentFeedback, even though feedback can contain copies of assistant messages, user corrections and comments linked to the user's account. | Add AgentFeedback and other appropriate AI-interaction records to the personal-data inventory/export, with internal safety metadata excluded where legally appropriate. |
| 🟠 P1 | Per-conversation deletion controls | All eight agent pages can list/create/open conversations, but no frontend or project-level delete-conversation action was found. | Add delete/clear controls with defined retention semantics and make deletion behaviour visible to the user. |
| 🟠 P1 | Agent model-credit abuse | Agent chats are authenticated, but no project-level per-user message/conversation quota, token budget or abuse throttle is evident around `base44.agents.addMessage/createConversation`. A compromised or malicious account can potentially consume model credits repeatedly. | Add per-user/per-agent rate and spend budgets, concurrency limits and abuse monitoring. Prefer hard server/platform quotas rather than UI throttles. |
| 🟠 P1 | LLM usage observability | No central LLM usage/cost ledger or token/model audit trail was found for the 12 direct `InvokeLLM` sites or agent conversations. | Record provider/model, operation, caller class, latency, success/failure, approximate token/cost usage and safety outcome without logging unnecessary prompt/private content. Alert on unusual spend. |
| 🟠 P1 | Weekly sentiment consent | `weeklySentimentReport` is admin-only and its scheduled workflow is disabled, but manual invocation emails every active non-restricted user without checking marketing/digest consent. | Filter recipients by explicit report/email consent and unsubscribe state even for manual admin runs. | 🟠 P1 | Weekly AI market recommendations | `weeklySentimentReport` asks the LLM for “recommendations for the coming week” and distributes them in a mass market email. This is stronger than the application's “advisory only” market framing and can reach minors/users who did not request market advice. | Remove prescriptive recommendations from broadcasts. | 🟠 P1 | Market Watch advice boundary | `market_watch` explicitly labels rising cards “good time to sell”, falling cards “good time to buy”, and tells the model to “suggest when to act”. That conflicts with the stronger non-financial-advice boundary used elsewhere. | Reword to descriptive price movement/alerts only. Do not direct users to buy/sell or time the market; present price data, uncertainty and sources and let the collector decide. |
| 🟠 P1 | Collection Advisor advice boundary | `collection_advisor` is told to decide whether “holding or trading makes sense”, flag cards “worth holding” and suggest budget allocation for future acquisitions. | Reframe as collection-management options rather than financial/value-timing advice, especially for younger collectors. Avoid prescriptive budget allocation and future-value implications. |
| 🟠 P1 | Market Watch capability overclaim | The Market Watch page says the agent “monitors listings”, can “get alerted when new ones appear” and can “trigger alerts”, but the agent tool config is read-only and has no alert-creation tool. | Change the UI/help text to the real capability or add a separately authorised, user-confirmed non-agent alert feature. | 🟠 P1 | Model version pinning | Most high-impact `InvokeLLM` calls do not specify a provider/model version. Card possession, moderation and scanner behaviour can therefore change when platform defaults change without a SwapPulse code deployment. `MODEL_VERSION = 'llm-vision-v2'` is an application label, not evidence of the actual provider model. | Pin supported model identifiers where the platform allows it, and store the actual provider/model version used for every trust-sensitive result. | 🟠 P1 | Prompt/schema provenance | Card verification, moderation and learning artefacts generally do not record an immutable prompt version/schema version alongside the model result. | 🟠 P1 | AI attestation identity binding | `create-card-attestation` explicitly states its result is off-chain and not cryptographically bound to the collector's smart account, yet downstream Web3/card UX can present possession attestations next to on-chain identity. | Bind high-trust attestations to a signed challenge from the smart account before representing them as identity-linked evidence, or clearly keep them as Base44 account assertions. |

## Verified LLM / Agent strengths

The fresh audit re-verified several controls that should be preserved:

- All eight Base44 agents are authenticated-only and currently have read-only entity tools.
- Collector Copilot, Trade Assistant and Moderation Agent contain explicit untrusted-data / prompt-injection boundaries.
- Moderation Agent explicitly disables memory and cross-conversation context.
- `ai-moderation` fetches authoritative stored content instead of caller-supplied text, wraps it as untrusted content, uses a structured schema and is advisory-only.
- Autonomous moderation/escrow is disabled, and all high-risk scheduled AI workflows are security-held rather than weakening authentication.
- Card scanner and possession-check functions use private file references with short-lived signed URLs and explicit multimodal prompt-injection instructions.
- Scanner results require user review before collection mutation; the scanner does not automatically add cards.
- AgentFeedback submission has authentication, an agent allowlist, input sanitisation and a 60/hour rate limit.
- Learning insights are quarantined, inactive and require human approval; live AgentFeedback and AgentInsight tables were empty during this audit.
- RAG refresh uses fixed GitHub paths, immutable commit SHA, content hashing and admin review before publication.
- Web trends use a fixed prompt, internet prompt-injection rules, sanitised output and a six-hour cache/backoff.
- Specialist UIs no longer display raw tool inputs/results.

## LLM / Agent release decision

SwapPulse should **not** be considered LLM/Agent-release ready while the unresolved P0 findings remain.

The recommended remediation order is:

**block Markdown remote-image/external-link exfiltration and standardise indirect-prompt-injection defences → redefine/strengthen Level 2 possession verification → prove and implement AI conversation/feedback erasure/export → add server-side staff gating for the moderation agent → minimise individual vote/presence/social/private collection data exposed to agents → pin memory/model/prompt provenance → add agent cost controls and observability → correct market-advice/capability claims → harden multimodal byte/type validation → fix policy/help drift → add adversarial AI regression/evaluation suites.**

After remediation, rerun prompt-injection tests with malicious Post/TradeListing/Circle/Meetup/AgentInsight content, verify no generated Markdown can cause unauthorised remote requests, test cross-account/role isolation, test false-positive card possession scenarios, test conversation/account erasure and export, exercise every direct `InvokeLLM` call under malformed outputs, and record the exact provider/model/prompt versions used for the release.
