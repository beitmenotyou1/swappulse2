## Live audit evidence

The audit queried current Base44-visible data on 12 September 2026:

- **446 public Post rows** matched `visibility_scope=public` and `moderation_status=escalated`. The returned rows were overwhelmingly labelled `scam`, AI-generated, high confidence and `recommended_action: hide`.
- **0 AccountStatus rows**, so the account-enforcement privilege/state-machine vulnerabilities are currently latent in the audit-visible data rather than evidence of an active enforcement incident.
- **0 ContentReport rows** and **0 TradeDispute rows**.
- **0 ModerationDecisionLog rows**, supporting the finding that the visible AI Review Queue has no demonstrated current producer.
- **0 BotAttempt rows** and **0 BlockedRegistration rows**.
- The ModerationLog query returned the maximum requested **500 rows**, heavily dominated by historical `auto-resolve` / `auto-escalate` entries from the prior autonomous design. This proves at least 500 audit events exist, not that the total is exactly 500.
- `ModerationLabel` still has records beyond offset **2,000**; an item was returned at `skip=2000`.

Sparse enforcement/report/dispute datasets reduce immediate migration complexity, but they do not make the code-proven trust-boundary defects safe.

## Verified strengths worth preserving

- `ai-moderation` is now **advisory-only**: it loads authoritative content server-side, treats content as untrusted data, uses structured output and does not directly mutate enforcement state.
- Automatic AI moderation workflows for posts/listings/messages are explicitly on **SECURITY HOLD** rather than running through an unauthenticated internal-call assumption.
- Toxic-label follow-up is also held so an LLM-triggered workflow cannot automatically add strikes/restrictions.
- The conversational moderation agent's configured tools are read-only and its instructions explicitly treat posts/messages/records as untrusted data.
- DM reporting verifies that the authenticated caller is a participant and deliberately does **not** decrypt or routinely escrow E2EE message plaintext.
- Trade dispute evidence URLs have schema-level HTTP(S) constraints and the staff UI additionally passes displayed URLs through `getSafeHttpUrl` before opening/rendering.
- Central federation policy now classifies `org.swappulse.tradeDispute` as **NEVER_FEDERATE**, which is the correct privacy direction even though stale frontend/schema copy still says otherwise.
- The newer custom feed generator filters `moderation_status: escalated`; the remaining problem is inconsistent adoption, especially Explore.
- Login-code and WebAuthn flows explicitly consult enforcement state before returning login credentials when the lookup succeeds.
- Discord role reconciliation removes managed roles when AccountStatus is not active, giving enforcement a useful downstream integration once AccountStatus semantics are fixed.
- Destructive force-delete UI has multi-stage confirmation and type-to-confirm. The blocker is backend completeness/atomicity, not lack of warning.
- Moderation/report/dispute entities are staff-readable rather than public, and `reported_message_plaintext` is field-restricted to staff for legacy records.

## Architecture recommendation

Moderation should converge on one backend-owned case and enforcement architecture:

1. **ModerationCase**: immutable target reference, reporter/source provenance, case type, evidence revision/hash, state and assignment.
2. **ModerationEvent**: append-only human/AI/report/federation events. Never edit the original evidence or history.
3. **PlatformLabel**: backend-only issuer, subject, value, severity/action, created/expires/revoked state and external-label delivery state.
4. **Independent EnforcementState**: suspension, visibility restriction, messaging restriction, registration block and staff role restrictions represented independently rather than one overwritable enum.
5. **Role hierarchy**: normal moderator, senior moderator, admin, protected admin/last-admin rules and optional dual approval for destructive actions.
6. **Canonical visibility policy**: every Explore/feed/search/profile/recommendation endpoint calls the same server-side policy before returning content.
7. **Canonical report/dispute endpoints**: load authoritative target/participants, derive identity, rate-limit, dedupe and create immutable evidence.
8. **AI advisory boundary**: AI can classify/summarise/recommend, but cannot execute. Every recommendation records model/prompt/policy versions and the evidence snapshot it saw.
9. **Human decision executor**: typed actions such as dismiss-label, hide-content, warn-user, suspend-account and resolve-dispute are explicit and permission-checked. Never infer execution from changing an audit row.
10. **Appeals**: every appealable action has case reference, deadline, evidence, independent review policy and outcome notification.
11. **Federation outbox**: AT label issue/retraction is durable, idempotent, signed by the correct issuer and reconciled independently from local state.
12. **Abuse controls at mutation boundary**: bot/rate/replay checks execute inside the backend action, not as optional browser pre-flight.
13. **Audit immutability**: staff cannot fabricate/edit historical events; corrections are new events.
14. **Operator observability**: full pagination, backlog age/SLA, partial failures, external-label delivery health, appeal backlog and enforcement health.

## Required release tests

Before Moderation is release-ready, the exact build should prove at least the following:

- a post author cannot edit any moderation field through direct entity/API calls;
- one escalated/hide-labelled post is excluded from Explore, every custom feed, search, profile, recommendations and public endpoints;
- moderator cannot directly create/update AccountStatus;
- moderator cannot suspend an account, lift an admin suspension or shadow-ban an admin;
- admin suspension remains effective after any moderator action and concurrent transitions;
- AccountStatus datastore failure cannot allow a suspended login or expose enforced content;
- expiry produces consistent login/content/Discord-role state;
- duplicate AccountStatus rows cannot exist;
- force deletion is idempotent/resumable and never deletes User before required cleanup is complete;
- controlled PDS deletion/disconnect semantics are independently verified;
- normal report endpoint derives the real target/author and rejects fabricated IDs/types;
- duplicate/report-spam/rate-limit tests including direct API clients;
- DM reports require participant identity, preserve reporter ownership and never expose plaintext;
- trade dispute creation requires an authoritative participant and eligible trade state;
- staff cannot rewrite original report/dispute evidence;
- every dispute/report resolution produces an immutable audit event and user notification where policy permits;
- appeal can be filed only by an affected party and never mutates the original decision;
- post single/bulk dismiss produce identical local and external label retraction behaviour;
- external label failures retry/reconcile and do not silently look delivered;
- AI moderation remains advisory with no write tools and untrusted-content prompt-injection tests;
- ordinary users cannot call the moderation agent/API directly;
- decision-log reviews use atomic pending→resolved transition and concurrent reviewer tests;
- decision logs/moderation logs cannot be forged/edited directly by staff clients;
- bot-protected writes cannot bypass checks through direct entity APIs;
- action-bound bot token cannot be replayed or reused for another action;
- missing bot verification service fails safely for high-risk mutations;
- user/staff IP pseudonyms follow the approved retention/privacy design;
- queues paginate beyond 500 posts, 200 enforcement rows, 100 disputes/reviews and 50 logs;
- keyboard/screen-reader operation covers tabs, queues, dialogs, evidence and bulk actions;
- all supported locales render moderation/security copy correctly;
- canonical exact-commit build, lint, typecheck, unit, integration, E2E and adversarial suites pass.

## Release decision

SwapPulse Moderation is **NOT RELEASE READY**. The hardened advisory-only AI work is a meaningful improvement, but the release blockers sit in the human/platform trust boundaries: content owners can rewrite moderation state; Explore can return escalated scam-labelled posts; moderators can directly write AccountStatus and can downgrade an admin suspension; suspension checks fail open; force deletion is not atomic or PDS-complete; and bot protection can be bypassed when the client skips its pre-flight.

The recommended remediation order is:

**lock Post moderation fields -> fix Explore/all public enforcement -> make AccountStatus backend-only -> replace the single enforcement enum with hierarchy-safe independent states -> fail closed on suspension/enforcement lookup failure -> rebuild force deletion as a durable erasure job -> move reports/disputes behind authoritative backend endpoints -> make audit logs append-only -> implement real appeals -> unify label lifecycle/retractions -> bind bot controls to mutations -> finish AI review/dataflow cleanup -> add complete pagination/accessibility/localisation -> run exact-release regression/security tests.**

No functional application code or user data was changed during this audit. This file is an audit deliverable only.
