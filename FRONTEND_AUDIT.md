# SwapPulse Frontend Audit

**Audit date:** 11 September 2026  
**Scope:** React frontend, browser-side authentication/session handling, route guards, client trust boundaries, privacy/security controls shown to users, direct entity mutations, direct messaging/E2EE UX, PWA/service worker behaviour, uploads and browser storage, Web3 signing/recovery/bridge/staking UX, notifications, settings, accessibility, responsive navigation, public/private route behaviour, SEO/share behaviour and frontend release verification. Backend internals are excluded except where a frontend contract, browser mutation or user-facing promise depends on them.  
**Status:** **NOT FRONTEND-RELEASE READY**. Multiple unresolved P0 findings remain.

| Priority | Area | Finding | Required action |
| --- | --- | --- | --- |
| 🔴 P0 | Mobile primary actions | Authenticated mobile layouts mount both the Compose FAB and global Share FAB at `fixed bottom-20 right-4 z-40`. The controls overlap and Share is mounted after MobileNav, so a primary posting action can be obscured or intercepted. | Give Compose and Share distinct safe-area-aware positions, then test common phone widths and installed-PWA mode. |
| 🔴 P0 | Set browsing | `/set/:setId` renders `Explore`, but `Explore` does not read `setId`. Set cards therefore link to URLs that reopen the generic Explore state instead of the selected set. | Read `setId` with `useParams`, initialise/synchronise the set filter from the route and add direct-entry/back-forward route tests. |
| 🔴 P0 | Collector search | The main Search page invokes `search-profiles` using a free-text `{ query, limit }` contract while the current backend implements profile-chip discovery using `{ field, value, limit }`. Errors are converted to empty results. | Define one supported free-text profile-search API and use it consistently. Surface source failures instead of presenting false zero-result states. |
| 🔴 P0 | Feedback screenshot privacy | Opening the globally mounted Feedback control immediately runs `html2canvas(document.body)` and uploads the page screenshot before the user opts in or submits. This is available on Messages, Wallet, Settings, Admin and Moderation pages. Cancelling does not remove the already uploaded image. | Make screenshots explicitly opt-in, show a local preview before upload, exclude/redact sensitive regions, upload only on confirmed submission and delete abandoned uploads. |
| 🔴 P0 | False 2FA control | Account Settings contains a switch labelled **Two-factor authentication** and says it will require a second factor at login, but it only changes `SettingsConfig.security.mfaEnabled`. No authentication code consumes that value. The real TOTP/WebAuthn controls live separately in Security. | Remove the decorative switch immediately or bind it to the real factor-management API/state. Never show a security control as enabled unless the authentication boundary enforces it. |
| 🔴 P0 | False session-timeout control | Account Settings offers 1 hour, 6 hour, 24 hour and 7 day session timeout choices, but `security.sessionTimeout` is only stored in settings and is never used to expire or lock a session. | Remove the control or implement a server-authoritative session/inactivity policy and make the UI reflect the effective policy. |
| 🔴 P0 | Cookie consent overrides privacy | `CookieConsentBanner.persist()` always sends `notification_consent: true` and `do_not_sell: false`. A signed-in user who previously enabled Do Not Sell/Share or disabled notifications can reopen/save/reject cookie preferences and silently reverse those separate privacy choices. | Cookie-category updates must patch only cookie-related consent fields. Preserve existing federation and notification choices unless the user explicitly changes those controls. Add regression tests for Reject All and banner re-open. |
| 🔴 P0 | Custom handle trust in browser | `DomainHandleModal` obtains the persistent simulated signing key, sends a caller-provided DID to verification, constructs a `status: verified` HandleClaim in the browser, directly creates it, updates the PDS handle and then sets `handle_verified` on the user from the browser. | Replace the entire flow with one authenticated backend operation deriving DID from the session and returning a final authoritative result. The browser should only submit the requested domain and display status. |
| 🔴 P0 | Friendship acceptance in browser | `AddFriendLink` directly creates an accepted Friendship for the caller and updates the other party's pending Friendship row to `accepted`. A modified client can invoke the same entity methods outside the intended UI. Accepted friendship state is privacy-sensitive elsewhere. | Use backend request/accept/decline operations. The browser must never directly mutate another collector's friendship record or trusted acceptance state. |
| 🔴 P0 | Voice Space role authority | `InPlatformSpace` creates participant roles in the browser and directly updates `SpaceParticipant` for promote, demote, make moderator, revoke moderator, host mute/unmute and removal. UI `canManage` checks are bypassable. | Route every join and stage-management transition through an authorised backend endpoint. The browser should render permissions, not define them. |
| 🔴 P0 | Web3 recovery self-lock risk | `RecoveryPanel.propose()` calls `resetDeviceTestSigner()` before the backend accepts the recovery proposal. That deletes the currently stored signer and creates a replacement first. A failed proposal can therefore destroy a still-working local signer before recovery is on-chain/pending. | Generate a staged replacement key without deleting the active signer. Retain the current key until the recovery proposal is accepted and, ideally, until execution is confirmed. Require an explicit irreversible warning. |
| 🔴 P0 | Card bridge safety wording | `BridgePanel` correctly comments that cards are burned on the source chain, but the visible text tells users that the asset is “held here until the destination confirms”. That describes token escrow, not card burn, and obscures the failed-card-bridge recovery risk. | Use asset-specific confirmation language. For cards, explicitly disclose burn/recovery semantics before signing and disable card bridge-out until a demonstrated lossless recovery path exists. |
| 🔴 P0 | Staking asset recovery UX | When `valueFeaturesReady` is false, `StakingPanel` renders only a read-only stake view. Undelegate, withdraw and operator-exit controls disappear even for existing stake. Expired/revoked verification can therefore leave the UI with no recovery path. | Keep risk-reducing actions visible and callable regardless of current verification. Gate only new/increasing stake and operator registration. |
| 🔴 P0 | Client-side trust mutation architecture | The shipped frontend directly creates/updates trust-sensitive entities including Vouch, Reputation, Friendship, SpaceParticipant, SpaceSignal, HandleClaim, Follow, voting records, RSVP identity fields, Post system fields and multiple settings subjects. A modified client already has the entity names, method shapes and trusted fields required to tamper with them. | Migrate trust-sensitive mutations to narrow backend functions that derive identity and authoritative fields from `auth.me()`/server state. Keep browser entity writes only for genuinely user-owned, non-authoritative content. |
| 🟠 P1 | Decorative privacy settings | Settings presents Collection visibility, Trade listings visibility, Location precision, Hide monetary values and Data saver as active controls, but source-wide searches find no consumer or backend enforcement for those keys. | Wire each control to real rendering/data/federation behaviour with tests, or remove it. Privacy controls must never be decorative. |
| 🟠 P1 | Presence privacy | The app shell automatically publishes Presence heartbeats for signed-in users and surfaces Online Now. Help copy implies presence can be disabled, but there is no working presence control. | Add a real opt-in/opt-out presence setting, honour it before heartbeat creation/read exposure and delete stale presence when disabled. |
| 🟠 P1 | Consent continuity | Signed-out cookie choices live only in localStorage and are not automatically reconciled into the account after sign-in. Data & Rights then treats a missing ConsentRecord as marketing, analytics and push enabled. | Reconcile pre-login consent into the authenticated account and distinguish “not recorded” from “enabled”. |
| 🟠 P1 | Functional-cookie semantics | The cookie banner offers a Functional category, but app preferences, PWA features, IndexedDB E2EE keys and other functional storage are not actually gated by that setting. | Either classify essential/functional storage accurately and enforce the category, or remove a choice that the application cannot honour. |
| 🟠 P1 | Consent save failure feedback | Cookie consent persistence swallows backend errors and closes the banner anyway. A user can believe consent was recorded when only local state changed. | Keep the banner open or show a clear degraded state when account-side consent persistence fails. Retry safely and show the effective server state. |
| 🟠 P1 | Settings persistence races | `useSettings.update()` optimistically changes the entire config and fires asynchronous full-config writes without sequencing, rollback or user-visible save failure. Rapid changes can race and an older write can overwrite a newer privacy/notification choice. | Serialise/version settings writes, await acknowledgement, resolve conflicts and roll back or show an unsaved state on failure. |
| 🟠 P1 | Notification preference optimistic drift | `WhoCanReachYouCard` changes local state before saving. While `saving` is true, additional save calls are dropped, and failures do not roll local state back. The UI can therefore display privacy preferences that were never persisted. | Disable controls while saving or queue changes, then refresh from authoritative state after each mutation and roll back on failure. |
| 🟠 P1 | Browser-stored setup capability | Passwordless account setup stores `swappulse_setup_token` and email in localStorage across browser restarts. Any same-origin script can read the capability until successful completion removes it. | Keep setup capabilities in memory or sessionStorage at most, bind them tightly to one browser flow and clear them on failure/cancel/expiry. Prefer an HttpOnly one-time server flow. |
| 🟠 P1 | Browser-visible reusable login credential | The login UI receives a reusable `login_key` after OTP/WebAuthn and passes it to email/password login. A high-value account credential therefore exists in browser JavaScript memory. | Replace the password bridge with a one-time session exchange/magic capability so the browser never receives a reusable account password. |
| 🟠 P1 | Access-token storage | `app-params.js` persists `access_token` from the URL into localStorage by default before removing it from the address bar. Any same-origin script compromise gains a persistent bearer token, and URL-delivered tokens can persist longer than necessary. | Prefer secure cookie/session handling or session-scoped token storage. Do not persist URL bearer tokens unless strictly required. |
| 🟠 P1 | Cross-post credential exposure | Editing a CrossPostConfig repopulates stored `credential` and `extra_credential` into React inputs. Discord webhooks, Telegram bot tokens and other provider secrets are therefore retrievable by the browser instead of write-only. | Store provider credentials encrypted/server-side and return only masked metadata. Treat secret inputs as write-only replacement values. Never retrieve a Nostr private key to the app. |
| 🟠 P1 | Legacy simulated signing key | The frontend repeatedly calls `ensureUserDid()` and receives the persistent simulated HMAC `signingKey`, using it for posts, follows, trades, stories, polls, meetups and other records. | Retire browser possession of the simulated signer and derive authoritative identity/provenance from authenticated backend or real AT Protocol operations. |
| 🟠 P1 | E2EE key account isolation | Direct-message E2EE stores the keypair under one fixed IndexedDB key, `private-key`, rather than a user/DID-specific key. Multiple SwapPulse accounts in the same browser can reuse the same ECDH identity. | Namespace keys by stable account/DID and verify that the published public key matches the active account before sending/decrypting. |
| 🟠 P1 | E2EE key extractability | The P-256 ECDH private key is generated with `extractable: true` and stored in IndexedDB. A same-origin script compromise can export it, despite UI/policy language suggesting the key is strongly isolated to the device. | Generate the private key non-extractable where browser compatibility permits and accurately document the remaining same-origin threat model. |
| 🟠 P1 | Conversation partner identity | Conversation rows store the creator's target as `recipient_*`, but `ConversationList` and `MessageThread` always render `recipient_name/avatar/handle`. When the recipient views an incoming conversation, the header can identify themselves as the other party. | Resolve the other participant from `participant_dids` plus trusted profile metadata instead of reusing creator-relative recipient fields. |
| 🟠 P1 | DM notification path | The frontend `sendDirectMessage` path invokes the generic interaction notification function using a message action that is not part of that function's accepted interaction types, so message push/in-app notification attempts can fail silently. | Use a dedicated DM notification endpoint/event that derives participants server-side and sends a fixed non-content preview. |
| 🟠 P1 | Push registration truth | `subscribePush()` catches backend registration failure and still returns the browser subscription. `NotificationToggle` then reports Enabled based only on PushManager state. The UI can claim push is enabled while SwapPulse has no usable server token. | Treat backend registration as part of the transaction. On failure, unsubscribe/roll back or show a distinct “browser enabled, server registration failed” state. |
| 🟠 P1 | Push unregistration truth | Browser unsubscribe happens before backend deactivation; backend errors are swallowed. The UI can show Disabled while a stale server PushToken remains active until it naturally fails. | Make unregistration observable and reconcile server token state. Show failure and retry rather than silently claiming success. |
| 🟠 P1 | Privacy policy implementation drift | The current policy says E2EE DMs are mirrored to the PDS although current code says new DMs are local-only; it describes AI moderation applying labels despite the hardened advisory-only model; it promises deletion/export completeness that the backend audit disproves; and it describes consent-controlled functional storage that is not enforced. | Reconcile the policy line-by-line with the actual product before release and obtain privacy/legal review for the final wording. |
| 🟠 P1 | Remote image privacy | User/federated avatar and image components can render arbitrary remote URLs directly in the visitor's browser without a privacy proxy or consistent `no-referrer` policy. Third-party image hosts can receive network metadata and act as tracking pixels. | Proxy/cache remote media through a controlled image service where possible, validate media type/size and set a strict referrer policy. |
| 🟠 P1 | Third-party font request | Global CSS imports Google Fonts directly from `fonts.googleapis.com`. This third-party request occurs as part of page styling rather than being tied to recorded optional consent. | Self-host the required fonts or remove the external request. Update the privacy inventory if any third-party font delivery remains. |
| 🟠 P1 | Web3 transaction review | `useChainAction` drafts a transaction and immediately signs the returned hash with the local signer. The user sees generic progress text but no independent review of contract address, selector, calldata, destination, amount/token, fee or burn consequence before signing. | Add an explicit transaction-review confirmation generated from the signed draft, then sign only after the user confirms the exact effects. |
| 🟠 P1 | Bridge address validation UX | Bridge submit becomes enabled when a destination string is merely longer than seven characters. Ethereum/L2/Solana destination formats are not validated in the browser before an irreversible flow begins. | Add chain-specific client validation/checksum feedback while retaining authoritative server validation. Never imply an address is acceptable based on length. |
| 🟠 P1 | Software signer threat model | The Stark signer ciphertext and non-extractable AES-GCM CryptoKey live together in IndexedDB. This protects casual storage inspection but same-origin JavaScript can still ask the CryptoKey to decrypt/sign. | Keep testnet wording explicit and migrate high-value production signing to hardware/passkey-backed account validation with explicit approval. |
| 🟠 P1 | Card verification wording | `MintedCardsPanel` treats every `status: verified` CardVerificationSession as “Verified cards on chain” and says the collector proved possession. Lower trust levels, including self-claim/partial visual checks, do not establish Level 2 possession proof. | Filter/label by verification level and reserve “proved possession” language for the defined Level 2+ boundary. |
| 🟠 P1 | Card attestation wording | Card attestation UI still uses wording such as “AI VERIFIED” / ownership-oriented language even though the hardened model performs a visual possession check, not authenticity, grading or legal ownership verification. | Rename levels and CTA/copy to “visual match” / “possession check” and explain exactly what each level proves. |
| 🟠 P1 | Collection truncation | The Collection page loads at most 500 CollectionEntry rows even though bulk import supports much larger collections. Counts, total value, analytics, duplicates and binder operations silently operate on the truncated subset. | Add cursor pagination or a server aggregate/full collection API. | 🟠 P1 | Sidebar portfolio truncation | RightSidebar loads only 200 CollectionEntry rows and labels the resulting value/count as “Your Portfolio”. Large collectors receive incorrect totals without any indication that they are partial. | Use server aggregates or complete paginated data and label estimates explicitly when partial. |
| 🟠 P1 | Binder privacy optimistic failure | `setBinderSetting()` changes local binder visibility/grid state, then silently ignores `auth.updateMe()` failure. A user can see their binder as private/public locally even when persistence failed. | Roll back on failure and show a clear save error, especially for `binder_public`. |
| 🟠 P1 | Global sharing on private routes | Layout mounts the global Share FAB on protected/internal routes including Messages, Settings, Wallet, Admin and Moderation. ## Verified frontend controls and strengths

The audit also re-verified several good foundations that should be preserved. User/post text is normally rendered as React text rather than arbitrary HTML; no broad user-controlled `dangerouslySetInnerHTML` sink was found. External links use shared HTTP(S)-only handling in newer flows, video embeds are click-to-load, SEO JSON-LD is assigned through `textContent`, authentication return paths use a same-origin-safe helper, route-level lazy loading is widely used, the main layout includes a skip-to-content link and global focus-visible styling, Web3 draft signing validates that the value is a Starknet field hash and zeroes decrypted private-key bytes after signing, the testnet signer vault is scoped per Base44 user ID, scanner/card-attestation media uses private uploads in the hardened path, and the newer security-factor UI uses genuine backend step-up rather than browser-only state.

## Frontend release decision

SwapPulse should **not** be treated as frontend-release ready while any unresolved P0 remains. The immediate remediation order should be: **feedback screenshot privacy and cookie-consent regression; remove fake 2FA/session-timeout controls; move custom-handle/friendship/voice-space/trust authority out of the browser; fix Web3 recovery/bridge/staking safety; repair the three major navigation/search route blockers; then privacy/settings/E2EE/push/PWA/accessibility issues.**

After remediation, rerun the frontend audit against the exact deployed commit at phone, tablet and desktop widths, signed out and signed in, with at least two test accounts, keyboard/screen-reader testing, installed-PWA offline/push testing, multi-account E2EE testing and explicit malicious-client tests proving the browser can no longer assign trusted state directly.
