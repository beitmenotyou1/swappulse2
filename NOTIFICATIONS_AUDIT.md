# SwapPulse Notifications Audit

**Audit date:** 12 September 2026  
**Scope:** In-app notifications, Web Push/PWA delivery, unread/read state, notification settings and consent, quiet hours, social interactions, follows/bell alerts, direct messages, trade notifications, wishlist/price alerts, achievements, starter packs, wallet/chain alerts, weekly email digest, AT Protocol notification ingestion/import, deep links, delivery logs, workflows, permissions and notification-specific test coverage.  
**Overall score:** **38/100 - High Risk / Needs Remediation**  
**Release status:** **NOT RELEASE READY**

## Findings

| Priority | Area | Finding | Required action |
| --- | --- | --- | --- |
| P0 | Push recipient isolation | **NF-001 - PushToken records are not cryptographically or authoritatively bound to the creator's DID.** `PushToken` RLS permits any authenticated user to create a row they own while accepting an arbitrary `did`. The central dispatcher later selects active subscriptions by recipient DID using service-role access. A malicious authenticated user can therefore create a PushToken addressed to another user's DID but containing an attacker-controlled push subscription and receive that recipient's push payloads. The normal `register-push-token` function stamps the correct DID, but direct entity creation remains allowed. Current data has one active PushToken and no evidence that this exploit has been used. | Make PushToken backend-only for create/update/delete. Derive `did` and user ownership exclusively from the authenticated session. Reject endpoint registration if its existing owner does not match the authenticated identity. Add a regression test proving a user cannot register a token for another DID. |
| P0 | Notification policy isolation | **NF-002 - SettingsConfig notification policy can be created for another user's DID.** `SettingsConfig` RLS is based on `created_by_id`, not `data.did == user.did`. The dispatcher loads the newest SettingsConfig by recipient DID. An authenticated attacker can therefore create a newer config under a victim DID and alter push channels, event toggles, quiet hours or timezone used for that victim. Current data already contains six SettingsConfig rows, including duplicate DID rows and three rows whose stored DID does not match the creator's current `User.did`; those mismatches may be legitimate migration history, but they demonstrate that policy identity and row ownership are already capable of diverging. | Move SettingsConfig mutation behind a backend upsert that derives DID from the authenticated user. Enforce one authoritative config per current identity, reconcile historic DID changes, and reject direct browser creation with arbitrary DID. |
| P0 | Notification policy isolation | **NF-003 - NotificationPreference can be created for another user's DID.** The entity is described as one record per user, but its create rule only checks row ownership. A malicious authenticated user can create a row they own with a victim's `did` and `paused: true`, `followed_only`, or `on_site_only`; `shouldDeliverNotification()` then loads the newest row by victim DID and can suppress that victim's notifications. There are currently zero NotificationPreference records, so this is a code-proven latent issue rather than an observed active attack. | Make NotificationPreference backend-owned and session-derived. Enforce uniqueness by current user/DID and use a server upsert endpoint. Add cross-account mutation tests. |
| P0 | Consent integrity | **NF-004 - ConsentRecord ownership is not bound to its declared user_id or DID.** RLS allows an authenticated user to create an owned ConsentRecord while choosing arbitrary `user_id` and `did`. Backend communication code builds a service-role consent map keyed by `user_id`, so a forged row can influence another account's push/marketing consent. `getConsentMap()` also iterates records newest-first and overwrites map entries as it goes, meaning an older duplicate can override a newer consent decision. The one current ConsentRecord has a DID that differs from its owner's current User DID, consistent with historic identity migration. | Make consent writes backend-only through `update-consent-preferences`, bind both user_id and DID to the session, enforce one row per user, and resolve the newest authoritative record deterministically. Treat explicit withdrawal as fail-closed. |
| P0 | Interaction authenticity | **NF-005 - Authenticated users can forge trusted interaction notifications to arbitrary recipient DIDs.** `notify-interaction` correctly binds regular callers to their own actor identity, but it accepts caller-supplied `recipientDid`, `post.id`, post URI/content and action type without loading the authoritative post or proving that a Like, Repost, Reaction, Quote or Comment record by the caller actually exists against a post owned by that recipient. A logged-in attacker can therefore inject false social events into another user's trusted notification inbox and vary subject IDs to evade normal grouping. | Derive the recipient and target from the authoritative interaction/post records server-side. Require the triggering interaction to exist and belong to the authenticated actor. Make producers call notification creation after successful authoritative mutations rather than accepting a free-form client notification request. Add abuse/rate tests. |
| P0 | Push delivery | **NF-006 - The central Web Push path is currently failing in production.** The current NotificationLog dataset contains 296 dispatch records; 264 are recorded as `failed` with `VAPID setup failed`, including the newest notification attempts on 10 September 2026. Earlier records show some successful delivery, so this is a current regression/configuration failure rather than a design-only concern. | Validate the deployed VAPID public/private key pair and runtime configuration immediately. Add a startup/health check that verifies Web Push configuration, an admin delivery diagnostic, alerting on sustained failure rate, and a release gate requiring a successful real-device test push. |
| P0 | Multi-account push isolation | **NF-007 - A browser push endpoint is not globally exclusive to one SwapPulse identity.** `register-push-token` searches for an existing endpoint only within the current DID. The same browser PushSubscription endpoint can therefore remain active under an old account and be registered again under a different account after account switching. Pushes for both identities can reach the same browser, leaking the previous account's notification content to the current device user. | Treat endpoint as globally unique. On authenticated registration, atomically transfer or reject an endpoint already bound to another user after appropriate re-authentication. On logout/account switch, deactivate that account's endpoint where policy requires it. Add shared-device/account-switch tests. |
| P1 | Delivery architecture | **NF-008 - Several notification senders bypass the central dispatcher and its policy controls.** `dispatchBellNotifications`, `checkWishlistAlerts`, `sendTradeAdvicePush`, and parts of `sendPush` send Web Push directly. They do not consistently apply NotificationPreference, SettingsConfig event/channel rules, quiet hours, multi-device PushToken delivery, daily rate controls or NotificationLog observability. | Route every user-facing push through one authoritative dispatcher. Pass a typed event and recipient, then apply consent, preference, channel, quiet-hour, rate, token and logging policy exactly once. Retire direct `webPush.sendNotification` paths outside the dispatcher. |
| P1 | Trade notifications | **NF-009 - The Trade Status Notifications workflow calls a backend function that does not exist.** The workflow invokes `notifyTradeUpdate`, but no `base44/functions/notifyTradeUpdate` function is present in the current app. Trade status changes therefore cannot deliver through the workflow as documented. | Implement a backend-owned idempotent trade-status notification producer or update the workflow to an existing supported function. Verify listing owner and participants server-side, then test open/accepted/completed/cancelled transitions. |
| P1 | Settings contract | **NF-010 - Notification setting keys do not match actual notification types.** Settings expose keys such as `direct_message`, `achievement`, `trade_update`, `followed_post`, `community_label`, `vouch_received`, `meetup_announcement`, `challenge_update`, and `weekly_digest`, while actual Notification/dispatcher types include `message`, `reputation`, social interaction types, wallet events and `chain_*` events. Unknown types default enabled. Several visible toggles therefore do not control the notifications their labels promise, while some real events have no user toggle at all. | Define one canonical notification event enum shared by schema, UI, producers, dispatcher and documentation. Add explicit mappings only where unavoidable and test every visible toggle against the real event type it controls. |
| P1 | Master pause | **NF-011 - “Pause all notifications” is not universally enforced before in-app records are created.** `notify-interaction` and AT notification ingestion call the filter before creation, but other producers such as `notify-new-message`, chain event helpers, achievements and some starter-pack flows create Notification rows first and only invoke the dispatcher afterwards. A paused user can therefore still receive in-app notifications even when the UI says every notification is silenced. | Require all notification creation to go through one backend policy gate before the Notification entity is written. Treat `paused` as authoritative for both in-app and push channels. |
| P1 | Channel settings | **NF-012 - The “In-app toasts” channel toggle is not an authoritative in-app channel control.** SettingsConfig channels are read by the dispatcher mainly to decide push versus an `in_app` outcome, but producers independently create Notification entities and realtime popups. Disabling the in-app channel does not reliably stop in-app records/toasts. | Model channels explicitly and enforce them before record creation/popup dispatch. Decide whether “in-app” means persistent inbox records, foreground toasts, or both, then expose separate controls if needed. |
| P1 | Quiet hours | **NF-013 - Quiet-hour modes “Hold until end” and “Batch into digest” are UI-only choices.** The dispatcher detects a quiet window but ignores the stored `mode`; both choices simply downgrade push to an `in_app` result. There is no deferred queue, release at quiet-window end, or digest batch. | Implement a durable deferred-notification queue with scheduled release and a real digest batch, or remove the unsupported modes and accurately label quiet hours as “suppress push”. |
| P1 | PWA integration | **NF-014 - The service worker and React NotificationHandler use incompatible message protocols.** `NotificationHandler` listens for `PUSH_RECEIVED` and `NAVIGATE` service-worker messages, but `public/sw.js` never posts either message. It directly displays OS notifications and directly navigates on click. As a result, the foreground push-banner path and `mark-notification-opened` hook in NotificationHandler do not run for actual push clicks. | Define one service-worker/client protocol. Post foreground delivery and click events with the log/notification IDs, or move opened/read tracking to a backend URL/click endpoint. Add service-worker integration tests. |
| P1 | Push deep links | **NF-015 - Legacy/direct push payloads use `url`, but the service worker only reads `data.route`.** Bell notifications, wishlist alerts, broadcast push and trade-advice push emit a top-level `url`; `sw.js` ignores it and falls back to `/`. Those push notifications can therefore open the app home instead of the intended card, trade or collection destination. | Standardise the payload shape on `data.route` using the safe deep-link builder. Remove legacy payload formats and test notification clicks for each event family. |
| P1 | Push registration UX | **NF-016 - Push subscription can appear enabled even when backend registration failed.** `subscribePush()` catches and logs failure from `register-push-token`, then still returns the browser PushSubscription. `NotificationToggle` checks only local `PushManager`, so it can display “Enabled” while the server has no usable token for the account. | Treat backend token registration as part of the subscription transaction. Surface failure, optionally unsubscribe the local browser token on failure, and expose a backend registration health state in the UI. |
| P1 | Multi-device push | **NF-017 - Unregistering one device clears the legacy user push subscription even when other active devices remain.** The backend deactivates the matching PushToken but unconditionally clears `User.push_subscription`. Legacy senders that still depend on that field stop reaching the user even though another PushToken device may still be active. | Eliminate legacy `User.push_subscription` after all senders use PushToken. Until then, recompute the legacy mirror from a remaining active token rather than clearing it unconditionally. |
| P1 | Token lifecycle | **NF-018 - Legacy direct push paths do not clean up expired subscriptions.** The central dispatcher deactivates PushToken records on 404/410, but bell/wishlist/trade-advice senders silently drop failed legacy subscriptions and leave `User.push_subscription` stale, contrary to the notification API documentation. | Centralise token lifecycle handling. On 404/410, deactivate/remove the authoritative token and update any compatibility mirror. |
| P1 | Direct messages | **NF-019 - The DM client invokes `notify-interaction` with unsupported action type `message`.** `dmBridge.sendDirectMessage()` makes a best-effort call using `actionType: 'message'`, while `notify-interaction` only accepts like/repost/quote/comment/reaction. The call always fails; delivery currently depends on the separate New Message Notifications workflow. | Remove the dead client call and make the workflow/backend producer the single DM notification source, or provide a dedicated authenticated DM notification function that verifies the DirectMessage record. |
| P1 | Direct messages | **NF-020 - New-message notification creation has no idempotency key.** `notify-new-message` creates an in-app Notification for every workflow invocation without checking a stable group/message key. Workflow retries or duplicate triggers can create duplicate inbox entries and duplicate pushes. | Use `message_id` as an idempotency key/group key and make creation upsert/insert-once. Add workflow retry tests. |
| P1 | Realtime alerts | **NF-021 - Normal-user realtime trade/price notification calls target an admin-only backend.** `realtime.js::notifyForMe()` invokes `notify-system-event`, but that function rejects callers unless `role === 'admin'`. For ordinary users, realtime-detected trade matches and price alerts fail to persist/dispatch through this path. | Move these detections to trusted backend producers/workflows, or add a user-safe endpoint that derives recipient and event from authoritative server data. Do not make the current free-form system endpoint public. |
| P1 | Recipient filters | **NF-022 - System alerts are incorrectly passed through actor relationship filters as actor `system`.** `notify-system-event` calls `shouldDeliverNotification(... actorDid: 'system')`. Users who select “only people I follow” or “on-site users only” can have legitimate price/trade/system events rejected because `system` is not a followed/on-site actor. | Omit actorDid for system-generated events so only applicable controls such as pause/event/channel policy are evaluated. |
| P1 | Wishlist/price alerts | **NF-023 - Scheduled wishlist alerts do not create unified Notification inbox records.** `checkWishlistAlerts` sends direct push/email only. This contradicts the Notifications documentation and means a user can receive a price/trade alert outside the app with no persistent entry in their notification history. | Create the canonical in-app notification through the central notification service and dispatch configured channels from that record/event. |
| P1 | Wishlist/price alerts | **NF-024 - Wishlist alerts are marked triggered even when no notification was successfully delivered.** Once a search matches, `last_triggered_at` is updated regardless of whether the user has a push subscription, email address, or whether either send succeeds. The 24-hour dedup window can therefore suppress retries after total delivery failure. | Record channel-specific delivery results and update the dedup timestamp only after at least one configured channel succeeds, or maintain retry/backoff state separately. |
| P1 | Weekly digest | **NF-025 - Weekly digest controls are split across unrelated settings and do not share one source of truth.** The Notifications settings expose an `email_digest` channel and `weekly_digest` event toggle, but the scheduled `weeklyDigest` function actually checks `User.weekly_digest` plus marketing consent. The profile has a separate WeeklyDigestToggle. Changing the notification settings does not necessarily change digest delivery. | Consolidate weekly digest preference into one backend-owned setting and have both UI surfaces read/write it. Make email channel, event toggle and marketing consent semantics explicit and consistent. |
| P1 | Rate limiting | **NF-026 - The 50/day push limit counts NotificationLog rows rather than successful push deliveries.** A log is created before the limit check, and the count includes failed, in-app-only and the current attempt. Large failure bursts can consume a recipient's push quota even though no pushes were delivered. | Count successful push deliveries only, excluding the current pending attempt, or maintain an atomic per-recipient delivery counter. |
| P1 | Read state | **NF-027 - “Mark all read” processes at most 500 unread records.** The backend queries a maximum of 500 and loops through them. Users with more than 500 unread notifications can press Mark All and still have older unread items, while the client optimistically reports success. | Use paginated/batched server processing until no unread records remain, or store and enforce a durable read checkpoint. |
| P1 | Notification history | **NF-028 - The Notifications page only loads the latest 50 records and has no cursor or “load more”.** Current production data already exceeds the query ceiling: the audit query returned the maximum 500 Notification records. Older history is therefore inaccessible from the normal page. | Add cursor-based pagination/infinite scroll and keep filters server-compatible so older records remain reachable. |
| P1 | AT Protocol ingestion | **NF-029 - Live Bluesky ingestion only requests the latest 30 notifications and does not page a cursor.** The workflow runs every five minutes; if an account receives more than 30 relevant AT notifications between successful polls, older unseen events can fall out of the window and never be mirrored locally. | Persist the last processed cursor/indexed timestamp per user and page until the previous checkpoint is reached, with a bounded continuation mechanism for bursts. |
| P1 | Deduplication | **NF-030 - Comment notification dedup collapses distinct comments from the same actor on the same post.** Both local `notify-interaction` and live AT ingestion build keys based on action type + subject/post + actor. Multiple legitimate comments/replies by one actor to the same target share that key, so later comments are treated as duplicates. | Use the unique interaction record URI/ID for comment/quote/reaction events. Keep actor+subject dedup only for interaction types whose protocol semantics are singular, such as one current like record. |
| P1 | Policy data model | **NF-031 - “One record per user” notification settings are not actually unique.** SettingsConfig, NotificationPreference and ConsentRecord do not enforce the documented one-record invariant. Service code usually takes one row by sort order, making policy dependent on duplicate timing. Current SettingsConfig data already contains duplicate rows for the same stored DID. | Enforce a stable per-user key/idempotent upsert and migrate duplicates to one canonical record. Do not rely on newest-row races for security/privacy policy. |
| P1 | Identity migration | **NF-032 - Notification policy state is keyed to mutable DID values without a complete migration/reconciliation layer.** Current data contains SettingsConfig and ConsentRecord DIDs that differ from their creators' current User DIDs, indicating historic identity changes can leave stale policy rows. PushToken, preference/filter and dispatcher lookups are DID-centric, so a DID change can silently reset or strand settings. | Bind policy primarily to immutable Base44 user ID and resolve current DID at delivery time. On DID migration/link changes, transactionally reconcile PushToken, settings, preferences and consent denormalised DID fields. |
| P1 | Privacy failure mode | **NF-033 - Notification preference and settings lookups fail open.** `notificationFilter` explicitly delivers on preference/follow/on-site lookup errors, and the dispatcher silently falls back to default-enabled settings if SettingsConfig reads fail. A transient datastore failure can therefore send a notification that a user had paused or disabled. | Fail closed for explicit privacy/suppression controls. Cache the last known policy if necessary, but do not interpret an inability to read a user's opt-out as permission to send. |
| P1 | Read/open state | **NF-034 - Opening an OS push does not mark the persistent Notification inbox record read.** The service worker only navigates. It does not identify/update the Notification entity, and the push log ID is not linked to a corresponding Notification record for read-state mutation. A user can act on a push yet retain a stale unread badge/item. | Include both delivery-log and Notification record IDs in the canonical push event, then atomically mark opened/read after a validated click. |
| P1 | Channel policy | **NF-035 - Explicit notification consent is not an authoritative gate for the central dispatcher or several direct senders.** `ConsentRecord.notification_consent` is checked by `sendPush`, but `dispatchNotification` does not consult it, and bell/wishlist/trade-advice paths also bypass it. A user who withdraws push consent can still be eligible for other push paths if a subscription remains. | Make notification consent the first mandatory gate inside the central dispatcher and remove all bypass senders. On withdrawal, deactivate push tokens or otherwise make dispatch impossible until re-consent. |
| P2 | Unread badge | **NF-036 - Navigation unread count is silently capped at 200.** `useUnreadCount()` fetches at most 200 unread records and uses array length as the badge count. | Use a server-side count endpoint or display `200+` when capped. |
| P2 | Optimistic read state | **NF-037 - Read-state mutations fail silently with no rollback.** `markRead()` and `markAllRead()` optimistically alter local state and swallow backend errors. The UI can show an item as read while the server remains unread. | Roll back on failure and show a non-intrusive error/retry state. |
| P2 | NotificationState | **NF-038 - NotificationState is effectively dead/append-only state rather than the documented cross-device checkpoint.** The client creates a new NotificationState on each Mark All action, no notification read logic consumes it, and the current dataset contains zero NotificationState rows. | Either implement one upserted checkpoint that drives unread calculations and federation/repository sync, or remove the unused entity/write. |
| P2 | Direct-message privacy/UX | **NF-039 - DM notification previews use the encrypted message body itself.** `notify-new-message` slices `DirectMessage.body`, which is E2EE ciphertext, for `target_label` and push body. Plaintext is not leaked, which is good, but users receive unreadable ciphertext and the push service/OS is unnecessarily given ciphertext material. | Use a fixed privacy-preserving string such as “Encrypted message” and never include message ciphertext in notification payloads. |
| P2 | Wallet/chain UX | **NF-040 - Wallet and chain notification types are not fully represented in notification card/popover/banner presentation.** The schema includes wallet_topup, escrow, low_balance and multiple `chain_*` events; current production notifications include wallet_topup and chain_stake. UI metadata/action-text maps omit most of them, so users can see generic “Someone notified you” copy and generic bell icons for important financial/chain events. | Create explicit safe copy, icons and routes for every wallet/chain event and test them with representative metadata. |
| P2 | Social UX | **NF-041 - Repost notifications have an icon but no action text case in NotificationCard/Popover.** They fall through to generic “notified you” wording despite being a first-class action type. | Add repost copy consistently across card, popover and popup presentation. |
| P2 | Documentation/UI drift | **NF-042 - Notification filter documentation and the actual page disagree.** Documentation describes All, Mentions, Trades, Alerts and Follows, while the current page exposes All, Unread, Mentions and Follows. Trade/alert filtering is unavailable. | Update the UI to the documented filter set or update docs after product decision; preferably add server-compatible trade/alert filters with pagination. |
| P2 | OS notification grouping | **NF-043 - Service-worker notification tags are only the notification type.** `sw.js` uses `notificationType` as the browser `tag`, so multiple unrelated notifications of the same type can replace/collapse one another in the OS notification centre instead of remaining individually actionable. Legacy payloads all fall back to tag `default`. | Use a stable per-event/group identifier as the tag, and use renotify/grouping intentionally where supported. |
| P2 | Delivery observability | **NF-044 - NotificationLog has one aggregate status for a multi-device dispatch.** When several PushToken subscriptions are attempted, one success makes the log `delivered` even if other devices fail. There is no per-device delivery audit or failure reason history. | Add child delivery-attempt records per token/device or structured per-device outcomes while retaining a parent event status. |
| P2 | Broadcast scalability | **NF-045 - Admin broadcast push only scans the first 500 users.** `sendPush` calls `User.list(..., 500)` and has no continuation, so accounts beyond the cap silently miss broadcasts. | Paginate all users or enqueue batches with resumable cursor state. |
| P2 | Weekly digest completeness | **NF-046 - Weekly digest source datasets are capped globally before per-user partitioning.** Collection entries are limited to 500, trades to 200, wishlist to 500. At scale, later users can receive incomplete portfolio/trade/wishlist summaries even though they opted in. | Query per user or page all source datasets before aggregation. Add correctness tests above each current cap. |
| P2 | AT ingestion scalability | **NF-047 - Live AT notification ingestion only considers the first 500 migrated users.** Accounts outside that global query will never enter the rotating 20-user processing window. | Cursor/page migrated users, persist rotation position, and make coverage measurable. |
| P2 | Regression testing | **NF-048 - No dedicated notification/push regression tests were found in the current Base44 source.** A project search found no notification-focused test/spec files; the sandbox also exposes no package manifest/test runner. Critical cross-account, consent, workflow retry, service-worker and multi-device behaviours therefore lack executable regression coverage here. | Add unit tests for policy/dedup/deep links, integration tests for entity RLS and producers, workflow retry/idempotency tests, and browser/service-worker Web Push tests including account switching and revoked consent. |

## Release gate

Notifications should remain **NOT RELEASE READY** until at minimum NF-001 through NF-007 are fixed and regression-tested. In particular, do not treat browser push as production-complete while the current delivery logs continue to record `VAPID setup failed`.

## Current production evidence

The audit used read-only production/entity inspection in addition to source review. The current technical state shows:

- The Notification query returned the audit maximum of **500 records**, confirming that the normal 50-item page is already truncating available history.
- NotificationLog contains **296 records** in the current dataset. **264** are recorded as failed specifically because of `VAPID setup failed`; the newest observed failures are dated **10 September 2026**.
- One active PushToken record currently exists. No evidence of cross-DID PushToken abuse was found; NF-001 and NF-007 are architectural trust-boundary findings.
- There are **zero NotificationPreference records** and **zero NotificationState records** currently.
- There are **six SettingsConfig records**. Duplicate stored DID values exist, and three records have a stored DID that differs from the creator's current `User.did`. This can result from legitimate identity migration, but confirms stale/duplicate policy state exists today.
- The current ConsentRecord count is one. Its stored DID differs from the owner's current User DID, while its immutable Base44 user_id remains associated with that account.

No malicious rows, fake victim tokens or forged notifications were created during this audit.

## Verified strengths

Several parts of the notification architecture are solid foundations and should be retained:

- `Notification` records are backend-controlled: ordinary browser users cannot create, rewrite or delete arbitrary Notification rows directly, and reads are scoped to the recipient DID/admin.
- `mark-notifications-read` service-role mutation verifies the authenticated recipient before changing a record.
- The normal `register-push-token` backend derives the user's DID from the authenticated session rather than trusting a body DID.
- The central dispatcher supports multiple PushToken devices and deactivates token records that return HTTP 404/410.
- VAPID private material stays server-side; the browser only fetches the public key.
- Server deep-link builders produce internal SwapPulse routes, and imported Bluesky URLs are converted into on-site post/profile routes rather than intentionally sending users off-site.
- `notify-interaction` binds ordinary callers to their authenticated actor identity, preventing direct actor-DID impersonation.
- Live AT notification ingestion excludes enforced accounts, records remote origin metadata, checks NotificationPreference before creating supported social notifications, and mirrors the remote read flag.
- Historical AT notification import uses cursor pagination and stores progress on the user, so the backfill is resumable rather than a single shallow snapshot.
- Direct messages remain local-only and E2EE; the notification defect exposes ciphertext, not message plaintext.
- Weekly portfolio digest email requires both the user-specific digest opt-in and marketing consent.
- System/broadcast notification functions are admin-gated rather than freely callable with arbitrary recipients.

## Recommended remediation order

1. Lock PushToken, SettingsConfig, NotificationPreference and ConsentRecord mutation behind backend-owned session-derived upserts.
2. Fix and independently verify the deployed VAPID configuration, then require a successful real-device push health test.
3. Make notification consent and master pause mandatory fail-closed gates inside one central notification service.
4. Remove free-form client notification creation semantics from `notify-interaction`; derive recipients/targets from authoritative interaction records.
5. Enforce global push endpoint ownership and safe account-switch/logout handling.
6. Route every push producer through the central dispatcher and retire direct legacy `webPush.sendNotification` implementations.
7. Repair Trade Status Notifications and move realtime price/trade matching to trusted backend producers.
8. Create one canonical event-type registry shared by entity schema, producers, settings UI, cards and documentation.
9. Implement real quiet-hour hold/digest semantics or remove unsupported choices.
10. Unify the service worker and React push/open protocol and standardise payload/deep-link shape.
11. Add idempotency for DM and comment/reply events, then repair social dedup keys.
12. Add cursor pagination to notification history and live AT ingestion, and remove global 500-user/source caps.
13. Reconcile notification policy state whenever a user's DID changes.
14. Add notification-specific security, workflow, multi-device and PWA regression tests.

## Required regression tests

### Recipient isolation

- User A cannot create or mutate a PushToken addressed to User B's DID.
- User A cannot create SettingsConfig, NotificationPreference or ConsentRecord policy for User B.
- The same push endpoint cannot remain active under two unrelated identities without an explicit authenticated transfer.
- DID migration preserves the same account's notification policy without leaking or resetting it.

### Consent and policy

- Withdrawn notification consent blocks every push producer.
- `paused: true` prevents both in-app records and push delivery.
- `followed_only` and `on_site_only` apply only to actor-originated events and do not suppress system events.
- Every event toggle disables the exact corresponding event type.
- Policy datastore failure does not override an explicit opt-out.

### Push and PWA

- Valid VAPID configuration sends successfully to a real browser/device subscription.
- Invalid VAPID keys fail health checks before release.
- Push click opens the expected internal route and marks both delivery log and persistent notification appropriately.
- Browser-only subscription with backend registration failure is shown as failed, not enabled.
- Multi-device delivery records per-device success/failure and unregistering one device leaves other devices working.
- 404/410 invalid subscriptions are deactivated for every delivery path.

### Social and messaging

- A caller cannot forge a like/repost/comment notification without the corresponding authoritative interaction.
- Multiple distinct comments from the same actor on the same post each produce one notification.
- Workflow retry of the same DirectMessage produces exactly one notification.
- DM push copy never contains plaintext or ciphertext body material.

### Trade, wishlist and system events

- Every trade status transition invokes a real backend producer and notifies only authorised participants.
- Realtime/scheduled price alerts create a persistent in-app Notification and configured external channels.
- Failed wishlist delivery remains retryable and does not start the 24-hour success suppression window.
- Quiet-hour hold and digest modes behave as labelled.

### Read state and scale

- Mark All reads more than 500 unread records correctly.
- Notification page can traverse more than 500 historical records without duplicates or gaps.
- Unread count above 200 is accurate or intentionally represented as a capped value.
- More than 30 AT notifications between polls are fully ingested.
- More than 500 migrated users continue to receive AT notification ingestion.
- Broadcast and weekly digest processing covers datasets above current limits.

## Audit limitations

- The required Base44 MCP README endpoint returned HTTP 403 when fetched from the project sandbox during this audit. The audit proceeded against the connected app's actual source, schemas, workflows and live entity data.
- No destructive exploit demonstration was performed. Cross-account PushToken/settings/preference/consent findings are established from RLS plus backend lookup behaviour, not from planting malicious production records.
- The audit did not expose or copy VAPID private keys. The active VAPID problem is evidenced by the application's own NotificationLog failure state.
- No notification-focused automated test files or runnable package manifest were available in the Base44 sandbox snapshot, so notification regression tests could not be executed there.
- External browser push-service availability can vary by platform. The report distinguishes that from the application's explicit `VAPID setup failed` state, which occurs before normal delivery succeeds.

## Conclusion

SwapPulse has a broad notification feature set and several good building blocks: backend-controlled inbox records, a central dispatcher, multi-device token modelling, safe internal deep links, AT Protocol ingestion and resumable notification import. The system is not ready for production sign-off yet because its trust boundaries are split across direct entity writes and multiple delivery paths, and the current central push configuration is demonstrably failing.

The remediation goal should be one authoritative server-side notification pipeline: authenticated/verified event -> authoritative recipient -> consent and preference policy -> persistent notification -> configured channels -> per-device delivery result -> read/open reconciliation. Once every feature uses that same path, most of the current security, privacy, reliability and UX drift disappears together.
