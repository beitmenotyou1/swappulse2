# SwapPulse Blockchain / Web3 Audit

**Audit date:** 11 September 2026  
**Scope:** Entire SwapPulse Web3 surface: Cairo/Starknet contracts, V2 identity and assurance, SwapPulseAccount and recovery, SWPX token, CardNft, Proof of Usership, staking, bridge, Base44 chain mirrors and functions, user signing, relay/RPC policy, deployment configuration, reconciliation, node/testnet architecture, wallet and on-chain UI integration.  
**Status:** **NOT WEB3-PRODUCTION READY**. The frozen V2 identity and relay foundations are substantially hardened, but unresolved P0/P1 lifecycle, recovery, bridge, reconciliation, governance and test-evidence issues remain.

| Priority | Area | Finding | Required action |
| --- | --- | --- | --- |
| 🔴 P0 | Card verification authority | A collector previously could update their own `CardVerificationSession`, including `status` and `verification_level`, while `mint-card` trusted those fields. | **Completed:** card verification-session create/update is backend/admin controlled, card identity is derived server-side, private image uploads are used, and possession-verified status requires a server-issued Level 2+ result. Preserve this boundary. |
| 🔴 P0 | Identity reconciliation / revocation | The live `ChainIdentity` still reports verification `ACTIVE` although its V2 assurance expired on 3 September 2026 at 00:14:34 UTC, and `last_reconciled_at` is still 2 September. No scheduled identity-reconciliation workflow exists. More seriously, `valueFeatureEligible()` trusts the mirrored revocation status until reconciliation, so an on-chain revocation before natural expiry can remain invisible to Base44 value-feature checks. | Schedule authenticated identity reconciliation, enforce a maximum reconciliation age for value-bearing actions, and have the relay or action boundary live-read effective verification/revocation for high-risk writes. Expiry/revocation must fail closed independently of stale mirrors. |
| 🔴 P0 | Staking asset recovery | Base44 applies `valueFeatureEligible()` to every staking action, including `request_undelegate`, `withdraw` and `exit_validator`. The UI also switches staking to read-only after expiry/revocation. The Cairo contract correctly permits those recovery actions without current verification, but the application layer blocks them. | Split staking into risk-increasing and recovery actions. Require current verification for registration, additional self-stake and delegation, but always allow the owner to undelegate, withdraw and exit subject to contract timing and ownership checks. |
| 🔴 P0 | Bridge event reconciliation | After bridge submission, Base44 stores the source transaction hash and marks the transfer `PENDING_RELAY`, but does not capture the authoritative `BridgeOutInitiated.nonce`. The reconciler skips transfers without a nonce, so the bridge lifecycle can become permanently unreconcilable. | Parse the accepted transaction receipt/event, persist nonce, asset, destination, recipient commitment and amount/token ID, and advance state only from authoritative chain events. |
| 🔴 P0 | Bridge destination safety | `chain-action-draft` validates a destination address only by supported chain name plus a coarse 8 to 120 character length. The raw destination is then committed and a token can be locked or a card burned. | Add strict destination-chain validation and canonicalisation before drafting/signing. Validate EVM checksum/length rules, Solana public keys, and every future destination format. Never lock or burn first and validate later. |
| 🔴 P0 | Card bridge recovery | `BridgeAdapter.bridge_out_card()` burns the source CardNft. `refund()` only restores token transfers, `release_inbound()` handles fungible tokens only, CardNft has no secure bridge remint entrypoint, and the original attestation remains permanently spent. A failed card bridge therefore has no demonstrated lossless recovery path. | Redesign card bridging before enabling it. Prefer lock-and-mint or add a narrowly authorised, replay-safe remint/recovery protocol that restores the exact burned token semantics. Prove failure, refund, replay and return-to-origin flows with integration/fuzz tests. |
| 🔴 P0 | Card mint reconciliation | `mint-card` changes `ChainCardToken` to `MINTED` immediately after receiving a transaction hash. It does not verify receipt success, parse `CardMinted`, or record the chain `token_id`. The mirror can therefore claim a confirmed mint without authoritative chain evidence and can later lack the token ID needed for bridge/ownership operations. | Introduce `SUBMITTED` first. Reconcile the receipt and `CardMinted` event, verify owner/card/attestation/level, persist `token_id`, and only then mark `MINTED`. |
| 🔴 P0 | Account deletion / Web3 identity lifecycle | `delete-account` does not revoke active on-chain identity verification, remove the private Base44 `ChainIdentity` user mapping, or address recovery-controller state. The immutable public identity anchor may remain by design, but a deleted account can leave an orphaned private mapping and a still-trusted verification assertion. | Define a deletion-specific Web3 lifecycle. Revoke current verification where policy requires, remove/anonymise the private user-to-chain mapping, invalidate app-side value eligibility, document what public chain data is immutable, and define how recovery/account ownership survives or is transferred without retaining deleted-user private data. |
| 🟠 P1 | Network verification freshness | `getVerifiedConfig()` checks that stored `verified_*` pins still equal configuration fields but does not enforce any maximum age on `last_verified_at`. The live config was last independently verified on 1 September 2026. | Add verification freshness policy and periodic live re-verification. High-risk actions should fail closed when deployment verification is stale or a live relay readiness proof cannot be obtained. |
| 🟠 P1 | Permanent V2 cut-over verification | `chain-network-verify` reads `verification_v2_required()` and returns its value, but it can still save the network as `CONFIGURED` when the configured mode is V2 and the on-chain one-way V2 requirement is false. | When `identity_verification_mode` is V2, require `verification_v2_required == true` before setting `CONFIGURED`. Preserve the irreversible-cutover invariant in every network activation path. |
| 🟠 P1 | Network policy verification | `chain-network-verify` verifies class hashes, owners, key wiring and bridge minter authority, but it does not pin/verify critical economic policy such as token max supply, staking minimum, unbonding period, usership reputation weight or enabled bridge destinations. | Extend the canonical manifest/config verification to critical immutable/governed policy parameters. A deployment with the correct class hashes but wrong economic configuration must not be treated as equivalent. |
| 🟠 P1 | Identity-registry governance | `IdentityRegistry` correctly supports self-sovereign `change_account_self`, but the registry owner can also unilaterally change an active identity account, merge identities and upgrade the registry. A single production owner therefore remains capable of changing user identity bindings. | Before real-value production, move privileged registry actions to documented multisig/timelock/governance with separation of duties, explicit emergency procedures and event monitoring. Limit unilateral account changes to narrowly defined recovery/governance cases. |
| 🟠 P1 | Recovery key separation | The live ChainNetworkConfig uses the same address for the recovery controller and registry owner. A compromise of that authority therefore affects registry administration and smart-account recovery together. | Use a separately controlled recovery authority, preferably threshold/multisig or dedicated recovery governance, with distinct keys, monitoring and operational procedures. |
| 🟠 P1 | Recovery-delay floor | `SwapPulseAccount.set_recovery_delay()` enforces only a 30-day maximum and permits a delay of zero. The account owner can therefore configure a recovery controller with immediate execution, undermining the timelock safety property if the controller is later compromised. | Enforce a non-zero production minimum when recovery is enabled, or make zero-delay an explicitly separate testnet-only mode that cannot be activated on production deployments. |
| 🟠 P1 | SWPX mint / upgrade governance | NativeToken uses OpenZeppelin ERC20 accounting and a max supply, but the owner can add/remove minters and upgrade the implementation. The bridge is also an authorised minter. These are central supply-control authorities. | Put production mint-authority and upgrades behind multisig/timelock/governance, publish the max-supply/minter policy and monitor every minter/upgrade event. |
| 🟠 P1 | Staking slashing governance | StakingPool limits a single slash to 50% and burns slashed SWPX, but slashing remains owner-controlled and does not require cryptographic service-fault evidence or governance approval. | Keep testnet slashing clearly labelled. Before real value, implement provable-fault/governance policy, appeal/emergency procedures and separate slash authority from ordinary application administration. |
| 🟠 P1 | Bridge trust model | `confirm_relayed`, `refund` and `release_inbound` are owner-only assertions. Inbound token release/mint trusts the bridge owner rather than a light-client proof, threshold attestation, destination receipt verifier or multi-party quorum. | Treat the current bridge as custodial/trusted infrastructure. Before production, define and implement the external-chain verification model, replay domain, relayer quorum/governance and compromise recovery. |
| 🟠 P1 | External bridge implementation | No application/relay implementation was found that calls `confirm_relayed` or `release_inbound`; those entrypoints exist only in the Cairo contract. The end-to-end destination-chain relay is therefore not implemented in the audited tree. | Keep external bridge chains disabled. Implement destination submission, confirmation, inbound verification, retries, finality policy, monitoring and recovery before exposing bridge-out as a usable cross-chain service. |
| 🟠 P1 | Bridge card mirror state | `chain-action-submit` changes a linked `ChainCardToken` to `BRIDGED_OUT` as soon as the source invoke receives a transaction hash, before receipt/event confirmation. | Introduce `BRIDGE_PENDING`; move to `BRIDGED_OUT` only after the source burn and `BridgeOutInitiated` event are confirmed and reconciled. |
| 🟠 P1 | Card token standard | `CardNft` manually reimplements NFT ownership, balance, transfer, metadata and burn semantics instead of using OpenZeppelin Cairo `ERC721Component`. It lacks standard ERC-721/SRC5 transfer/approval/safe-transfer interoperability expected by wallets and indexers. | For the next production-compatible card-token design, use the established OpenZeppelin ERC721 components/interfaces where possible. If retaining a custom token, formally document the non-standard interface and independently audit every reimplemented ownership/transfer invariant. |
| 🟠 P1 | Card administrative authority | CardNft owner can mint any card and burn any existing card, and can replace the authorised bridge. These controls are acceptable for a private testnet but are a material production custody/trust authority. | Move production mint/burn/bridge configuration behind separated roles, multisig/timelock/governance and auditable policy. Avoid a single owner that can both create and destroy collector assets. |
| 🟠 P1 | Card verification semantics | CardNft and `mint-card` permit verification level 0 self-attested tokens, while generated metadata describes every mint as a “verified card possession attestation”. Level 0 is not verified possession. | Make metadata and UI trust language level-aware. Either require Level 2+ for tokens marketed as verified possession or clearly label Level 0 as self-attested with no possession-verification claim. |
| 🟠 P1 | Proof-of-Usership source pipeline | `usership-aggregate` reads admin-controlled `PointsLedger`, but no current producer for `PointsLedger` was found and the live ledger is empty. The Proof-of-Usership scoring pipeline is therefore implemented downstream but inert upstream. | Define authoritative server-side producers for each scored action, with idempotency and anti-duplication rules, then integration-test activity -> ledger -> aggregate -> chain score end to end. |
| 🟠 P1 | Proof-of-Usership commitment integrity | The activity root commits only to sorted Base44 ledger record IDs. It does not commit to action type, point value, wallet/identity, epoch or other score inputs, so the root does not prove the actual score calculation represented on-chain. | Commit to a canonical, domain-separated serialization of every scored input and its points/identity/epoch, ideally as a Merkle/Poseidon-friendly structure suitable for later proof verification. |
| 🟠 P1 | Proof-of-Usership authority | `ProofOfUsership.submit_score` is owner-only and accepts an `identity_id` plus `account` without checking the IdentityRegistry binding itself. The app currently supplies a matching private mirror, but the contract does not enforce that relationship. | Bind the contract to IdentityRegistry or remove the redundant account field. Validate canonical identity/account ownership on-chain before accepting a score if the account value has security or audit meaning. |
| 🟠 P1 | Contract test coverage | Checked-in Cairo test source covers IdentityRegistry, SwapPulseAccount, NativeToken and StakingPool. No dedicated source test files were found for CardNft, BridgeAdapter, ProofOfUsership or HandleRegistry, despite compiled test artefacts existing under `chain/target`. | Add maintained Foundry unit/integration/fuzz suites for every deployed/value-bearing contract, especially card burn/bridge recovery, bridge replay/finality, usership epochs/commitments and handle reservation/merge cases. Do not treat generated artefacts as substitute source tests. |
| 🟠 P1 | Production signing model | STARK_V1 keeps the private Stark scalar encrypted in browser localStorage with a non-extractable AES key in same-origin IndexedDB. It avoids server custody, but a same-origin compromise can still invoke signing/decryption operations. | Keep STARK_V1 testnet-only. Move production value/identity signing to audited passkey/WebAuthn/P-256 or hardware-backed account validation with explicit transaction approval and recovery design. |
| 🟠 P1 | Reconciliation timestamp semantics | `chain-identity-reconcile` updates `last_reconciled_at` even when reconciliation fails and separately stores a `failure_code`. Consumers can mistake “last attempted” for “last successful”. | Add distinct `last_reconcile_attempt_at` and `last_successful_reconcile_at`, and base freshness/security decisions only on successful authoritative reconciliation. |
| 🟠 P1 | Emergency controls | Value-bearing contracts do not expose a narrowly scoped emergency pause/guardian mechanism. A bridge, mint or new-stake incident therefore relies on owner/upgrades or application-side disabling while direct contract entrypoints remain callable. | Design scoped emergency controls for risk-increasing operations before production. Never let an emergency pause strand withdrawals, undelegations, account recovery or other user asset-exit paths. |
| 🟠 P1 | Deployment / explorer provenance | The repository `chain-explorer` implementation is pinned to the canonical public RPC, but an earlier live check returned HTTP 503 while raw RPC was healthy. This audit did not independently prove that the currently deployed Base44 function matches the audited source commit. | Redeploy/verify the canonical explorer function, smoke-test production block/transaction/address reads and record the exact deployed commit/config with release evidence. |
| 🟠 P1 | Documentation vs live architecture | Root README describes the V2/token/staking/support-contract baseline as deployed, while `chain/README.md` still contains older Milestone 1/“Phase 2 undeployed” language and an obsolete 26-test baseline. `IDENTITY_REGISTRY.md` also describes the older owner-only verifier scaffold. | Reconcile all Web3 docs against the actual V2 deployment/config and current verifier-role architecture so operators do not follow obsolete security assumptions. |
| 🟡 P2 | OpenZeppelin / Cairo dependency generation | The repo is pinned to OpenZeppelin Contracts for Cairo 3.0.0 and Cairo/Starknet 2.13.1. OpenZeppelin’s current stable Cairo line is 4.x, which requires a newer Cairo/Scarb generation. A major-version upgrade is not storage-compatible by default. | Do not blindly upgrade live contracts. Create a deliberate dependency-migration assessment, review security fixes and 4.x components, and use a new compatible deployment/migration strategy where major-version storage compatibility cannot be guaranteed. |
| 🟡 P2 | Amount range | Shared `u256Parts()` rejects values above the low 128-bit word even though Cairo contract APIs accept full `u256`. | Either support canonical full 256-bit amounts or explicitly document/enforce the 128-bit product limit everywhere so ABI capability and application capability cannot diverge silently. |
| 🟡 P2 | Dead signer action | Base44 supports an `add_signer` draft/submit action, but the current `SwapPulseAccount` ABI has no `add_signer` entrypoint and no frontend caller was found. | Remove the dead action or implement a formally designed multi-signer account model. Do not leave security-sensitive key-management APIs that cannot succeed against the deployed account class. |
| 🟡 P2 | Card metadata persistence | Minted card metadata is uploaded to a normal HTTPS Base44 file URL. The on-chain token stores the URI and attestation hash, but not a content hash of the metadata document itself. | Use content-addressed or hash-anchored metadata if long-term independent integrity is a goal, and define retention/migration behaviour for metadata hosting. |
| 🟡 P2 | Bridge chain namespace | The bridge encodes destination `2` as generic `L2`, which is not a unique chain identity once more than one L2 is supported. | Replace generic chain codes with a versioned registry of explicit destination networks/domains before external bridging is enabled. |
| 🟡 P2 | HandleRegistry deployment | HandleRegistry is compiled into the Cairo project but is not part of the current canonical SWAPPULSE_TESTNET ChainNetworkConfig/deployment set. | Treat it as undeployed/future functionality until its address/class hash, ownership, tests, migration and Base44 integration are explicitly verified. |
| 🟡 P2 | Rewards / decentralisation scope | Staking currently bonds community operators on a single Devnet runtime. There is no deterministic production reward distributor and no decentralised sequencer/validator consensus. Current operator documentation correctly warns about this. | Preserve the cautious wording. Do not advertise consensus security or token earnings until reward policy, multi-operator network architecture, governance and independent security review are real and verified. |
| 🟡 P2 | Fresh test execution | Cairo/Foundry tests could not be rerun in the Base44 sandbox because Scarb/snforge are not installed. The transaction-relay smoke suite also could not run because its local `starknet` npm dependency is absent in this sandbox. The documented 63-pass baseline is therefore historical evidence, not a fresh audit run. | Run `chain/scripts/test-chain.sh` and the relay policy suite in the pinned CI/toolchain environment against the exact release commit and attach machine-readable results before release. |
| 🟢 P3 | Card supply naming | `CardNft.total_minted` is decremented on burn, so it represents current live supply rather than lifetime total minted. | Rename the API/state in a future compatible version or add separate lifetime-minted and circulating-supply counters to avoid indexer ambiguity. |
| 🟢 P3 | Generated chain artefacts | Large compiled contract/test artefacts are present under `chain/target`. They can become stale relative to Cairo source and give a misleading impression of current test coverage. | Treat generated artefacts as disposable build output or record their source/toolchain hash explicitly. Never use their presence as proof that the current source compiled or passed tests. |
| 🟢 P3 | Legacy wallet models | Legacy `CustodialWallet`, `MultiChainWallet`, `MetaTransaction` and `WalletLink` schemas remain in the project, although they are admin-quarantined and the live queries in this audit returned no records. | Remove obsolete schemas after confirming no migration dependency remains, so future development cannot accidentally reintroduce custodial/key-server patterns. |

## Controls verified as strong in this audit

The audit also confirmed important security properties that should be preserved: no plaintext personal identity data is stored in the reviewed Cairo identity contracts; V2 attestations have one-time replay identifiers and dynamic expiry; verifier authority is separate from registry ownership; the user transaction flow signs an exact server-drafted V3 invoke and the submit path reconstructs calldata before forwarding it; privileged verifier/admin/recovery keys stay in the relay rather than browser code; legacy custodial wallet tables are empty and quarantined; the raw Devnet RPC is separated from the public gateway; and the public RPC gateway policy smoke test passed on 11 September 2026 with write methods, Devnet administration methods and batch requests blocked.

## Web3 release decision

SwapPulse should **not enable real-value production Web3 or external bridging while any P0 remains unresolved**.

Recommended remediation order:

**identity reconciliation/revocation freshness -> staking exits/withdrawals -> card mint receipt reconciliation -> bridge nonce/destination safety -> card bridge recovery -> deletion/revocation lifecycle -> governance/key separation -> Proof-of-Usership integrity -> complete contract tests -> production signer and external security review.**

After remediation, rerun the pinned Cairo/Foundry suite, relay policy smoke tests, RPC gateway policy tests, manifest verification against the public RPC, Base44 ChainNetworkConfig verification, V2 expiry/revocation/recovery tests, staking exit tests and end-to-end bridge/card lifecycle tests against the exact deployment commit.
