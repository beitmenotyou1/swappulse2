# SwapPulse Backend Audit

**Audit date:** 11 September 2026  
**Scope:** Base44 backend functions, shared server utilities, entity/RLS trust boundaries, authentication and account security, privacy/consent, federation/PDS integration, notifications, moderation/enforcement, community/trading state, uploads/imports, payments, scheduled workflows, Web3 orchestration and backend operational state. Pure frontend presentation and Cairo contract internals are outside scope except where Base44 backend behaviour directly controls them.  
**Status:** **NOT BACKEND-RELEASE READY**. Multiple unresolved P0 findings remain. Source/live-state review is complete, but build/test verification could not be rerun because the Base44 command workspace is currently empty.

## Verified backend controls and strengths

The audit also re-verified important controls that should be preserved during remediation:

- WebAuthn challenges are cryptographically random, HMAC-authenticated, short-lived, origin/RP-bound and single-use.
- Security-factor enrolment in the active UI requires a fresh email step-up capability; protected User/WebAuthn fields are backend-controlled.
- Login verification limits failed email-code/TOTP/WebAuthn attempts and checks suspension before returning the passwordless bridge credential.
- The age-verifier webhook uses HMAC authentication, a 16 KB request cap, strict metadata-only field allowlisting, stale/replay handling and fail-closed Base44 eligibility before chain synchronisation.
- PDS session helpers require HTTPS, validate DNS/IPs against SSRF, reject unsafe redirects and bind the authenticated DID to the expected PDS origin.
- Link-preview fetching revalidates every redirect target against the SSRF guard and uses a hard five-second timeout.
- Discord interaction verification uses Ed25519 signatures plus timestamp/app/guild checks; Discord OAuth linking uses signed/single-use state and does not persist OAuth access tokens.
- Status subscription confirmation is HMAC-signed and double-opt-in.
- General email/push broadcast functions are admin-only; `sendEmail` limits recipients to registered users and strips arbitrary HTML.
- Stripe donation completion is never trusted from the browser redirect alone; the session/amount/currency are verified directly with Stripe.
- AI moderation is advisory-only and cannot directly hide content, issue strikes or restrict an account.
- Sensitive active PDS app passwords are AES-GCM encrypted on the User record. The remaining plaintext risk is confined to the retired migration store identified above.
- Dedicated service-role visibility wrappers for binders, journals, visible posts/trades and story-viewer lists reapply ownership/visibility checks after bypassing RLS.

## Backend release decision

The Base44 backend should **not be considered production-ready while unresolved P0 findings remain**.

Recommended remediation order:

**push-token ownership and cross-post IDOR → account deletion/credential erasure → federation consent → Friendship/labeler/vouch/reputation/trust fields → Post/TradeListing/Challenge/Voice Space server authority → staking/bridge/card lifecycle → chain reconciliation and PDS delivery recovery → custom handles → DM/conversation/trade-message boundaries → notification/preferences/consent binding → imports/uploads/payment webhooks → automated backend security tests.**

After remediation, rerun this audit against the exact Base44/GitHub deployment commit and require backend integration/security tests, build/lint/type policy, scheduled-workflow smoke tests, PDS/federation tests, deletion/export tests, SSRF tests, notification privacy tests and chain orchestration tests to pass before declaring the backend release-green.
