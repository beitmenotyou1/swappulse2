# SwapPulse Backend Audit

**Audit date:** 11 September 2026  
**Scope:** Base44 backend functions, entity/RLS boundaries, authentication and MFA, service-role use, PDS/federation orchestration, notifications, imports/uploads, payments, privacy/deletion, scheduled workflows, external API consumption and backend test coverage.  
**Status:** **NOT BACKEND-PRODUCTION READY**

This audit follows `AUDIT_STANDARD.md`. Severity is based on impact and exploitability. A finding being exploitable does not mean exploitation was observed. Where live data was checked, that distinction is stated explicitly.

| Priority | Area | Finding | Required action |
| --- | --- | --- | --- |
| 🔴 P0 | Actor identity binding | Numerous user-created, actor-bearing entities, including `Post`, `TradeListing`, `Journal`, `Binder`, `Story`, `VoiceSpace`, `Follow`, `Vouch` and `Friendship`, permit creation based on `created_by_id` but do not make the actor `did` backend-derived/immutable. A modified client can therefore create records that claim another collector's DID. Those DID fields are later trusted by feeds, relationship checks, reputation, notifications and federation code. | Make actor identity backend-derived for every user-originated record. Clients must not be able to set or change `did`, actor/author DID, federation ownership fields, `bridged`, `at_uri`, `cid`, `record_type` or equivalent provenance fields. Add a migration scanner that verifies every user-originated row against the authoritative User/identity mapping and quarantines mismatches. |
| 🔴 P0 | PDS confused-deputy write | `outbound-reconcile` groups bridged records by `did` and uses that DID owner's stored PDS credentials, but does not require the record's `created_by_id` to be that user. Because user-created federated entities can also set `did`, `bridged` and `at_uri`, a forged local record can be selected during the recurring five-minute reconciliation and created/updated inside another collector's PDS repo using the victim's credentials. `initial-push-custom-records` has the same ownership assumption for records matching a user's DID. | Immediately bind every PDS write to an authoritative local owner. Require `created_by_id == user.id`, verify the record actor DID equals the authenticated PDS session DID, verify the `at_uri` repository DID equals that same DID, reject client-supplied federation state, and quarantine existing ownership/provenance mismatches before re-enabling bulk/reconciliation writes. Add negative integration tests proving one user cannot cause any write under another user's PDS session. |
| 🔴 P0 | Push notification confidentiality | `PushToken` create RLS binds only `created_by_id`; `data.did` is not bound to the authenticated collector. The privileged dispatcher later selects subscriptions by recipient DID. A signed-in attacker can therefore register an attacker-controlled push endpoint under another collector's DID and receive that collector's push payloads. | Make PushToken creation/update backend-only. `register-push-token` must derive DID from the authenticated User, enforce endpoint ownership/uniqueness and reject a token already associated with another identity. Migrate or invalidate inconsistent rows and add cross-user notification tests. |
| 🔴 P0 | Cross-post object authorisation | `crossPostDispatcher` validates that the caller owns their CrossPostConfig but reads caller-supplied `contentId` values through the service role for posts, journals, binders, podcasts, trades, voice spaces and card reviews without proving the source content belongs to the caller or is eligible for cross-posting. A known record ID can therefore cause another user's content, including non-public content, to be rendered and published through the attacker's external account. | Add per-type authoritative ownership and visibility checks before any service-role read is used for publication. Prefer a shared `canCrossPost(caller, entity)` policy and fetch user-owned content through the user-scoped API where possible. Reject private/followers-only content unless the product explicitly defines and verifies a safe publication transition. |
| 🔴 P0 | Friends-only privacy | `Friendship` creation does not bind `did` to the caller and permits client-controlled relationship status. `get-profile-config` considers a relationship mutual when accepted rows exist in both directions. A malicious client can create both accepted rows itself, including one that claims the target DID, and unlock profile fields intended for friends only without the target accepting. | Move friendship request/accept/reject transitions behind backend functions. Derive the initiator DID from authentication, allow only the target to accept their pending request, enforce a unique unordered relationship pair, and have privacy checks consume only server-authoritative relationship state. |
| 🔴 P0 | Federated actor integrity | The authenticated generic `atproto-bridge` create path accepts caller-supplied custom record bodies, while multiple inbound custom-record mappers prefer payload fields such as `voucherDid`, `authorDid`, `curatorDid` or `reviewerDid` over the repository DID. A collector can publish from their own repo while claiming another collector as the actor, and SwapPulse can ingest that claimed actor identity. | Derive actor identity from the authenticated PDS session and the repository component of the AT URI, never from mutable record-body actor fields. Restrict generic create to trusted backend capabilities or route collectors through authoritative per-record publication functions. Reject body actor fields that disagree with the repo DID and test malicious custom records end-to-end. |
| 🔴 P0 | PDS credential storage | The retired `PdsCredential` schema stores `app_password` in plaintext. The live database still contains **three** `PdsCredential` records even though current identity code uses encrypted credentials on the User record. These duplicate long-lived PDS authentication secrets remain recoverable to privileged database/backend access. | Migrate and securely delete all legacy PdsCredential rows, remove the schema and every fallback reader after migration, rotate the affected PDS app passwords, and verify logs/backups/exports do not retain plaintext copies. Keep only encrypted backend-only credential material. |
| 🔴 P0 | Account deletion coverage | `delete-account` uses a hand-maintained deletion list that omits multiple sensitive/user-linked entities, including authentication/security records, PDS credentials, age-verification data, consent/preferences, conversations/messages, Discord linkage and Web3 identity mappings. Deleting the User record therefore does not guarantee deletion or anonymisation of the user's private backend footprint. | Replace the manual list with a versioned data-inventory deletion policy covering every entity by ownership/participant key. Define delete, anonymise, legal-retention and immutable-ledger treatment per entity, include PDS and Web3 lifecycle actions, and continuously test the inventory against the actual entity catalogue. Do not delete the User identity until all mandatory cleanup is confirmed or durably queued. |
| 🟠 P1 | Deletion transactionality | Both self-service deletion and admin `force_delete` continue after individual cleanup failures and can still delete the User record. The response may contain per-entity errors while the identity needed to retry has already gone. | Implement a durable deletion job/state machine with idempotent phases, retryable failures and an auditable tombstone. Only finalise User deletion after required phases succeed. Keep self-service and enforcement deletion on the same shared engine so their inventories cannot drift. |
| 🟠 P1 | Admin force-delete drift | `enforcement` contains its own independent cleanup list, which is already different from `delete-account` and also omits sensitive/user-linked entities. Two deletion implementations can therefore produce different privacy outcomes for the same account. | Replace both copies with one tested deletion service and one canonical data-retention inventory. Enforcement should supply policy/reason parameters to that same service rather than maintain a separate cascade. |
| 🟠 P1 | Security factor removal | The live settings UI uses email step-up plus `security-factor-manage` to disable TOTP or remove WebAuthn credentials. A stronger parallel API exists that requires the current authenticator/passkey, but it is not the path used by the current settings UI. A stolen session plus email access can therefore remove the second factor that is meant to protect the account. | Require re-authentication with the strongest currently enrolled factor before removing or weakening MFA, with a separately designed recovery ceremony when that factor is unavailable. Wire the UI to the stronger backend and retire duplicate weaker factor-management endpoints. |
| 🟠 P1 | Rate-limit atomicity | Authentication/TOTP and bot-risk throttles use database read-modify-write counters without a unique atomic increment/compare-and-set boundary. Parallel requests can race and exceed intended request/attempt ceilings. | Use an atomic rate-limit primitive or unique keyed row with atomic increment/expiry semantics. Apply limits across account, IP/network and device dimensions where appropriate, and add concurrency tests that deliberately race verification attempts. |
| 🟠 P1 | Notification preference integrity | `NotificationPreference` creation is bound to `created_by_id`, but its `did`/user identity fields are not bound to the authenticated collector. The privileged notification filter selects a recipient's newest preference by DID, so another user can create a newer preference that suppresses or changes delivery for the victim. | Make preference mutation backend-only and derive `user_id`/DID from the authenticated account. Enforce one authoritative preference record per user and ignore any legacy row whose owner mapping does not match. |
| 🟠 P1 | Notification event integrity | `notify-interaction` binds the actor to the current user but accepts arbitrary recipient DID, action type and referenced content metadata without proving the interaction/resource actually exists or that the recipient owns the subject. This permits authenticated notification injection/spam toward arbitrary collectors. | Build notifications from authoritative persisted actions instead of caller assertions. For each notification type, load the source object, verify actor/recipient roles, deduplicate event IDs and rate-limit delivery. |
| 🟠 P1 | Direct-message encryption invariant | The normal DM client encrypts messages, but the DirectMessage backend/entity boundary does not enforce an encrypted envelope, conversation membership, recipient relationship or immutable sender identity strongly enough to make E2EE a server-enforced invariant. A modified client can persist plaintext or malformed message records outside the intended DM path. | Route DM creation through one backend `send-dm` capability. Derive sender identity, validate conversation membership/recipient, require a versioned encrypted envelope and bounded ciphertext size, prevent federation, and make direct entity creation unavailable to collectors. |
| 🟠 P1 | Invite authority | `InviteCode` can be directly created by an authenticated user with client-controlled code, inviter metadata, origin and status because create RLS only binds `created_by_id`. Public validation/redemption later trusts active invite records. This allows forged/admin-labelled invitations and relationship side effects outside the intended invite-generation path. | Make InviteCode writes backend-only. Generate codes cryptographically server-side, derive inviter DID/role from authentication, make origin/status immutable except through the invite state machine, enforce uniqueness/expiry/usage atomically and migrate malformed rows. |
| 🟠 P1 | Private circle membership | `follow-starter-pack` uses service-role writes to join every circle listed in a starter pack but does not apply the private-circle admission checks enforced by the normal `circle-membership` path. A starter pack containing a private circle can therefore bypass its membership policy. | Route every starter-pack join through the same central circle authorisation policy, or restrict packs to explicitly public/joinable circles and enforce that restriction on pack creation/update and follow. |
| 🟠 P1 | Public activity privacy | `get-activity` is public and uses the service role to aggregate journals, binders, trades, stories, meetup RSVPs and challenge activity by DID without consistently applying each resource's visibility rules. Metadata such as the existence/title of a private binder or non-public journal can leak through the activity stream. | Apply the canonical visibility policy for every activity source before projection. Build a guest-safe activity view from visibility-authorised records rather than querying private entities under service role and filtering ad hoc. |
| 🟠 P1 | Data export completeness | `export-my-data` relies on a fixed entity list and does not cover all user-linked data classes such as consent/preferences, authentication/security metadata, age verification, push/WebAuthn data, PDS/Discord identity linkage, Web3 mappings and participant-side conversation/message data. | Generate export coverage from the same canonical data inventory used for deletion. Define ownership/participant selectors per entity and regression-test that a synthetic user's complete footprint appears in the export while secrets that must not be re-exposed are represented safely. |
| 🟠 P1 | Vouch/reputation integrity | `Vouch` actor DID can be supplied by the client, while trust-profile calculation uses the stored voucher DID as identity evidence. A modified client can therefore create vouches that claim arbitrary voucher identities and distort portable/local trust calculations. | Make vouch creation backend-only or bind voucher DID to authenticated identity at schema/function level. Deduplicate by authoritative voucher/subject pair and recompute affected trust data after cleaning mismatched historical rows. |
| 🟠 P1 | External integration secrets | `CrossPostConfig` stores external integration credentials in owner-readable plaintext fields, including values that can represent webhook URLs, OAuth/bot tokens or other long-lived publisher credentials. | Move external credentials to backend-only encrypted secret storage. Return only masked metadata to clients, separate non-secret configuration from credentials and rotate existing credentials after migration. The live CrossPostConfig table was empty during this audit, so this is a design exposure rather than a currently observed stored-secret instance. |
| 🟠 P1 | AI import resource controls | `extract-collection-import` describes a 10-extractions-per-hour limit but actually counts recent `CollectionEntry` rows and only blocks at 5,000, so the intended AI extraction rate limit is effectively absent. | Create an atomic extraction-usage ledger keyed by user/time window and enforce a real per-user plus platform-wide budget before invoking the paid extraction integration. Add file-size/page/row limits and abuse telemetry. |
| 🟠 P1 | Import file ownership | `extract-collection-import` accepts an arbitrary HTTPS `file_url` rather than a private file URI proven to belong to the caller. The backend can therefore be used as an authenticated extraction proxy for remote content the user did not upload. | Accept only user-owned private Base44 file URIs or short-lived signed upload handles produced by an authenticated upload step. Verify ownership, MIME/magic bytes and size before model/integration use. |
| 🟠 P1 | PDS media quota | `pds-blob-upload` permits authenticated users to upload images up to 10 MB per request but has no durable per-user upload rate/storage quota. Users without a personal PDS may fall back to shared bridge-account storage, concentrating abuse and cost. | Add per-user request and storage quotas, enforce total daily/monthly limits, prefer personal PDS ownership for user media, sniff/transcode accepted images and monitor shared-account usage. |
| 🟠 P1 | Link-preview resource exhaustion | `fetch-link-preview` has strong SSRF/redirect controls and a timeout, but reads the entire response via `res.text()` without an upstream byte cap or per-user request budget. A very large public HTML response can consume function memory/bandwidth. | Stream with a strict response-byte ceiling, reject excessive `Content-Length`, stop reading after the cap, cache normal previews and apply per-user/IP rate limits. |
| 🟠 P1 | Repository import resource exhaustion | `import-repo` accepts a caller-supplied archive payload and can iterate external PDS/local writes without a strict archive byte limit, record/collection count cap, supported-collection allowlist or durable import-rate budget. | Import from an authenticated private upload, validate archive version/schema before processing, enforce hard byte/record/collection limits, allow only supported collections, provide dry-run validation and add idempotent resume/retry semantics. |
| 🟠 P1 | Workflow authentication model | Multiple active scheduled workflows invoke backend functions that require an authenticated `admin` user, while other workflow definitions are explicitly disabled because scheduled invocations do not yet have a platform-verifiable privileged identity. The internal caller model is therefore inconsistent and not demonstrated by tests in the audited tree. | Define a dedicated service principal/capability for scheduled work with narrow per-function scopes. Do not impersonate a human admin session. Integration-test every enabled workflow from the real scheduler and document which functions accept service capabilities versus interactive admin sessions. |
| 🟠 P1 | Stripe payment finality | Fiat donations are reconciled only when the browser return flow calls `verify-fiat-donation-session`. No Stripe webhook signature handler for `checkout.session.completed` or later payment events was found. A donor who pays and closes/navigates away before verification can leave local state pending indefinitely. | Add an idempotent Stripe webhook with official signature verification and an event ledger. Treat webhook/provider state as authoritative, keep browser verification as UX fallback, and reconcile stale pending sessions periodically. |
| 🟠 P1 | PDS token origin | `initial-push-custom-records` authenticates each user against their stored per-user PDS URL, but its subsequent `createRecord` fetch uses the global `PDS_URL` environment origin while sending that user's access JWT. If the origins differ, a bearer token is sent to the wrong server. A live migrated user currently has an external per-user PDS URL, while the global secret value was not inspectable through this audit. | Always use the validated `pdsUrl` returned by `getPdsSessionForUser` for every request carrying that session's JWT. Never combine a token from one origin with a separately configured origin. Add a test with two different PDS origins that fails if a token crosses origins. |
| 🟠 P1 | Backend security regression tests | The audited backend contains a very large function/RLS surface, but source search found only a small shared-client test suite and no maintained comprehensive backend authorization/RLS/security regression suite for the critical service-role boundaries found here. | Add automated negative tests for every user-facing service-role function and every sensitive entity: cross-user IDs, forged DIDs, role escalation, direct entity writes, workflow/service-principal calls, SSRF, rate-limit races, deletion/export completeness and federation confused-deputy cases. Make them release-gating. |
| 🟡 P2 | Legacy 2FA endpoint | `verify-2fa` retains an unauthenticated compatibility mode keyed by email. It returns `verified: true` when the target account has no TOTP and verifies TOTP by email when enabled. It does not currently issue a login/session credential and no current frontend default-mode caller was found, but it is a dangerous legacy security oracle that can be misused by future callers. | Remove the unauthenticated compatibility mode. Any factor verification endpoint should require a first-factor/security-flow capability and return only a short-lived audience-bound proof that cannot be treated as a generic boolean authorization signal. |
| 🟡 P2 | Login-code secret at rest | Login email codes are stored as raw six-digit values in the admin-only `LoginCode` entity, while newer security-step-up flows use protected token/code handling. A database/service-role read during the short validity window exposes usable authentication codes. | Store login codes as HMAC/hash values using a server-side secret/pepper, compare safely, preserve one-time consumption and keep only non-sensitive audit metadata. |
| 🟡 P2 | Turnstile context | Turnstile verification paths generally test only provider `success`; they do not consistently bind the response to expected hostname/action/cData/remote context and some calls lack an explicit outbound timeout. | Centralise Turnstile verification, validate expected hostname and action where available, bind challenge context, send remote IP only when appropriate, and use a bounded timeout/fail-closed policy. |
| 🟡 P2 | Donation verification abuse | `verify-fiat-donation-session` is public and performs a Stripe API lookup for any syntactically valid high-entropy Checkout Session ID. It has no rate limit and returns payment status plus amount/currency and a masked email when the ID is known. | Rate-limit by IP/session token, minimise response data, consider binding the success page to a signed browser state and cache/reconcile provider results so arbitrary repeated calls cannot consume Stripe/API capacity. |
| 🟡 P2 | Public health diagnostics | `health-check` is unauthenticated and exposes dependency-by-dependency health, latency/configuration state and error information. It does not return secret values, but it gives public callers detailed operational intelligence about backend dependencies. | Keep a coarse public readiness result and move detailed dependency/error/configuration diagnostics behind staff authentication or an internal monitoring endpoint. |
| 🟡 P2 | Legacy plaintext fallback | `getUserIdentity` attempts to decrypt the consolidated PDS app password but can fall back to treating the stored value as plaintext for legacy compatibility. This can mask migration/encryption failures and allows plaintext to survive indefinitely. | After the credential migration/rotation is complete, remove the plaintext fallback and fail closed on decryption errors. Store an explicit credential format/version so migration state is never inferred from a failed decrypt. |
| 🟡 P2 | Base44 SDK version drift | The backend imports both `@base44/sdk@0.8.40` and `@base44/sdk@0.8.44` across security-sensitive functions. The audit grep returned hundreds of imports, with most still on 0.8.40 while newer Web3/security paths use 0.8.44. | Pin one reviewed SDK version through a central dependency/import policy and upgrade coherently after regression testing. Avoid function-by-function dependency drift in authentication/service-role code. |
| 🟡 P2 | Third-party request resilience | Several fixed-origin integrations use plain `fetch()` without a shared timeout, response-size cap, bounded concurrency or circuit-breaker policy, including federation/AppView and migration paths. A slow or oversized upstream can consume backend execution capacity even when SSRF is not possible. | Introduce a shared external-request wrapper with timeout, redirect policy, byte caps, bounded concurrency, retry/backoff rules and safe error normalisation. Apply provider-specific limits consistently. |
| 🟡 P2 | Bridge blob fetch limits | `atproto-bridge` image/blob publication fetches remote allowlisted media and can buffer it before upload without the same strict byte/magic-type controls used by safer private-upload paths. Caller-provided MIME metadata is not a substitute for verifying the bytes. | Enforce byte caps before and during download, verify image magic/type, transcode where practical, use timeouts and reject unexpected content regardless of declared MIME. |
| 🟡 P2 | Account discovery by email local part | Authenticated `resolveUser` compares search input with the local part of users' email addresses. Although it does not return the full email, it can reveal that a particular email-style identifier maps to a SwapPulse account even when it is not the person's public handle. | Resolve users only through intended public identifiers such as handle/DID/display name. Do not use private email-derived identifiers as a discoverability key unless the user has explicitly opted in. |
| 🟡 P2 | Custom handle validation | `migrate-to-swappulse` accepts a caller-provided custom domain/handle and relies primarily on the PDS to reject invalid/unverified values. | Validate handle syntax and expected ownership flow in SwapPulse before attempting the PDS change, and separate custom-domain verification from the migration state machine so failures are deterministic and auditable. |
| 🟡 P2 | Backend endpoint inventory | Two factor-management families (`security-factor-manage` and `security-factor-management` plus different code/step-up flows) coexist, as does the legacy `verify-2fa` endpoint. This increases the chance that UI or future code selects a weaker path. | Consolidate authentication/security operations behind one versioned API, tombstone old routes with 410 responses, and maintain an endpoint inventory that identifies owner, authentication mode, callers and deprecation status. |
| 🟢 P3 | Login-code expiry copy | `send-login-code` and the actual verification policy use a short code lifetime, but user-facing email copy has historically described a longer validity window. | Make displayed expiry text come from the same constant/policy used by verification so security copy cannot drift. |
| 🟢 P3 | Crypto donation dead inventory | `CryptoDonation` describes backend creation and NowPayments IPN functions that are not present in the current function tree, and the current Donate UI exposes card donations only. This is stale backend/data-model inventory rather than an active payment vulnerability. | Remove or clearly archive the unused schema/documentation, or restore the full signed-IPN implementation only if crypto donations are intentionally reintroduced. |
| 🟢 P3 | Placeholder/temp entity surface | The entity directory still contains numerous `__noop*`, `_noop*` and `Tmp*` schemas from previous scaffolding/migrations. Even when harmless today, they enlarge the backend inventory and can acquire unsafe default access rules later. | Remove unused placeholder/temp schemas after confirming no migration/workflow dependency. Keep a small explicit migration history instead of permanent live schema clutter. |
| 🟢 P3 | PDS error detail | Some PDS session/request helpers include upstream response bodies or provider messages in internal thrown errors/logs. Current user-facing callers usually normalise these, but the practice increases the chance that provider detail is surfaced accidentally by a future endpoint. | Normalise provider errors at the shared helper boundary, log safe structured codes plus restricted diagnostics, and never propagate raw authenticated-provider bodies to user responses. |

## Live-state observations

The audit queried selected live Base44 entities without exposing credential values:

- Three User records existed at audit time.
- One User was marked as migrated from Bluesky and had an external per-user PDS URL.
- The retired plaintext `PdsCredential` table contained **three records**.
- The old SwapPulse `AppPassword` table contained **zero records**.
- `Friendship` contained **zero records** and `Vouch` contained **zero records**, so the relationship/reputation spoofing findings are exploitable design flaws rather than evidence of current abuse.
- `CrossPostConfig` contained **zero records**, so its plaintext credential finding is a storage-design risk with no live configured credential observed during this audit.
- A PushToken record existed, but this audit found no evidence that the DID-spoofing weakness had been abused.
- Imported/federated Post rows are commonly service-created and legitimately carry remote repository DIDs. Therefore a simple `created_by_id`/DID mismatch query is not sufficient to identify malicious posts; migration checks must distinguish trusted ingestion provenance from user-originated records.

## Verified strengths

Several backend controls are already well designed and should be preserved while fixing the findings above:

- `pdsSession.ts` validates user-supplied PDS origins, rejects credentials in URLs, applies SSRF checks, uses HTTPS, sets request timeouts, keys per-user session cache entries by **DID plus PDS origin**, and verifies the PDS returns the expected DID.
- The age-verifier webhook uses an HMAC secret and verifies the raw request body before privileged processing.
- Current `ai-moderation` is advisory-only. It does not independently hide content, add strikes or restrict accounts.
- Login-code verification is one-time and bounded by expiry/attempt logic; WebAuthn challenges are short-lived and single-use.
- The stronger WebAuthn/TOTP management path requires current-factor proof, even though the current settings UI is not using that path consistently.
- `fetch-link-preview` already has meaningful SSRF/private-network protections and manually validates redirects. The remaining finding is resource bounding, not arbitrary internal-network access.
- Sensitive User fields such as PDS app-password/signing material are not intentionally exposed by the public profile lookup functions inspected; those functions project selected public fields.
- Admin/test utilities inspected (`post-test-standard`, affiliate test, welcome-email test, synthetic chain verifier) are role-gated rather than anonymously callable.
- The unsafe legacy PDS migration function has been replaced by an explicit HTTP 410 tombstone instead of forwarding origin-bound credentials to a target PDS.
- No privileged backend secret values were found embedded in frontend source. Frontend references to secret names are administrative instructions, not secret contents.

The highest-risk backend findings align directly with the current OWASP API Security Top 10 categories, especially API1:2023 Broken Object Level Authorization, API3:2023 Broken Object Property Level Authorization, API4:2023 Unrestricted Resource Consumption, API5:2023 Broken Function Level Authorization, API7:2023 SSRF, API9:2023 Improper Inventory Management and API10:2023 Unsafe Consumption of APIs.

## Verification limitations

This was a source/RLS/live-entity audit through the Base44 MCP surface. The Base44 command sandbox available in this session does not expose the application source tree to shell commands even though MCP file operations do, so a full backend build/typecheck/test run could not be executed from that shell environment.

Source search found only a small shared-client test area and did not find a comprehensive release-gating backend authorization/RLS suite. Because of that, the audit must **not** be treated as dynamically proving absence of additional backend vulnerabilities.

The global `PDS_URL` secret value was not exposed or read. Therefore the `initial-push-custom-records` token-origin finding is based on the code's unsafe mixing of a per-user session with a separate global origin. A live migrated user does have an external per-user PDS URL, but this audit does not claim the global origin is definitely different.

## Backend release decision

**Do not treat the backend as production-ready while the unresolved P0 findings remain.** In particular, do not rely on recurring federation reconciliation as a safe cross-user boundary until actor identity and PDS write ownership are backend-enforced.

Recommended repair order:

1. Freeze/guard federation writers against cross-user PDS writes and bind all actor identity fields server-side.
2. Lock PushToken and NotificationPreference ownership to authenticated identity.
3. Fix CrossPost object authorisation and friendship/private-profile relationship state.
4. Remove/rotate live plaintext PDS credentials and eliminate plaintext compatibility fallback.
5. Replace account deletion/force-delete with one durable canonical deletion engine.
6. Harden MFA factor removal, invite creation, DMs and starter-pack circle membership.
7. Fix public activity/data-export privacy coverage.
8. Add resource controls for AI import, repo import, media and link previews.
9. Introduce a real scheduler service principal and provider webhooks/reconciliation.
10. Build a release-gating backend security suite, then rerun the full audit against the exact release commit.
